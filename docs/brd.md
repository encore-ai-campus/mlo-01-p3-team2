## 1. 배경과 문제

교육생이 학습, 질문, 프로젝트 공유와 교류를 서로 다른 공간에서 진행하면 참여 흐름이 끊기고 활동 이력을 함께 살피기 어렵다. 플랫폼에 광고를 제공하는 경우에도 광고 등록·노출·반응·포인트 사용을 같은 기준으로 추적할 수 있어야 한다.

이번 프로젝트는 18층 캠퍼스와 옥상 광장으로 구성된 메타버스 공간에 학습·커뮤니티·교류 콘텐츠를 모은다. 이용자의 활동과 광고 반응은 각 서비스의 업무 기록으로 보존하고, 계약에 따른 이벤트 수집·표준화·분석 흐름으로 연결한다.

핵심 문제는 화면을 만드는 것에 그치지 않는다. 학습 결과와 보상, 광고 예산과 과금, 서비스 기록과 수집 이벤트가 중복이나 누락으로 서로 달라지지 않도록 해야 한다. 장애가 발생했을 때도 원천 기록을 추적하고 다시 처리할 근거가 필요하다.

## 4. 이번에 할 일

### 4.1 캠퍼스와 사용자 활동

- 로그인·세션, 닉네임·아바타와 캠퍼스 이동을 제공한다.
- 18층·옥상 전환, 출입·충돌 처리와 콘텐츠 진입·복귀를 연결한다.
- 실시간 채팅, 게시글·댓글, 프로젝트·학습 정보 공유를 제공한다.
- 옥상의 휴식 공간·분수, 게임·심리 테스트·영상 등 콘텐츠 연결을 제공한다. 외부 콘텐츠 진입 기록과 외부 서비스 내부의 이용 완료는 구분한다.

### 4.2 Python·SQL 학습

- 과목, 초·중·고급, 객관식·빈칸 채우기를 구분한다.
- 각 분류의 200문제 중 10문제를 무작위로 출제하고 한 세션 안에서 문제 중복을 방지한다.
- 최대 3회 시도, 정답 판정·해설, 7/10 통과, 학습 결과·오답 복습과 세션 재개를 제공한다.
- 문제은행의 정답·해설·난이도를 검토하고 등록 명령으로 구성별 개수와 중복을 확인한다. 수량 충족과 교육적 품질 검수는 별도 기준으로 관리한다.
- 확정된 Python·SQL 강의실과 학습 팝업 디자인을 유지한다.

### 4.3 포인트와 광고

- 학습 정답에 난이도별 보상을 지급한다. 객관식·빈칸 채우기에 같은 정책을 적용한다.
- 개별 정답 시도의 `attempt_uuid`를 지급 기준으로 삼고 중복 제출 요청을 식별한다. 새로운 반복 학습의 정답에는 재지급을 허용하며 일일 지급 횟수 제한을 두지 않는다.
- 포인트 금액은 정책 변경이 가능하도록 관리하되 기존 지급 내역을 변경하지 않는다.
- 광고주가 캠페인·광고·소재·예산을 관리하고 매체의 광고 요청에 적절한 광고를 제공한다.
- 광고 반응과 과금을 기록하고 잔액·원장·보고 결과를 대조할 수 있게 한다. 세부 광고 선택·과금 규칙은 광고 서버 설계와 인터페이스 계약을 따른다.

### 4.4 데이터 수집·표준화·분석 기반

- 계정·채팅·게시판·댓글·콘텐츠 이용·이동·포인트의 이벤트 계약을 유지한다.
- 플랫폼 업무 DB에 필요한 기록과 Outbox를 저장하고 별도 발행자가 Kafka로 전달한다. 업무 요청의 성공을 Kafka 즉시 응답에 의존시키지 않는다.
- Kafka 원천 메시지를 MongoDB에 보존하고 계약 검증·표준화 후 성공한 메시지를 후속 Kafka 토픽으로 전달한다.
- 실패·충돌 입력은 별도 기록하고 재시도·재처리가 가능하게 한다. Spark 후속 처리 및 분석 데이터 구성은 해당 파이프라인 문서와 대조한다.
- 광고 이벤트는 광고 서버의 별도 계약을 따르며 플랫폼 이벤트와 동일한 형식이라고 가정하지 않는다.

### 4.5 운영 환경

- AWS 서비스 배치, 네트워크 접근 통제와 서비스별 설정을 관리한다.
- 업무 DB·이벤트 저장소·메시지 브로커의 역할을 구분하고 배포·관찰·백업·복구 절차를 준비한다.
- 로컬 시험, 팀 공유 환경, 운영 환경과 각 DB를 구분한다. 저장소에 코드가 있다는 사실만으로 운영 배포나 장애 대응 검증 완료를 선언하지 않는다.

## 5. 이번에 하지 않을 일

- 현금 결제·출금·환전 등 금융 서비스를 제공하지 않는다.
- 캠퍼스 포인트와 광고 포인트의 통합·전환 완료를 전제하지 않는다. README상 전환은 준비 중이며 별도 정책과 구현·검증이 필요하다.
- 자동 학습 추천·개인별 능력 평가·AI 모델 학습을 완료 범위로 간주하지 않는다.
- 외부 게임·영상 서비스의 내부 활동이나 완료 결과까지 자동 수집한다고 가정하지 않는다.
- 이벤트 수집을 이유로 사용자 답안 원문, 정답·해설, 채팅·게시글·댓글 본문을 Kafka 원천 이벤트에 추가하지 않는다.
- 다중 AZ 장애 대응, 무중단 운영, 목표 동시 접속 성능을 검증 없이 보장하지 않는다.
- 배포·DB 초기화·기록 삭제·기존 UI 재설계를 문서 작성 작업에 포함하지 않는다.

## 6. 업무 원칙과 제약

1. **기존 기록 보존**: 계정·세션·학습·포인트·광고 기록은 변경 전 영향을 확인하고 백업한다. 문제은행을 늘려도 과거 학습 기록의 문제 참조를 보존한다.
2. **중복과 재시도 구분**: 같은 제출 요청과 같은 시도를 식별한다. 재전송이 새로운 보상이나 과금으로 이어지지 않도록 한다.
3. **업무 기록과 이벤트의 일관성**: 플랫폼의 답안·보상·Outbox는 같은 DB 트랜잭션에서 관리한다. 재발행될 수 있는 이벤트는 후속 처리에서도 `event_uuid`로 중복을 처리한다. 전체 구간의 정확히 한 번 처리를 검증 없이 주장하지 않는다.
4. **서비스 경계 유지**: 플랫폼·광고 서버·데이터 파이프라인은 명시된 계약으로 연결한다. 캠퍼스 지갑과 광고 지갑의 정책을 혼용하지 않는다.
5. **개인정보 최소화**: 업무에 필요한 식별자와 활동 정보만 이벤트로 전달한다. 인증 정보·키·개인정보와 답안 원문을 공개 저장소나 진단 로그에 남기지 않는다.
6. **보존 기간 명시**: 채팅 본문은 플랫폼 문서의 30일 정책을 기준으로 하며 실제 정리 작업을 확인한다. 가입 후 1년 : soft delete, 이후 1년 지나면 hard delete입니다.
7. **화면·팀 코드 보호**: 확정된 강의실 디자인을 유지하고 다른 담당 영역은 영향 검토 없이 덮어쓰지 않는다. 문서 변경과 기능 변경을 분리한다.
8. **검증 환경 분리**: 시험은 별도 환경·DB에서 수행한다. SQLite의 잠금·행 잠금 제약을 고려하며 단순 대기 시간 증가를 동시성 해결의 근거로 삼지 않는다.
9. **운영 주장에 근거 필요**: 코드 시험, 브라우저 확인, 실제 운영 점검을 구분해 남긴다. 현재 인프라 문서의 서버 배치는 단일 AZ이므로 다중 AZ 가용성이 확보됐다고 표현하지 않는다.

| 개인정보나 접속 키 노출 | 이용자 피해·운영 접근 침해 | 공개 자료 검토, 본문 제외, 환경변수와 비밀정보 분리 | 지속 관리 |
| 단일 AZ·복구 절차 미검증 | 장애 시 서비스 중단·기록 손실 | 제약 명시, 백업과 복구 시험, 목표 복구 시간·시점 합의 | 미결정 포함 |
| 팀 공유 파일 동시 수정 | 학습·광고·이동 등 기능 회귀 | 기능별 브랜치와 PR 검토, 변경 범위에 맞는 회귀 검증 | 지속 관리 |

## 8. 완료 조건

1. 교육생·광고주·운영 담당자의 주요 이용 흐름과 역할별 권한을 확인한다.
2. Python·SQL 문제은행 2,400개의 분류별 수량, 정답·해설, 등록·재등록 결과를 검수한다.
3. 출제·3회 시도·통과·결과·복습·재개와 포인트 지급·중복 방지를 기록과 화면으로 대조한다.
4. 광고 선택·반응·예산·과금·보고를 계약과 원장으로 확인하고 캠퍼스 포인트와 구분한다.
5. 업무 기록 → Outbox → Kafka → 원천 보존 → 검증·표준화 → 후속 처리의 성공·실패·재처리 근거를 남긴다. 일부 구간의 시험을 전체 운영 완료로 확대하지 않는다.
6. 기존 계정·학습 기록과 UI, 이동·층 전환·채팅 등 팀 기능이 보존됐는지 변경 범위에 맞게 확인한다.
7. 배포 버전·설정·문제은행 버전, 백업·복구 절차와 장애 담당자를 문서화한다.
8. 실제 확인한 결과와 미확인·실패·보류 사항을 분리하고 팀 검토 후 완료 여부를 결정한다.

## 10. 이 작업이 필요한 이유와 기대 효과

### 왜 필요한가

캠퍼스 화면, 학습, 광고와 데이터 처리의 완료 기준을 하나의 업무 문서로 맞추기 위해 필요하다. 기능이 존재하는 것과 사용자가 안전하게 이용할 수 있는 것을 구분하고, 담당 영역 사이의 누락을 드러낸다.

### 사용 편의성

교육생은 같은 공간에서 학습·질문·교류를 이어가고 학습 상태를 다시 확인할 수 있다. 광고주는 등록부터 반응·포인트 사용까지 일관된 화면과 기록으로 관리할 수 있다.

### 업무상 이점

팀은 역할별 책임과 서비스 계약을 기준으로 개발·검토한다. 기록과 이벤트의 연결 근거가 있어 장애 분석과 재처리, 정합성 확인을 반복 가능한 절차로 만들 수 있다.

### 기대되는 이익

학습 참여와 교류를 이어갈 기반, 광고 운영을 설명할 수 있는 기록, 향후 이용 흐름을 분석할 수 있는 데이터 기반을 확보한다. 참여율·학습 효과·광고 성과·운영 비용 개선은 공개 후 측정할 항목이며 현재 달성한 성과로 표현하지 않는다.
