## 0. 요약

**결과(10/17, 로컬 운영 조건):**
- 소켓 프로세스 **4개**면 100명이 모두 계속 움직여도 가장 바쁜 프로세스 **46.5%**다. 키 → 움직임 상위 5% 41ms, 다른 사람 위치 간격 상위 5% 155ms.
  - 한 프로세스는 같은 조건에서 포화된다(98.4%, 71명만 접속, 키 → 움직임 상위 5% 2.8초).
- 이동 20% 기준으로 **200명·4개 45.1%, 300명·6개 43.5%**다. 모두 접속했고 끊김이 없었다.
- 프로세스 사이 기능(서로 보이기·채팅·점프·찌르기·쪽지·세션 교체·만료·로그아웃 위치·프로세스 장애)은 12가지 확인을 모두 통과했다(M4).
- **실사용 모방(1명 초당 10건, 실제 사람 약 1.5명분) 100명은 프로세스 4개를 넘친다(89%, M8).** 이동만이면 67.5% 이고, 찌르기·점프의 전달 방식과 조작마다의 DB 확인이 넘치게 한다. 위치 묶음(가까운 사람만 보내기의 대상)은 몫이 작다(§8).
- **다음 천장은 front-a 의 프론트 중계(파이썬 하나)다.** 100명 모두 이동에 운영 코어 65.6~70.2%였다.
  front-a nginx 가 WebSocket 을 game-server 로 바로 넘기면(로컬에 같은 edge 설정으로 확인) 중계는 **4.3%**(HTTP 만)로 내려가고 지연은 그대로다. 인프라에 요청한다(M6).

**배경(10/16):**

- **"8명이 한계"는 서버 CPU 기준으로는 맞지 않는다.** 5분 추적(10/16 17:53~17:58, 실사용자 3→8명) 동안 백엔드는 운영 코어 하나의 **최고 40%**였고, 느린 DB 로그나 서버가 끊은 연결도 없었다.
- **서버로 쓴 맥북의 GPU 99%는 서버가 아니라 그 맥에 열린 게임 탭(브라우저)이 쓴 것이다.** (§1.1, 10/16 21시 측정)
  - 서버(Docker 안의 Python)는 GPU 에 닿지 않는다. 맥의 GPU 사용자 목록에 컨테이너 가상머신이 없다.
  - 서버 코드에는 그리기가 없다. 서버는 위치·상태 JSON 만 보낸다.
  - 게임 탭 하나만으로 M4 Pro GPU 가 **100%**가 됐다. 다른 접속자가 0명일 때도 그렇다.
  - 화면 전체(3004×1692 화소)를 **화면 주사율대로 초당 약 120번** 처음부터 다시 그리기 때문이다. 한 번에 이미지 그리기 132번과 흐림 효과 8번이 들어간다.
- **같은 그리기를 사용자마다 자기 컴퓨터에서 한다.** 사용자들이 느낀 지연은 각자 컴퓨터의 그리기가 따라가지 못한 것일 가능성이 크다.
  - 서버가 한가했던 8명 때의 느림과도 맞는다.
  - 다만 사용자 PC 에서는 아직 재지 않았다(B0).
  - 맥 GPU 가 100%여도 서버 응답(키 → 움직임)은 같았다. 맥 GPU 가 서버를 느리게 한 것은 아니다.
- 그래서 계획은 **두 갈래**다.
  - **B: 브라우저 그리기 줄이기**(프론트만, 사용자가 느끼는 지연에 바로 닿는다)
  - **M: 백엔드 여러 프로세스 + Redis**(서버 천장 올리기)
  - 둘은 서로 기다리지 않는다. B1·B2 는 작아서 먼저 할 수 있다.
- 그래도 지금 구조의 천장은 낮다. **실사용자 한 명이 부하 시험 사용자 약 6명분**을 쓴다(사람당 운영 코어 3.1% 대 0.49%).
  그래서 한 프로세스의 한계는 **실사용 약 30명**이고, 실사용 100명이면 운영 코어 **약 3.2개분**이 필요하다.
- 운영 game-server(t3.2xlarge)의 vCPU 8개는 **물리 코어 4개 × 하이퍼스레딩**이다. 모두 바쁘면 운영 코어 약 5개분이다.
  프로세스 5개를 각각 70% 이하로 돌리면 100명은 들어가지만 **여유가 거의 없다**. "1명이 초당 10건 행동하는 시험"을 통과하려면 사람당 비용을 줄이는 다음 계획이 필요하다(§8).
- 구조: **daphne N개 + 세션 고정 nginx + Redis**(채널 계층과 공유 상태) **+ 백그라운드 작업 하나**. 프론트 중계(front-a)가 붙는 주소(`:8000`)는 그대로 둔다.
- **캠퍼스 문은 먼저 없앤다(M1).** 문은 리소스를 줄이려고 쓰지 않기로 했다. 그래서 여러 프로세스 사이에 문 상태를 나누지 않고, Redis 에도 두지 않는다.
  - 강의실 유리문 7개는 이미 지도에서 빠져 있다(10/15 #78).
  - 하지만 **창고 슬라이드문(`door-storage`) 하나는 아직 열고 닫는 기능이 살아 있다**. 로컬 브랜치, 최신 `dev`(`405b9d4`), 운영 사본(10/16) 모두 그렇다.
- **M 이 바꾸지 않는 것:** 브라우저 코드와 메시지 형식, 판정 규칙(서버 권위 이동·충돌·층 전환·세션 정책). Redis 주소가 없으면 **지금과 똑같이 한 프로세스로** 돈다. 그래서 로컬 개발·기존 시험·되돌리기는 설정만으로 된다.
  B 는 브라우저의 그리기 빈도·해상도만 바꾸고 메시지·판정은 그대로다.

## 3. 설계

### 3.1 구성

```
브라우저 ─ front-a nginx(443) ─ 프론트 중계(Python, 8004) ─ game-server :8000
                                                              │
                                              nginx :8000 (세션 쿠키로 고정 배정)
                                    ┌──────────┬──────────┼──────────┐
                                  daphne    daphne     daphne   … (127.0.0.1:9101~)
                                    └──────────┴────┬─────┴──────────┘
                                         Redis 127.0.0.1:6379  ── campus_jobs(작업 하나)
                                                    │
                                              MySQL Router(그대로)
```

### 3.2 채널 계층: `channels_redis` 의 **PubSub 계층**

- 기본 계층(`RedisChannelLayer`)은 방송 한 번마다 Redis 를 **차례로 네 번** 오간다(`channels_redis/core.py` `group_send`: 오래된 멤버 정리, 그룹 멤버 이름 전체 읽기, 큐 정리, Lua 스크립트).
  메시지에는 받는 소켓 이름 목록 전체가 실린다. 직렬화는 프로세스마다 한 번이다.
- PubSub 계층(`channels_redis.pubsub.RedisPubSubChannelLayer`)은 방송 한 번이 `PUBLISH` 한 번이다. 프로세스마다 한 번 받아 자기 소켓에 나눠 준다.
- 기본 계층은 안정판이고 소켓마다 큐 상한(`ChannelFull`)이 있다.
- PubSub 계층은 아직 **Beta**이고 큐 상한이 없다.
- 그래서 M2에서 두 계층을 **설정만 바꿔** 같은 조건으로 재고 숫자로 고른다. PubSub 을 먼저 기대하는 이유는 모두가 들어 있는 `campus.main` 방송(입장·채팅·점프)이 잦기 때문이다.
- 설정: `CAMPUS_REDIS_URL` 이 있으면 Redis 계층, 없으면 지금의 메모리 계층.

### 3.3 세션 고정 배정 (nginx `hash $cookie_campus_sessionid consistent`)

- 같은 로그인 세션은 언제나 같은 프로세스로 간다. 와이파이가 바뀌어 다시 붙는 경우가 가장 흔한데, 이때 **지금 코드(`consumers.py:184` 이동 상태·교실 상태 복사)가 그대로 동작**한다.
- HTTP 도 같은 규칙으로 보낸다(로그인 전 요청은 한 프로세스로 몰리지만 가볍다).
- 프로세스 하나가 죽으면 그 세션들은 다른 프로세스로 옮겨 다시 붙는다. 이때는 Redis 의 최신 위치(§3.5)로 이어 붙고, **교실 안 상태는 잃는다**(교실 밖 마지막 위치로 나온다). 장애 때만 생기는 일이라 받아들인다.

### 3.4 프로세스 사이에 나누는 상태: 묶음 흐름

프로세스마다 채널 계층에 "프로세스 채널" 하나를 두고 `campus.cluster` 그룹으로 서로 주고받는다(PubSub 이면 프로세스당 0.1초에 `PUBLISH` 한 번).

| 보내는 것 | 주기 | 받는 프로세스가 하는 일 |
|---|---|---|
| 입장·퇴장 | 생기는 즉시 | 사본에 넣고 빼며 자기 소켓에 `join`·`leave` 를 보낸다(구현: 채널 계층 방송 대신 이 흐름. 늦게 오는 방송 때문에 막 붙은 소켓이 welcome·join 을 모두 놓치지 않게) |
| 이번 묶음의 변경(`pending_moves`) | 0.1초(`flush_moves` 와 같이) | 자기 소켓에 보내는 **다음 `moves` 묶음에 합친다** → 받는 사람에게는 지금처럼 0.1초에 메시지 한 개. 다른 프로세스 사람의 위치는 최대 0.1초 늦다 |
| 자기 사람 전체 목록(상태·채널 이름·세션 해시) | 1초 | 다른 프로세스 사람 사본(`remote`)을 맞춘다. 새로 뜬 프로세스는 **이것을 한 번 받은 뒤에** 첫 소켓을 받는다 |
| (보내는 것이 없음) | 3초 | 3초 동안 소식이 없는 프로세스의 사람은 지우고 자기 소켓에 `leave` 를 보낸다(프로세스가 죽었을 때 유령 방지) |

- `welcome` 목록과 찌르기 대상은 "내 프로세스 사람 + `remote`"로 본다. 다른 프로세스 사람에게 찌르기를 보낼 때는 사본의 채널 이름으로 `channel_layer.send` 한다.
- 입장·퇴장·채팅·점프 같은 화면용 방송은 지금처럼 채널 계층(`broadcast`)이 맡는다. 묶음 흐름은 서버가 판단에 쓰는 사본과 `moves` 만 맡는다.
- 프로세스 사이에 맞춰야 할 바뀌는 지도 상태는 없다. 문을 없애고 나면 지도는 정적 데이터(`worlds.json`)뿐이다.
- 브라우저는 아는 사람만 `moves` 로 갱신한다(`presence.js:164`). 그래서 묶음이 `join` 보다 먼저 와도 문제없다.
- 같은 세션이 다른 프로세스에 남아 있으면(§3.3의 장애 뒤) 사본의 세션 해시로 찾아 `presence.replaced` 를 보낸다.
- Redis 연결 풀에서는 같은 프로세스의 메시지도 순서가 바뀔 수 있다. 메시지마다 번호를 달고 떠난 사람의 번호를 10초 기억해, 그보다 앞선 목록·입장이 늦게 와도 되살리지 않는다.
  이동은 아는 사람만 고친다(구현 `campus/cluster.py`).

### 3.5 Redis 에 두는 값 (키·값): 세션별 최신 위치 하나

| 키 | 값 | 쓰기 | 읽기 |
|---|---|---|---|
| `campus:pos:<세션 해시>` | 사용자·최신 위치·관측 시각(만료 시간 있음) | 묶음 흐름과 같이 0.1초마다(바뀐 사람만), 마지막 프레임 때 | 로그아웃·세션 만료·정리 작업(동기 클라이언트) |

- `session_registry` 의 함수 이름과 동작은 그대로 두고 저장 위치만 바꾼다. 이동 틱(30Hz)마다 Redis 에 쓰지 않고, 0.1초 묶음 때만 쓴다.
- 문 상태는 두지 않는다(M1에서 기능을 없앤다).
- Redis 에 두는 값은 모두 다시 만들 수 있다. 그래서 디스크에 저장하지 않는다(`save ""`, `appendonly no`). 주소는 `127.0.0.1` 에만 연다.

### 3.6 백그라운드 작업은 한 번만: `manage.py campus_jobs`

- 식단 갱신·세션 정리·outbox 전송을 이 명령 하나가 돌린다(지금의 `start_*` 함수를 그대로 부른다).
- daphne 로 띄운 소켓 프로세스는 `apps.py` 조건(`runserver`/`run-campus.py`)에 맞지 않으므로 작업을 시작하지 않는다.
- 세션 정리의 만료 알림은 Redis 계층을 거치므로, 어느 프로세스의 소켓에도 닿는다.

### 3.7 실행

- 소켓 프로세스: `daphne -b 127.0.0.1 -p 910N config.asgi:application` × N(systemd 템플릿 `playdata-backend@910N`).
- nginx: `0.0.0.0:8000` → 위 N개(세션 고정, `proxy_read_timeout 3600s`, `Upgrade` 전달, `Host`·`X-Forwarded-Proto` 는 중계가 준 그대로).
  front-a 의 `BACKEND_URL` 과 방화벽(8000)은 바꾸지 않는다.
- Redis: Ubuntu 24.04 `redis-server`(7.0). 로컬 시험도 같은 판(7.0)과 nginx 1.24 를 쓴다.
- 로컬 개발: `run-campus.py` 는 그대로다(Redis 없이 한 프로세스).

## 4. 단계

### M0. 8명에서 느렸던 원인 확인 — 일부 확인됨(§1.1)

- 확인한 것: 서버는 GPU 를 쓰지 않는다. 맥의 GPU 99%는 게임 탭의 그리기다. 맥 GPU 가 꽉 차도 서버 응답은 같았다.
- 남은 것: 사용자 PC 에서 그리기가 따라가지 못했는지 확인(B0).
- 시험 위생: 서버로 쓰는 컴퓨터에서는 게임 탭을 열지 않고 잰다. 열어야 하면 그 탭의 GPU·CPU 를 함께 적는다.

### B. 브라우저 그리기 줄이기 (프론트만, M 과 따로)

화면 규칙(무엇이 보이는가)은 바꾸지 않는다. 바뀌는 것은 "얼마나 자주, 얼마나 큰 해상도로 다시 그리는가"다.

#### B0. 사용자 PC 에서 재기 (코드 변경 없음)

- 사용자들에게 게임 화면의 개발자 도구 콘솔에 붙일 측정 한 줄을 준다. 10초 동안의 초당 프레임, 프레임 간격 상위 5%·최대, 프레임마다 JS 시간을 출력한다.
- Windows 는 작업 관리자의 GPU 열을 함께 본다.
- 함께 적을 것: 브라우저, GPU(내장/외장), 화면 해상도·배율·주사율, 그때 화면에 보인 사람 수.
- 맥 측정 도구(`ioreg` GPU 사용자별 시간)는 `loadtest/gpu_mac.py` 로 넣는다(§1.1 에 쓴 것).
- 판단: 사람이 늘 때 프레임 간격이 33ms(30fps)를 넘으면 그 PC 의 지연은 그리기 때문이다.

#### B1. 다시 그리는 횟수 묶기 [완료 — 60fps]

- `campus.js` 의 `frameDue` 가 지도 갱신(`update`)을 **평균 초당 60번**으로 묶는다.
  - 120·240Hz 는 한 프레임 건너 하나, 144Hz 는 고르지 않게 평균 60번을 그린다. 60Hz 이하는 매 프레임 그린다.
  - 프레임 시각이 1ms 흔들려도 놓치지 않는다.
- 교실 화면도 같은 갱신에서 그리므로 함께 묶인다. 갱신 안의 입력 전달·보간도 60번으로 함께 묶인다. 입력은 어차피 0.1초 간격으로 보낸다.
- **하지 않은 것:** 멈춰 있을 때 30fps 로 낮추거나 그리지 않기. "바뀐 것이 없다"를 가리기 어렵다(포털 빛·점프·찌르기·말풍선·광고). B 확인 숫자가 모자라면 한다.

#### B2. 해상도 상한 [완료 — 1920×1680]

- 캔버스는 **가로 1920·세로 1680 화소까지**다(사용자 결정 10/16).
  - 화면 비율을 유지하고, 원래 배율(`devicePixelRatio`, 최대 2)보다 키우지 않는다. 작은 화면을 키워 GPU 일을 늘리지 않는다.
  - 예: Retina 노트북 3004×1692 → **1920×1081**(화소 41%). 1920×1080·1366×768 화면은 그대로다. 4K 는 1920×1080 이 된다.
- 지도(`campus.js` `pixelScale`)와 교실(`learning/static/learning/classroom.js`, 같은 함수를 넘겨받는다)에 적용했다.
- 시험(node 83개 모두 통과, 프론트 Django 8개 통과)
  - `tests/render-limits.test.cjs`(새): 주사율 60·75·120·144·240·30Hz 에서 초당 그리기 수, 화면 크기별 캔버스 크기
  - `classroom-controller.test.cjs` 에 교실 캔버스 상한 추가

#### B1·B2 결과 (10/16 22시, 같은 맥 M4 Pro, 같은 위치, 개발 서버 로컬 전용)

| 조건 | 바꾸기 전 | 바꾼 뒤 |
|---|---|---|
| 혼자, 화면이 데워진 뒤(구 → 신 → 구 순서) | 브라우저 GPU **84%**, 118fps, 캔버스 3004×1692 | 브라우저 GPU **39~50%**, 60fps(상위 5% 17.4ms), 1920×1081 |
| 20명 계속 이동(화면 근처 18명) | 브라우저 GPU **95%**, 장치 **100%**, 100fps(재는 중 6.5초 멈춤 한 번) | 브라우저 GPU **34~45%**, 장치 42~64%, **60fps 고르게**(상위 5% 17.7ms, 최대 26.5ms) |
| 브라우저 GPU 프로세스 CPU | 39% | 26~31% |
| 서버 응답(봇 20명, 키 → 움직임 상위 5%) | 87ms | 52ms(그리기와 무관, 시험마다의 흔들림 범위) |

- 화면 그리기는 GPU 장치를 꽉 채우지 않고 60fps 를 지킨다. 같은 장면에서 GPU 일이 절반 아래로 줄었다.
- 줄어든 정도가 예상(프레임 ½ × 화소 41%)보다 작다. 일이 줄면 애플 GPU 가 클럭을 낮춰 사용률(바쁜 시간 비율)이 일의 양만큼 내려가지 않기 때문으로 본다.
  클럭을 낮출 수 없는 약한 GPU 에서는 그만큼 여유가 생긴다. 사용자 PC 확인(B0)에서 본다.

#### B3. 흐림 효과 미리 그려 두기 [완료]

- 포털 빛(`portalEnergy`·`compactPortalEnergy`)의 프레임마다 `shadowBlur` 를 없앴다. 같은 선·점을 굵고 옅게 한 번 더 그려 번짐을 흉내 낸다.
  한 번만 그려 두는 포털 바닥·게시판은 그대로 흐림을 쓴다.
- 시험(`portal-glow.test.cjs`): 한 프레임 그리기에서 `shadowBlur` 설정 0번(바꾸기 전 캠퍼스 4번).
- 측정(B1·B2 적용 뒤, 포털이 화면에 있을 때): 흐림 켬 32~34% / 끔 31~32%. B1·B2 뒤에는 흐림 몫이 작았다. 화면은 거의 같다.

#### B4. (필요할 때만) 정적 장면 묶기

- 바닥·가구는 한 번 그린 장면을 쓰고 사람과 겹치는 가구만 다시 그린다. 지금은 프레임마다 `drawImage` 132번이다.
- 깊이 정렬(사람이 가구 뒤에 가려지는 것)을 다시 짜야 해서 크다. B1~B3 로 모자랄 때만 한다.

#### B 확인

- 같은 맥(M4 Pro)에서 게임 탭 하나로 화면에 20명이 보일 때 측정한다.
  - 브라우저 GPU 40% 이하
  - 60fps 에서 프레임 간격 상위 5% ≤ 20ms
- B0 에서 가장 약했던 사용자 PC 에서 같은 조건 30fps 이상(상위 5% ≤ 33ms)
- node 시험: 묶기·상한이 입력·위치 갱신을 건너뛰지 않는지 고정한다.

### M2. Redis 채널 계층 (아직 한 프로세스) [완료 — PubSub]

|---|---|---|---|---|---|
| 메모리 | 66.9% | — | — | 100/100 | 35ms |
| **PubSub** | **67.1%** | 1.5% | 14.8 | 100/100 | 43ms |
| 기본 계층 | 68.2% | 1.9% | 106 | 1개 끊김(Redis 읽기 시간 초과 → 1011) | 36ms |

- `backend/requirements.txt` 에 `channels-redis`(4.3.0)·`redis` 를 넣는다. `CAMPUS_REDIS_URL` 이 있으면 Redis 계층, 없으면 메모리 계층을 쓴다.
- `loadtest/compose.yaml` 에 `redis:7.0` 을 추가한다. 운영 패키지 목록(`requirements-prod.txt`)에도 같은 버전을 더한다.
- 확인: 기존 시험이 모두 통과해야 한다(메모리 계층). 같은 100명 시험을 **메모리 / PubSub / 기본 Redis 계층**으로 돌려, 한 프로세스에서 Redis 를 거치는 비용을 숫자로 남긴다. 여기서 계층을 고른다.

- M5의 "100명·이동 1.0"을 **중계를 거쳐**(중계도 운영 코어 하나로 제한) 다시 잰다.
- 중계가 70%를 넘으면 둘 중 하나를 고른다.

### M8. 실사용 모방 시험 (1명 초당 10건) [완료 — 프로세스 4개로 모자람]

**행동의 정의**(`loadtest/campus_load.py --behavior real`): 사용자가 직접 한 일이 서버로 가는 것이다. 누르고 있는 키의 0.1초 갱신·ping·활동 POST 는 행동이 아니다.
모든 행동은 서버 규칙(점프 착지 0.72초, 채팅 0.8초, 계단·교실·부스는 그 자리에서)을 지켜 실제로 받아들여진다(포화 전에는 거절 0건). 길은 서버와 같은 지도·충돌 판정(`campus.motion`)으로 찾는다.

| 행동 | 몫·간격 | 하는 일 |
|---|---|---|
| 이동 키 | 슬롯의 약 80% | 가려는 곳 쪽 키 둘을 번갈아 누르고 뗀다(사람이 키를 고쳐 누르듯) |
| 점프 | 슬롯의 10%(착지 0.8초를 지킨다) | `control jump` |
| 찌르기 | 슬롯의 10% | 0.3~0.8초 누르고 뗀다(누르기·떼기가 각각 행동) |
| 채팅 | 평균 12초 | 전체 방송 |
| 패널(HTTP) | 평균 15초 | 식단·쪽지 목록·쪽지 보내기·커뮤니티·포인트·점심 룰렛 |
| 할 일 | 캠퍼스: 돌아다니기 73%·옥상 계단 12%·교실 15%. 옥상: 돌아다니기 80%·내려가기 15%·부스 5% | 계단·포탈 이동 확인, 교실 학습 자리에서 E → 한 문제 풀기 → 출구에서 E, 부스 E |
| 접속마다 | — | 첫 화면 `GET /` |

빠진 것: 광고(로컬에 광고 서버가 없다), 정적 파일(운영은 nginx), 커뮤니티 글쓰기. 실제 행동 수는 사람마다 초당 9.3~9.9건이었다.

**보정:** 한 프로세스·8명(10/16 실사용 측정과 같은 구성)에서 운영 코어 45.0%, 사람당 약 4.5%다. 실사용은 3.1%였으므로 **이 시험의 한 명은 실제 사람 약 1.5명분**이다(조금 무겁게 잡힌 기준).

**결과(100명·소켓 프로세스 4개·edge 직접 전달, 행동을 하나씩 더하며):**

| 넣은 행동 | 가장 바쁜 프로세스 | 백엔드 전체(코어) | 키 → 움직임 상위 5% | 다른 사람 위치 간격 상위 5% | Redis |
|---|---|---|---|---|---|
| 이동·계단·교실만 | **67.5%** | 2.57 | 36ms | 179ms | 2.6% |
| + 채팅·패널 | 89.4%(포화) | 3.39 | 55ms | 242ms | 2.7% |
| + 찌르기 | 92.3%(포화) | 3.57 | 130ms | 1,282ms | 27.7% |
| 전부(+ 점프) | 89.4%(포화) | 3.52 | 197ms | 1,549ms | 34.0% |

- 전부 넣으면 점프 응답이 수십 초 늦고(10초 안에 못 받은 것 3,091건) 채팅도 늦다. 끊긴 연결은 없다.
- 원인(py-spy, 포화된 프로세스 하나 30초)
  - 사람마다 30Hz 이동 계산(`motion_loop`)이 이벤트 루프의 가장 큰 몫이다(41.6%, 깨우기 비용은 따로). 사람 수²로 느는 위치 묶음(`flush_moves`)은 5.3%, Redis 받기는 5.6%다.
  - 찌르기·점프는 받는 사람마다 채널 계층 메시지 하나다(찌르기는 받는 사람마다 Redis PUBLISH). 그래서 Redis 가 2.7% → 34%로 뛴다.
  - 조작(점프 등)마다 세션을 DB 로 확인한다(`current_identity`). 소켓 DB 스레드는 프로세스에 하나라 차례로 돌고, CPU 가 포화되면 GIL 을 늦게 받는다. 그동안 그 사람의 다음 메시지가 모두 뒤에 밀린다.
  - 이동 계산을 30 → 15Hz 로 줄이면 이동만일 때 전체가 11% 줄지만 키 → 움직임이 36 → 65ms 로 는다. 쓰지 않는다(임시 설정으로 재고 되돌렸다, `results/real-b4-u100*-tick*.json`).
- **결론: "가까운 사람의 위치만 보내기" 하나로는 모자란다.** 위치 묶음은 몫이 작다. 찌르기·점프의 전달 방식과 조작마다의 DB 확인이 먼저다(§8).

**§8 1·2 적용 뒤(10/17):** 찌르기·점프·채팅을 받는 사람마다 채널 계층에 넣지 않는다(`share_effect`). 이 프로세스의 소켓에는 바로 쓰고, 다른 프로세스에는 0.1초 cluster 묶음에 한 번 싣는다.
점프는 같은 층의 `VIEW_RANGE`(1200, 기본 확대에서 2560×1440 화면 모서리) 안에만 간다. 점프는 조작마다 세션을 DB 로 보지 않는다. 브라우저는 바꾸지 않았다(메시지 모양이 같다).

## 7. 결정이 필요한 것

- **운영 Redis 위치:** game-server 에 설치하는 것으로 진행했다(배포 문서). 인프라가 관리형 Redis 를 주면 주소만 바뀐다.
- **프로세스 수:** **4개를 권장한다**(M5: 100명 모두 이동에 가장 바쁜 프로세스 46.5%). 물리 코어가 4개라 그 이상은 하이퍼스레딩 몫을 확인한 뒤 늘린다.
- **front-a 의 WebSocket 직접 전달(M6):** 인프라 요청(`deploy/campus-multiprocess/README.md` §5 에 edge 템플릿 변경안). 로컬 확인에서 중계 69% → 4%, 지연 그대로.
- **배포 시점:** 팀 절차. 백엔드·프론트를 함께 올리고 열린 탭은 새로고침한다(최적화 계획 §6.2와 같다).

## 8. 다음 계획 (M8 결과로 고친 순서)

실사용 모방 100명(M8)이 프로세스 4개를 넘친다. 측정상 몫이 큰 것부터:

1. **찌르기·점프를 위치 묶음처럼 보낸다.** 받는 사람마다 채널 계층을 거치지 않고 0.1초 묶음에 실어 이 프로세스의 소켓에 바로 쓰고, 다른 프로세스에는 cluster 흐름(M3)으로 보낸다.
   받는 사람은 같은 층의 가까운 사람만이다("가까운 사람만 보내기"를 이벤트에 먼저). Redis 34% 와 점프 지연이 이것이다.
2. **꾸밈 동작(점프·찌르기)은 조작마다 DB 를 보지 않는다.** 만료 시각 확인·10초 세션 확인·로그아웃 알림이 이미 있다. 층 이동 같은 상태 변경은 그대로 확인한다.
3. ~~다시 잰다~~ — 1·2 를 적용했다(M8 '§8 1·2 적용 뒤'). 응답·지연은 모두 기준 안으로 들어왔고, CPU 는 가장 바쁜 프로세스 91.8% 로 남았다.
4. ~~효과도 0.1초 위치 묶음에 싣기~~·~~웹소켓 `least_conn`~~ — 적용했다(M8 '§8 4 의 앞 두 가지 적용 뒤'). 가장 바쁜 프로세스 82.8%.
5. 남은 후보(이동 자체가 가장 큰 몫):
   - **누르고 있는 키의 갱신을 0.1 → 0.2초로:** 서버의 키 유효 시간은 0.35초라 그대로 움직인다. 사람마다 초당 입력이 약 18 → 13개(브라우저 수정).
   - **이동 계산을 사람마다 따로 깨우지 않고 프로세스에 하나로:** 30Hz 로 사람마다 잠들고 깨는 비용(M8 프로파일의 타이머·루프 몫)을 줄인다.
   - **프로세스 6개:** 운영 박스는 물리 4코어라 하이퍼스레딩 몫을 먼저 확인한다(운영에서 `corebench.py` 8개 동시, 허락받은 뒤).
   - 실제 사람으로 다시 재기: 보정(1.5배)은 10/16 의 8명·5분 한 번에서 나왔다.

- 합격 기준은 §5 와 같다(가장 바쁜 프로세스 70% 이하, 키 → 움직임 상위 5% ≤ 100ms, 다른 사람 위치 간격 ≤ 200ms, 끊김 없음). 여기에 행동 거절 0건과 조작 응답 상위 5% ≤ 200ms 를 더한다.
- 서버 쪽 생성기에 더해 **실제 브라우저 몇 개**를 같이 붙여 그리기 지연(프레임 간격)을 같은 시간에 잰다. 사용자가 느끼는 지연은 둘의 합이다.
