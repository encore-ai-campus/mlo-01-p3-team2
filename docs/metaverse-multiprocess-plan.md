# 메타버스 100명 계획: 백엔드 여러 프로세스 + Redis, 브라우저 그리기

> 작성: 2026-10-16. 기준: 브랜치 `feat/metaverse-load` `42fd2ae`(최적화 1~7단계 끝난 상태, [최적화 계획](metaverse-optimization-plan.md)).
> 상태: **계획**. 코드는 아직 고치지 않았다. 작업과 검증은 로컬(`loadtest/`)에서 하고, 운영 서버는 읽기만 한다.

## 0. 요약

- **"8명이 한계"는 서버 CPU 기준으로는 맞지 않는다.** 5분 추적(10/16 17:53~17:58, 실사용자 3→8명) 동안 백엔드는 운영 코어 하나의 **최고 40%**였고, 느린 DB 로그나 서버가 끊은 연결도 없었다.
- **서버로 쓴 맥북의 GPU 99%는 서버가 아니라 그 맥에 열린 게임 탭(브라우저)이 쓴 것이다.** (§1.1, 10/16 21시 측정)
  - 서버(Docker 안의 Python)는 GPU 에 닿지 않는다. 맥의 GPU 사용자 목록에 컨테이너 가상머신이 없다.
  - 서버 코드에는 그리기가 없다. 서버는 위치·상태 JSON 만 보낸다.
  - 게임 탭 하나만으로 M4 Pro GPU 가 **100%**가 됐다. 다른 접속자가 0명일 때도 그렇다.
  - 화면 전체(3004×1692 화소)를 **화면 주사율대로 초당 약 120번** 처음부터 다시 그리기 때문이다. 한 번에 이미지 그리기 132번과 흐림 효과 8번이 들어간다.
- **같은 그리기를 사용자마다 자기 컴퓨터에서 한다.** 사용자들이 느낀 지연은 각자 컴퓨터의 그리기가 따라가지 못한 것일 가능성이 크다.
  - 서버가 한가했던 8명 때의 느림과도 맞는다.
  - 다만 사용자 PC 에서는 아직 재지 않았다(B0).
  - 맥 GPU 가 100%여도 서버 응답(키 → 움직임)은 같았다. 맥 GPU 가 서버를 느리게 한 것은 아니다.
- 그래서 계획은 **두 갈래**다.
  - **B: 브라우저 그리기 줄이기**(프론트만, 사용자가 느끼는 지연에 바로 닿는다)
  - **M: 백엔드 여러 프로세스 + Redis**(서버 천장 올리기)
  - 둘은 서로 기다리지 않는다. B1·B2 는 작아서 먼저 할 수 있다.
- 그래도 지금 구조의 천장은 낮다. **실사용자 한 명이 부하 시험 사용자 약 6명분**을 쓴다(사람당 운영 코어 3.1% 대 0.49%).
  그래서 한 프로세스의 한계는 **실사용 약 30명**이고, 실사용 100명이면 운영 코어 **약 3.2개분**이 필요하다.
- 운영 game-server(t3.2xlarge)의 vCPU 8개는 **물리 코어 4개 × 하이퍼스레딩**이다. 모두 바쁘면 운영 코어 약 5개분이다.
  프로세스 5개를 각각 70% 이하로 돌리면 100명은 들어가지만 **여유가 거의 없다**. "1명이 초당 10건 행동하는 시험"을 통과하려면 사람당 비용을 줄이는 다음 계획이 필요하다(§8).
- 구조: **daphne N개 + 세션 고정 nginx + Redis**(채널 계층과 공유 상태) **+ 백그라운드 작업 하나**. 프론트 중계(front-a)가 붙는 주소(`:8000`)는 그대로 둔다.
- **캠퍼스 문은 먼저 없앤다(M1).** 문은 리소스를 줄이려고 쓰지 않기로 했다. 그래서 여러 프로세스 사이에 문 상태를 나누지 않고, Redis 에도 두지 않는다.
  - 강의실 유리문 7개는 이미 지도에서 빠져 있다(10/15 #78).
  - 하지만 **창고 슬라이드문(`door-storage`) 하나는 아직 열고 닫는 기능이 살아 있다**. 로컬 브랜치, 최신 `dev`(`405b9d4`), 운영 사본(10/16) 모두 그렇다.
- **M 이 바꾸지 않는 것:** 브라우저 코드와 메시지 형식, 판정 규칙(서버 권위 이동·충돌·층 전환·세션 정책). Redis 주소가 없으면 **지금과 똑같이 한 프로세스로** 돈다. 그래서 로컬 개발·기존 시험·되돌리기는 설정만으로 된다.
  B 는 브라우저의 그리기 빈도·해상도만 바꾸고 메시지·판정은 그대로다.

## 3. 설계

### 3.1 구성

```
브라우저 ─ front-a nginx(443) ─ 프론트 중계(Python, 8004) ─ game-server :8000
                                                              │
                                              nginx :8000 (세션 쿠키로 고정 배정)
                                    ┌──────────┬──────────┼──────────┐
                                  daphne    daphne     daphne   … (127.0.0.1:9101~)
                                    └──────────┴────┬─────┴──────────┘
                                         Redis 127.0.0.1:6379  ── campus_jobs(작업 하나)
                                                    │
                                              MySQL Router(그대로)
```

### 3.2 채널 계층: `channels_redis` 의 **PubSub 계층**

- 기본 계층(`RedisChannelLayer`)은 방송 한 번마다 Redis 를 **차례로 네 번** 오간다(`channels_redis/core.py` `group_send`: 오래된 멤버 정리, 그룹 멤버 이름 전체 읽기, 큐 정리, Lua 스크립트).
  메시지에는 받는 소켓 이름 목록 전체가 실린다. 직렬화는 프로세스마다 한 번이다.
- PubSub 계층(`channels_redis.pubsub.RedisPubSubChannelLayer`)은 방송 한 번이 `PUBLISH` 한 번이다. 프로세스마다 한 번 받아 자기 소켓에 나눠 준다.
- 기본 계층은 안정판이고 소켓마다 큐 상한(`ChannelFull`)이 있다.
- PubSub 계층은 아직 **Beta**이고 큐 상한이 없다.
- 그래서 M2에서 두 계층을 **설정만 바꿔** 같은 조건으로 재고 숫자로 고른다. PubSub 을 먼저 기대하는 이유는 모두가 들어 있는 `campus.main` 방송(입장·채팅·점프)이 잦기 때문이다.
- 설정: `CAMPUS_REDIS_URL` 이 있으면 Redis 계층, 없으면 지금의 메모리 계층.

### 3.3 세션 고정 배정 (nginx `hash $cookie_campus_sessionid consistent`)

- 같은 로그인 세션은 언제나 같은 프로세스로 간다. 와이파이가 바뀌어 다시 붙는 경우가 가장 흔한데, 이때 **지금 코드(`consumers.py:184` 이동 상태·교실 상태 복사)가 그대로 동작**한다.
- HTTP 도 같은 규칙으로 보낸다(로그인 전 요청은 한 프로세스로 몰리지만 가볍다).
- 프로세스 하나가 죽으면 그 세션들은 다른 프로세스로 옮겨 다시 붙는다. 이때는 Redis 의 최신 위치(§3.5)로 이어 붙고, **교실 안 상태는 잃는다**(교실 밖 마지막 위치로 나온다). 장애 때만 생기는 일이라 받아들인다.

### 3.4 프로세스 사이에 나누는 상태: 묶음 흐름

프로세스마다 채널 계층에 "프로세스 채널" 하나를 두고 `campus.cluster` 그룹으로 서로 주고받는다(PubSub 이면 프로세스당 0.1초에 `PUBLISH` 한 번).

| 보내는 것 | 주기 | 받는 프로세스가 하는 일 |
|---|---|---|
| 이번 묶음의 변경(`pending_moves`)·떠난 사람 | 0.1초(`flush_moves` 와 같이) | 자기 소켓에 보내는 **다음 `moves` 묶음에 합친다** → 받는 사람에게는 지금처럼 0.1초에 메시지 한 개. 다른 프로세스 사람의 위치는 최대 0.1초 늦다 |
| 자기 사람 전체 목록(상태·채널 이름·세션 해시) | 1초 | 다른 프로세스 사람 사본(`remote`)을 맞춘다. 새로 뜬 프로세스는 **이것을 한 번 받은 뒤에** 첫 소켓을 받는다 |
| (보내는 것이 없음) | 3초 | 3초 동안 소식이 없는 프로세스의 사람은 지우고 자기 소켓에 `leave` 를 보낸다(프로세스가 죽었을 때 유령 방지) |

- `welcome` 목록과 찌르기 대상은 "내 프로세스 사람 + `remote`"로 본다. 다른 프로세스 사람에게 찌르기를 보낼 때는 사본의 채널 이름으로 `channel_layer.send` 한다.
- 입장·퇴장·채팅·점프 같은 화면용 방송은 지금처럼 채널 계층(`broadcast`)이 맡는다. 묶음 흐름은 서버가 판단에 쓰는 사본과 `moves` 만 맡는다.
- 프로세스 사이에 맞춰야 할 바뀌는 지도 상태는 없다. 문을 없애고 나면 지도는 정적 데이터(`worlds.json`)뿐이다.
- 브라우저는 아는 사람만 `moves` 로 갱신한다(`presence.js:164`). 그래서 묶음이 `join` 보다 먼저 와도 문제없다.
- 같은 세션이 다른 프로세스에 남아 있으면(§3.3의 장애 뒤) 사본의 세션 해시로 찾아 `presence.replaced` 를 보낸다.

### 3.5 Redis 에 두는 값 (키·값): 세션별 최신 위치 하나

| 키 | 값 | 쓰기 | 읽기 |
|---|---|---|---|
| `campus:pos:<세션 해시>` | 사용자·최신 위치·관측 시각(만료 시간 있음) | 묶음 흐름과 같이 0.1초마다(바뀐 사람만), 마지막 프레임 때 | 로그아웃·세션 만료·정리 작업(동기 클라이언트) |

- `session_registry` 의 함수 이름과 동작은 그대로 두고 저장 위치만 바꾼다. 이동 틱(30Hz)마다 Redis 에 쓰지 않고, 0.1초 묶음 때만 쓴다.
- 문 상태는 두지 않는다(M1에서 기능을 없앤다).
- Redis 에 두는 값은 모두 다시 만들 수 있다. 그래서 디스크에 저장하지 않는다(`save ""`, `appendonly no`). 주소는 `127.0.0.1` 에만 연다.

### 3.6 백그라운드 작업은 한 번만: `manage.py campus_jobs`

- 식단 갱신·세션 정리·outbox 전송을 이 명령 하나가 돌린다(지금의 `start_*` 함수를 그대로 부른다).
- daphne 로 띄운 소켓 프로세스는 `apps.py` 조건(`runserver`/`run-campus.py`)에 맞지 않으므로 작업을 시작하지 않는다.
- 세션 정리의 만료 알림은 Redis 계층을 거치므로, 어느 프로세스의 소켓에도 닿는다.

### 3.7 실행

- 소켓 프로세스: `daphne -b 127.0.0.1 -p 910N config.asgi:application` × N(systemd 템플릿 `playdata-backend@910N`).
- nginx: `0.0.0.0:8000` → 위 N개(세션 고정, `proxy_read_timeout 3600s`, `Upgrade` 전달, `Host`·`X-Forwarded-Proto` 는 중계가 준 그대로).
  front-a 의 `BACKEND_URL` 과 방화벽(8000)은 바꾸지 않는다.
- Redis: Ubuntu 24.04 `redis-server`(7.0). 로컬 시험도 같은 판(7.0)과 nginx 1.24 를 쓴다.
- 로컬 개발: `run-campus.py` 는 그대로다(Redis 없이 한 프로세스).

## 4. 단계

### M0. 8명에서 느렸던 원인 확인 — 일부 확인됨(§1.1)

- 확인한 것: 서버는 GPU 를 쓰지 않는다. 맥의 GPU 99%는 게임 탭의 그리기다. 맥 GPU 가 꽉 차도 서버 응답은 같았다.
- 남은 것: 사용자 PC 에서 그리기가 따라가지 못했는지 확인(B0).
- 시험 위생: 서버로 쓰는 컴퓨터에서는 게임 탭을 열지 않고 잰다. 열어야 하면 그 탭의 GPU·CPU 를 함께 적는다.

### B. 브라우저 그리기 줄이기 (프론트만, M 과 따로)

화면 규칙(무엇이 보이는가)은 바꾸지 않는다. 바뀌는 것은 "얼마나 자주, 얼마나 큰 해상도로 다시 그리는가"다.

#### B0. 사용자 PC 에서 재기 (코드 변경 없음)

- 사용자들에게 게임 화면의 개발자 도구 콘솔에 붙일 측정 한 줄을 준다. 10초 동안의 초당 프레임, 프레임 간격 상위 5%·최대, 프레임마다 JS 시간을 출력한다.
- Windows 는 작업 관리자의 GPU 열을 함께 본다.
- 함께 적을 것: 브라우저, GPU(내장/외장), 화면 해상도·배율·주사율, 그때 화면에 보인 사람 수.
- 맥 측정 도구(`ioreg` GPU 사용자별 시간)는 `loadtest/gpu_mac.py` 로 넣는다(§1.1 에 쓴 것).
- 판단: 사람이 늘 때 프레임 간격이 33ms(30fps)를 넘으면 그 PC 의 지연은 그리기 때문이다.

#### B1. 다시 그리는 횟수 묶기

- 화면 그리기를 **최대 60fps** 로 묶는다. 120·144Hz 화면에서 남는 프레임은 건너뛴다.
- 나와 주변 사람이 모두 멈춰 있고 움직이는 효과(포털 빛 등)만 남으면 30fps 로 낮춘다. 바뀐 것이 없으면 그리지 않는다.
- 입력·위치 갱신은 지금처럼 매 프레임 받는다. 그리기만 건너뛴다.
- 측정(§1.1): 60fps 로 묶으면 M4 Pro 브라우저 GPU 80~90% → 38~58%.

#### B2. 해상도 상한

- `campus.js:104` 의 상한 `Math.min(devicePixelRatio, 2)` 를 낮춘다. 후보는 1.5 다(화소 약 56%). 화질 설정으로 사용자가 고르게 할 수도 있다.
- 측정(§1.1): 1배면 28~32%.
- Windows 노트북은 보통 배율 1.25~1.5 라 이미 화소가 적다. 대신 GPU 가 약하므로 B0 숫자로 상한을 정한다.

#### B3. 흐림 효과 미리 그려 두기

- 포털 빛의 `shadowBlur`(프레임마다 8번)를 미리 그린 이미지로 바꾼다. 실시간 흐림을 없애는 것이다.
- §1.1 에서 확정하지 못한 몫을 B1·B2 뒤에 다시 잰다.

#### B4. (필요할 때만) 정적 장면 묶기

- 바닥·가구는 한 번 그린 장면을 쓰고 사람과 겹치는 가구만 다시 그린다. 지금은 프레임마다 `drawImage` 132번이다.
- 깊이 정렬(사람이 가구 뒤에 가려지는 것)을 다시 짜야 해서 크다. B1~B3 로 모자랄 때만 한다.

#### B 확인

- 같은 맥(M4 Pro)에서 게임 탭 하나로 화면에 20명이 보일 때 측정한다.
  - 브라우저 GPU 40% 이하
  - 60fps 에서 프레임 간격 상위 5% ≤ 20ms
- B0 에서 가장 약했던 사용자 PC 에서 같은 조건 30fps 이상(상위 5% ≤ 33ms)
- node 시험: 묶기·상한이 입력·위치 갱신을 건너뛰지 않는지 고정한다.

### M1. 캠퍼스 문 없애기 (창고 슬라이드문 하나)

문은 쓰지 않기로 했다(리소스 감소). 지금 남은 문 기능은 창고 슬라이드문(`door-storage`) 하나다. 이것을 없애면 창고 입구는 강의실처럼 **늘 열린 통로**가 되고, 화면에서 문이 사라진다.
여러 프로세스 작업 전에 하는 이유: 프로세스 사이에 나눌 상태가 하나 줄고(Redis 키·묶음 흐름의 문 항목이 없어진다), 이동 계산의 매 충돌 검사에서 문 모양 계산이 빠진다.

| 쪽 | 없애는 것 |
|---|---|
| 백엔드 | `campus/doors.py`(파일).<br>`motion.py`: `walkable` 의 문 충돌(:58, 충돌 검사마다 문 모양을 새로 만든다), `distance` 의 문 분기(:87), 모든 함수의 `doors` 인자.<br>`poke.py` `find_target`·`clear` 의 `doors` 인자.<br>`consumers.py`: `room.doors`, `welcome` 의 `doors`, `door` 메시지와 `receive_door`, `door_state` 로 이동 틱 깨우기, `control_state` 비교 키의 문 |

  운영 front-a 에만 있는 수정 파일 중 `classroom-assets.js` 는 건드리지 않는다. `isometric.js` 는 이 브랜치가 이미 고치므로 겹침이 하나 더 늘 뿐이다(최적화 계획 §1).

  - 객체 ID 는 만든 순서(`'object-'+objects.length`)라 문을 지운 뒤 다른 객체의 ID 가 바뀌지 않아야 한다. 문은 끝 쪽에서 만들고 그 뒤 객체는 ID 를 직접 적지만, 지우기 전후 전체 ID 목록을 비교하는 시험으로 고정한다.

### M2. Redis 채널 계층 (아직 한 프로세스)

- `backend/requirements.txt` 에 `channels-redis`(4.3.0)·`redis` 를 넣는다. `CAMPUS_REDIS_URL` 이 있으면 Redis 계층, 없으면 메모리 계층을 쓴다.

- 확인: 기존 시험이 모두 통과해야 한다(메모리 계층). 같은 100명 시험을 **메모리 / PubSub / 기본 Redis 계층**으로 돌려, 한 프로세스에서 Redis 를 거치는 비용을 숫자로 남긴다. 여기서 계층을 고른다.

### M3. 프로세스 사이 상태 (§3.4·§3.5)

- 새 모듈 하나(`campus/cluster.py`)에 묶음 흐름·사본·유령 정리·최신 위치를 모은다. `consumers.py` 에서는 `connect`·`flush_moves`·`leave`·찌르기 대상을 고치는 곳만 부른다.
- Redis 가 없으면 모든 함수가 지금 동작(메모리)으로 돈다.
- 시험: 합치기·유령 정리·서버 전용 필드(채널 이름·세션 해시)가 브라우저로 나가지 않는지를 단위 시험으로 고정한다.

### M5. 부하 시험 확장과 측정

- 소켓 프로세스를 **컨테이너 하나에 하나씩**(각각 `cpu_quota 5000` = 운영 코어 하나) N개 띄우고, 앞에 nginx·Redis 를 둔다. 프로세스 하나가 운영 코어 하나보다 빨라지지 않게 하려는 것이다.
- `run.py` 가 프로세스별 CPU(가장 바쁜 프로세스가 지연을 정한다)·Redis CPU·명령 수·nginx CPU 를 함께 남긴다.
- 측정 표(각 5분):

| 사람 | 이동 비율 | 프로세스 N |
|---|---|---|
| 100 | 0.2(지금 시험과 같음) | 1·2·4 |
| 100 | **1.0**(모두 계속 움직임 — 실사용에 가까움) | 2·4·5·6 |
| 200·300 | 0.2 | 4·6 |

- 하이퍼스레딩: 프로세스가 4개를 넘으면 운영에서는 물리 코어를 나눠 쓴다. 로컬 숫자보다 느려지므로, N이 5·6일 때의 결과는 **낙관적인 값**으로 적는다.
  운영 박스에서 `corebench.py` 를 8개 동시에 30초 돌려 보면 확정할 수 있다. 운영 CPU 를 쓰는 일이라 허락받은 뒤에만 한다.

### M6. 프론트 중계 확인

- 지금은 모든 WebSocket 메시지가 front-a 의 **파이썬 프로세스 하나**(`frontend/pages/sockets.py`)를 지난다. 운영 front-a 의 8004 도 `python` 하나다.
  백엔드를 늘리면 다음 천장은 이 중계다.
- M5의 "100명·이동 1.0"을 **중계를 거쳐**(중계도 운영 코어 하나로 제한) 다시 잰다.
- 중계가 70%를 넘으면 둘 중 하나를 고른다.
  - **중계 여러 개:** front-a nginx 의 `upstream edge_frontends`(이미 `least_conn`)에 서버를 더 둔다. 코드 변경이 없다.
  - **WebSocket 만 nginx 가 바로 넘기기:** 중계를 거치지 않는다.

  front-a nginx 는 인프라가 관리하므로 요청 사항으로 정리한다.

### M7. 배포 문서와 인프라 요청

- 순서: Redis·nginx 설치 → 새 코드(Redis 주소 없이 올려 지금과 같은지 먼저 확인) → 소켓 프로세스·작업 서비스·nginx 켜기 → 예전 `playdata-backend` 끄기.
  8000 포트를 넘겨받는 순간 모두 한 번 다시 연결된다(재연결 간격은 흩어 놓았다, 6d).
- 되돌리기: 새 서비스와 nginx 사이트를 끄고 예전 `playdata-backend` 를 켠다. Redis 주소가 없으면 코드는 지금과 같게 돈다.
- 인프라 확인
  - t3 의 **CPU 크레딧 방식**(`unlimited`/`standard`): 기준 성능은 vCPU 당 40%(8개 합쳐 3.2개분)이다. `standard` 면 크레딧이 떨어진 뒤 그 아래로 묶인다. 실사용 100명(약 3.2개분 이상)은 그 경계에 있다.
  - front-a 쪽 변경(M6)의 담당.

## 5. 완료 기준

- 이동 비율 1.0, 100명, 운영 조건에서 모두 접속을 유지한다.
- 가장 바쁜 프로세스가 운영 코어의 70% 이하다.
- 키 → 움직임 상위 5% ≤ 100ms, 다른 사람 위치 간격 상위 5% ≤ 200ms, 생성기 지연이 작다.
- 두 프로세스 확인(M4)을 모두 통과한다.
- 문 기능이 남아 있지 않다(백엔드·프론트·지도 데이터). 창고 입구가 늘 지나갈 수 있다(M1).
- 브라우저 그리기가 "B 확인"을 통과한다.
- 기존 시험(백엔드·프론트 Django·node)이 그대로 통과한다. Redis 가 없을 때의 동작은 지금과 같다(시험이 그대로 고정한다).
- 결과 표를 이 문서 §1 아래에 남긴다.

| PubSub 계층이 Beta, Redis 연결이 끊기면 그동안의 메시지를 잃는다 | 위치·목록은 1초 전체 목록으로 되살아난다. 세션 만료는 소켓의 10초 확인이 다시 잡는다. 쪽지 알림 하나는 놓칠 수 있다. M2에서 기본 계층과 비교한다 |
| PubSub 큐에 상한이 없다(밀린 소켓의 메모리) | M5에서 프로세스 메모리를 함께 잰다. 늘면 소켓별 상한을 둔다 |
| Redis 가 멈추면 전체가 멈춘다 | 같은 박스, `Restart=always`. 지금도 프로세스 하나가 단일 장애점이다 |
| 세션 고정의 쏠림(어떤 프로세스에 사람이 몰림) | 프로세스별 접속 수·CPU 를 M5에서 본다. 100명/4개면 대체로 25±5명이다 |
| 다른 프로세스 사람의 위치가 최대 0.1초 늦다 | 받는 간격(0.1초)은 그대로다. M5의 "다른 사람 위치 간격"으로 확인한다 |
| 하이퍼스레딩·t3 크레딧 | §4 M5·M7 |
| 프론트 중계가 다음 천장 | §4 M6 |
| 부하 생성기는 서버만 잰다(그리기 비용이 안 보인다) | B0·B 확인은 실제 브라우저로 잰다. 서버를 띄운 컴퓨터에서는 게임 탭을 열지 않는다(M0) |
| B1·B2 로 화면이 덜 부드럽거나 덜 선명해 보인다 | 60fps·해상도 1.5 는 대부분의 화면에서 차이가 작다. 화질 설정을 두면 사용자가 고른다 |

## 7. 결정이 필요한 것

- **운영 Redis 위치:** game-server 에 설치하는 것을 기본으로 계획했다. 인프라가 관리형 Redis 를 주면 주소만 바뀐다.
- **프로세스 수:** M5 숫자로 정한다(예상 4~5).
- **front-a 변경 담당:** M6에서 필요할 때.
