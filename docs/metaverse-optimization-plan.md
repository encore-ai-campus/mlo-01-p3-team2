## 0. 요약

- 서버 전체(8코어)는 한가하지만, 게임 백엔드는 **프로세스 하나**(`runserver`/daphne, 메모리 채널 계층)라서 **한 코어가 천장**입니다.
- 부하의 대부분은 **가만히 있는 사람**이 만듭니다. 위치가 그대로여도 계산·전송이 반복되고, 메시지마다 고정 비용이 붙어 사람 수에 대해 제곱보다 빠르게 늘어납니다.
- 그래서 순서는 다음과 같습니다. **측정 도구 → 불필요한 전송 제거 → 메시지당 고정 비용 제거 → 이동과 DB 저장 분리 → DB 호출 줄이기 → 화면 갱신 → 재로그인 원인 구분 → 운영 설정.**
- 판정 규칙(서버 권위 이동·충돌·층 전환·세션 정책)은 바꾸지 않습니다. 바뀌는 것은 "언제·얼마나 자주 보내고 저장하는가"입니다.

## 2. 문제점

### 2.1 움직이지 않을 때도 상태를 계속 보냄

서버는 사용자마다 초당 최대 30번 이동 상태를 계산하고 본인에게 보냅니다(`motion_loop`, consumers.py:306·318). 다른 사람에게도 약 0.1초 간격으로 위치를 전달하는데, **이전과 위치가 같아도 보냅니다**(consumers.py:268, 서버 판정 프레임은 0.1초가 지나면 무조건 방송).

8명이 가만히 있어도 각 사용자의 상태가 나머지 7명에게 반복 전달됩니다. 방송 전달 수는 초당 10×N²입니다.

브라우저도 키를 누르지 않을 때조차 0.1초마다 빈 `input`을 보냅니다(presence.js:259 `tick → publish(t)`, 100ms 제한만 있음). 서버의 키 유효 시간은 0.35초(motion.py:243)이고, 연결 생존은 5초마다 오는 `ping`이 맡습니다. 그래서 빈 입력을 반복할 이유가 없습니다.

### 2.2 메시지마다 붙는 고정 비용

Channels 4.3.2의 `dispatch`는 모든 핸들러 앞에서 `aclose_old_connections()`를 부릅니다. 이 호출은 `sync_to_async(thread_sensitive=True)`라서, 모든 소켓의 DB 작업이 함께 쓰는 **스레드 하나**를 왕복합니다. DB를 쓰지 않는 다른 사람의 `move` 수신도 마찬가지입니다.

`InMemoryChannelLayer`는 `send`·`group_send`·`receive`마다 `_clean_expired()`를 호출합니다. 이 함수는 **모든 채널과 모든 그룹 구성원을 훑습니다.**

메시지 수가 N²이고 메시지마다 N을 훑으므로 실제 비용은 N³에 가깝습니다.

### 2.3 이동 처리가 DB 저장을 기다림

위치가 바뀌면 약 5초 간격으로 DB에 저장하고, 층 이동·접속 종료 때도 저장합니다. 문제는 **이동 처리 흐름 안에서 저장이 끝날 때까지 기다린다**는 점입니다.

> 이동 계산 → 위치 전달 → DB 저장 완료 대기 → 다음 이동 계산

`motion_loop`는 `control_lock`을 쥔 채(consumers.py:310) `receive_movement` → `checkpoint`(consumers.py:291) → `store_position`을 기다립니다. 같은 잠금을 쓰는 키 입력 처리(consumers.py:209)도 함께 기다립니다.

게다가 모든 소켓의 DB 호출은 2.2의 **스레드 하나에 줄을 섭니다.** 그래서 다른 사람의 느린 호출이나 DB 장애 순간(오늘 3100·2013·1290)이 이 사용자의 이동까지 늦춥니다.

이것이 실제 끊김의 원인인지는 운영 환경에서 시간을 재야 확정할 수 있습니다(§4 0단계).

### 2.4 DB 호출이 많고, 호출마다 새 연결

- `CONN_MAX_AGE`를 정하지 않아(기본 0) `database_sync_to_async` 호출마다 라우터를 거쳐 MySQL에 새로 접속합니다.
- 5초마다 세션을 재확인합니다(consumers.py:706-709, `min(10, 5)`). `current_identity()` 한 번에 Session·ActiveLogin·Session(다시)·User·Profile 질의가 나갑니다. 바로 뒤 `checkpoint()`가 `session_user()`로 같은 확인을 한 번 더 합니다(consumers.py:726 → 680).
- `ping`(5초)마다 `touch_platform_session` UPDATE를 보냅니다(consumers.py:235). 실제로 바뀌는 것은 15초에 한 번뿐입니다.
- ~~추첨 스케줄러가 1초마다 새 연결로 조회합니다~~ — 추첨 기능을 없앴다(2026-10-16, 아래 4c·4d 도 함께 없어졌다).
- ~~추첨이 바뀔 때마다(설문 시작·제출 확인 등) **모든 소켓이 개인 스냅샷을 DB에서 다시 만듭니다**~~(추첨 기능 제거)(raffle/live.py:16 → consumers.py:620). 참가자 N명이면 스냅샷을 약 2N²번 만듭니다. 브라우저도 15초마다 `/api/raffle/`을 따로 조회합니다(raffle.js).
- HTTP 요청 하나에 `check_session`이 2~3번 돕니다: 미들웨어 앞, 화면 데이터의 `session_context`, 미들웨어 뒤 touch.
- **새 연결마다 TLS 핸드셰이크**: mysqlclient 기본(`ssl_mode=PREFERRED`)과 운영 라우터(`client_ssl_mode=PREFERRED`)가 앱→라우터 구간도 TLS 로 연결한다.
  부하 시험에서 연결 하나에 운영 코어 약 23ms 였고, 이것이 백엔드 CPU 의 가장 큰 몫이었다(§1.1).
- 브라우저는 소켓이 붙어 있어도 15초마다 HTTP 조회 셋(세션 상태·추첨·쪽지)을 보낸다. 셋 다 소켓이 이미 알려 주는 것이다(welcome·`raffle_state`·`private_message`·`session_expired`). 요청마다 새 DB 연결(TLS)이다.

### 2.5 같은 아바타 정보를 받아도 화면을 다시 갱신함

브라우저는 본인 상태(`control_state`, 초당 30번)를 받을 때마다 `acceptSelf → applyIdentity`로 아바타 정보를 적용하고 `campus:avatar` 이벤트를 발생시킵니다(presence.js:94-97·206-212). 이 이벤트를 받은 화면은 아바타 미리보기 이미지 주소와 이름을 다시 설정합니다(campus.js:346-348).

캐릭터 모양이나 이름이 바뀌지 않았는데도 같은 작업을 반복합니다. 이미지를 매번 새로 내려받는 것은 아니지만, 불필요한 화면 처리가 생깁니다.

### 2.6 연결이 잠깐 끊긴 것과 로그인 만료를 구분하지 못함

연결 상태는 두 가지입니다.
- **로그인 세션:** 이 사용자가 로그인한 상태인지.
- **실시간 연결(WebSocket):** 위치·채팅 등을 주고받는 통로.

와이파이가 바뀌거나 서버 응답이 늦어지면 실시간 연결은 끊길 수 있지만, 로그인까지 만료된 것은 아닙니다.

브라우저는 종료 코드 `4401`을 받으면 확인 없이 곧바로 로그인 화면으로 갑니다(presence.js:194-198). 서버가 `4401`로 닫는 곳은 여러 군데입니다(consumers.py:75·83·131·771, `session.expired` 알림 포함).
- 미인증
- 정책 만료(최대 8시간·비활동 30분)
- 다른 곳의 새 로그인(`replaced`)
- 세션 행 없음
- 다른 사용자

**서버는 지금 닫는 이유를 기록하지 않아서**, 재로그인의 원인은 아직 확정하지 못했습니다.

재연결 간격은 1→2→4→8→10초입니다(presence.js:201). 사용자마다 다르게 흩뜨리지 않아서, 여러 사람이 동시에 끊기면 같은 순간에 다시 몰립니다.

**이미 되어 있는 것**(시험으로 고정만 합니다):
- 같은 세션의 재접속은 새 캐릭터를 추가하지 않고 기존 캐릭터의 연결을 교체하며, 위치를 이어받습니다(consumers.py:133-164).
- 끊길 때 누르고 있던 키를 브라우저(presence.js:92)와 서버(consumers.py:144) 모두 초기화합니다.

### 2.7 결함 (부하 때 드러남)

- **세션 감시 작업이 조용히 죽음:** consumers.py:709에서 자기 자신에게 보내는 `presence.check`가 `ChannelFull`로 실패하면 예외를 잡지 않아 감시 작업이 끝납니다. 그 소켓은 세션 재확인과 60초 유휴 종료가 멈춥니다. 오늘 로그에 7건 있었습니다.
- **과부하 때 유령 캐릭터:** 소켓 처리가 60초 넘게 밀리면 `InMemoryChannelLayer`가 그 채널을 모든 그룹에서 말없이 뺍니다. 그 사용자는 다른 사람의 움직임·채팅을 받지 못합니다.

### 2.8 운영 설정 (코드 밖)

- **광고 반응 재전송:** `deploy/ad71`의 타이머가 5초마다 `--once`로 새 프로세스를 띄웁니다. 명령에는 상주 모드(`--poll-interval`)가 이미 있습니다.
- **Kafka 연결 실패:** 서버가 10/16 02:43(UTC)에 새로 떴고(주소 10.10.10.166) 그 뒤 Kafka에 연결하지 못합니다. outbox가 쌓이고, 전송기는 맨 앞 한 건을 120초씩 붙잡습니다. 방화벽이 옛 주소만 허용하는지 확인이 필요합니다.
- **MySQL 연결 비용:** 운영 라우터는 이미 서버 쪽 연결을 재사용한다(`max_idle_server_connections=64`). 비싼 것은 앱→라우터의 새 연결(TLS)이다.
  - `CONN_MAX_AGE` 전체 적용은 쓸 수 없다: ASGI 에서 소켓마다 연결을 하나씩 붙잡아 100명에서 동시 연결 152개(MySQL 상한 151)를 넘었다(실험).
  - 앱→라우터(127.0.0.1) 구간만 TLS 를 끄는 안은 **하지 않는다**: 운영 라우터는 `server_ssl_mode=PREFERRED` 라 DB 서버 구간은 계속 암호화되지만,
    TLS 없이 붙으면 `caching_sha2_password` 가 인증 캐시가 빈 직후(재시작 등) 접속을 거절한다(로컬 재현: 2061). mysqlclient 2.3.0 에는 공개 키를 받는 옵션도 없다.
  - 그래서 연결 **수**를 줄인다: 소켓의 DB 호출은 연결 하나를 이어 쓰고(4f), 소켓이 붙어 있으면 HTTP 조회를 하지 않는다(4g).

## 3. 원칙

1. **판정은 그대로 둡니다.** 서버 권위 이동·충돌·층 전환·교실·세션 정책·이벤트 계약(Kafka 토픽·필드)은 바꾸지 않습니다.
2. **측정 먼저, 단계마다 다시 측정합니다.** 같은 재현 스크립트로 전후 숫자를 남깁니다.
3. **단계마다 시험을 먼저 씁니다.** 새 동작("정지하면 방송 0건" 등)을 시험으로 고정한 뒤 고칩니다. 기존 시험은 모두 통과해야 합니다.
4. **옛 화면과 호환됩니다.** 브라우저 캐시에 옛 JS가 남아 있어도 깨지지 않게, 서버만 바꾸는 단계와 브라우저만 바꾸는 단계를 나눕니다. 메시지 형식을 바꾸는 것(1d)은 따로 판단합니다.
5. **작게 커밋합니다.** 단계 하나 = 커밋 하나. 작업 브랜치는 `dev`에서 만듭니다.

### 1단계. 불필요한 전송 줄이기 (2.1)

- **1a 서버 `move` 방송 [완료]:** 바뀐 것이 있을 때만 보냅니다(위치·방향·`moving`·층·교실 여부). 이동 중에는 지금처럼 0.1초 간격을 유지하고, 이동 시작·정지·방향 전환·층 이동은 바로 보냅니다(consumers.py:262-290).
  - **마지막 정지 위치(`moving=false`)는 반드시 보냅니다.** 지금의 `changed` 계산은 `moving`을 보지 않으므로 조건에 넣습니다.
  - 호환: 브라우저는 업데이트가 끊긴 상대를 지우지 않고 300ms 뒤 `moving=false`로만 바꿉니다(presence.js:265). 새 접속자는 `welcome`에서 전체 목록을 받습니다.
- **1b 본인 상태(`control_state`) [완료]:** 직전에 보낸 것과 같으면 보내지 않습니다(consumers.py:318).
  - `hints()`(motion.py:223)는 위치가 바뀌었을 때만 다시 계산합니다.
  - 교실의 `exitCooldownMs`는 0이 될 때까지 바뀌므로 그동안은 보냅니다.
  - 호환: 브라우저의 연결 끊김 판단(10초)은 5초마다 오는 `pong`이 유지합니다.
- **1c 브라우저 빈 입력 [완료]:** 키·찌르기가 없으면 보내지 않습니다. 누르고 있는 동안에는 지금처럼 0.1초마다 보냅니다(presence.js:64-67·259). 서버의 키 유효 시간은 0.35초이고, 간격을 늘리면 서버가 밀릴 때 캐릭터가 끊겨 걸을 수 있어 그대로 둡니다.
- **1d 여러 사람의 이동 묶기 [완료]:** 0.1초마다 바뀐 사람들의 위치를 한 메시지(`moves`)로 보낸다. 직렬화는 한 번이고 채널 계층을 거치지 않고 소켓에 바로 쓴다.
  - 정지·방향 전환도 다음 묶음(최대 0.1초 뒤)에 간다. 브라우저는 300ms 동안 소식이 없으면 걷기를 멈추므로 보이는 차이는 없다.
  - 브라우저는 **이미 아는 사람만** 갱신한다: 떠난 뒤 늦게 도착한 묶음이 그 사람을 되살리지 않는다(새 사람은 `join`).
  - 서버만 판정하는 이동(운영)만 묶는다. 시험용 옛 좌표 이동은 지금처럼 `move` 다.
  - **배포:** 스크립트 주소에 내용 버전(`?v=`)이 붙어 새로고침하면 새 JS 를 받는다. 배포 중 열려 있던 탭은 재연결해도 옛 JS 라 다른 사람이 멈춰 보인다 — 새로고침 안내가 필요하다.
- **1e 쉬는 사람의 이동 틱 [완료]:** 마지막 틱에 바뀐 것이 없고 키·경로·찌르기·교실 출입 대기가 없으면 30Hz 틱을 돌리지 않고 0.5초에 한 번만 살핀다.
  입력·명령·문 변경은 바로 깨운다(입력을 반영한 **뒤**에 깨워서 틱 처리 중에 온 입력도 놓치지 않는다).

확인:
- 정지 N명을 1초 두면 `move` 0건, `control_state` 0건.
- 이동 → 정지 때 `moving=false` 한 건이 전달됨.
- 키를 누르는 동안 끊김 없이 이동함(유효 시간 시험).
- 기존 이동·문·찌르기·교실 시험 통과.
- 0b 숫자 비교.

### 3단계. 이동과 DB 저장 분리 (2.3) [완료]

> 이동 처리는 계속 진행하고, 별도 저장 작업이 최신 위치를 가져가 주기적으로 저장합니다.

- 이동 루프는 "저장할 최신 위치"(dirty 표시와 관측 시각)만 갱신하고 기다리지 않습니다.
- 소켓마다 저장 작업 하나가 5초마다 최신 위치 **하나만** 저장합니다. 모든 좌표를 줄 세우지 않습니다. 저장 중 새 위치가 들어오면 다음 저장에 반영합니다.
- **층 이동**은 지금처럼 즉시 저장하고 층 이동 이벤트(`record_floor_transfer`)의 순서를 지킵니다. 저장 작업에 "지금 저장"을 요청하되 이동 루프는 기다리지 않습니다.
- **로그아웃·종료(`leave`)**는 마지막 위치 저장이 끝날 때까지 기다립니다. 최종 위치가 빠지지 않게 하기 위함입니다.
- **저장 실패**는 dirty를 유지해 다음 주기에 다시 시도하고, 실패를 로그로 남깁니다.
- 세션 만료 때 `expire_record`가 `session_registry.latest`로 마지막 위치를 저장하는 흐름은 그대로 둡니다.

확인:
- DB 저장이 1초 걸리게 지연을 주입해도 이동 틱 간격과 키 입력 응답이 유지됨.
- 층 이동·종료 때 최종 위치가 저장됨.
- 저장 실패 뒤 다음 주기에 저장됨.
- `movement_observed` 이벤트 수가 바뀌지 않음(같은 입력 → 같은 이벤트).

### 4단계. DB 호출 줄이기 (2.4)

- **4a [완료]** 세션 재확인 주기를 5초에서 10초(`session_check_interval`)로 바꿉니다. 5초였던 이유(위치 저장 겸용)는 3단계에서 사라집니다. `presence_check` 안의 중복 확인(`current_identity` 뒤 `session_user` 재실행)도 없앱니다.
- **4b [완료]** `ping` 때 `touch_platform_session`은 소켓이 기억한 마지막 시각 기준으로 15초에 한 번만 호출합니다. DB가 실제로 고치는 주기와 같으므로 결과는 같습니다.
- **4c [완료 → 추첨 기능 제거로 함께 없어짐]** 추첨 변경 알림을 묶습니다: 첫 변경은 바로, 1초 안의 나머지는 끝에 한 번(최신 상태로). 스냅샷 생성이 "변경 수 × N"에서 "묶음 수 × N"으로 줄어듭니다.
- **4d [완료 → 추첨 기능 제거로 함께 없어짐]** 추첨 스케줄러는 지금처럼 1초마다 살피되(추첨 시각 정확도) DB 연결을 이어 쓴다. 비쌌던 것은 조회가 아니라 매번의 새 연결(TLS)이었다.
- **4e [완료]** HTTP 요청 하나 안에서는 미들웨어가 구한 `request.campus_session_status`를 다시 씁니다(`session_context`·세션 상태 응답).
- **4f 소켓 DB 연결 재사용 [완료]:** 소켓의 DB 호출(`database_sync_to_async` 12곳)을 `campus/socket_db.py` 로 옮겼다. 원래도 스레드 하나에서 차례로 돌았으므로 순서는 그대로이고,
  그 스레드의 연결만 이어 쓴다(`CONN_MAX_AGE` 60·건강 검사, 발행기와 같은 방식). HTTP 요청의 연결 정책은 그대로다. 20명: 운영 코어 70%→48%, 동시 연결 최대 7.
- **4g 소켓이 붙어 있으면 HTTP 조회를 하지 않는다 [완료, 브라우저]:** 쪽지 상태(`messages.js`, 쪽지함을 열면 그대로)·세션 상태(`session-policy.js`)의 15초 조회(추첨 `raffle.js` 는 기능 제거로 없어짐)는
  소켓이 끊겨 있을 때(다른 화면 포함)만 한다. 세션 경고는 띄우기 전에 그 마감을 한 번 확인한다(다른 탭의 활동이 늘렸을 수 있다). 활동 POST 는 그대로다.
  100명: 접속 18/100 → 100/100.

확인:
- 0b 기준으로 사용자당 초당 DB 호출 수가 줄어듦.
- 세션 만료·교체·로그아웃 시험 통과.

### 6단계. 재로그인 원인 구분과 재연결 (2.6)

- **6a 원인 수집:** 0c 로그로 운영에서 `4401`이 언제·어떤 이유로 나가는지 모읍니다. 결과에 따라 6b~6c의 범위를 정합니다.
- **6b 서버 [완료, 주기적 세션 확인]:** 일시적인 DB 오류(연결 끊김·읽기 전용·복제 오류)를 로그인 만료로 다루지 않습니다. 세션 확인 중 `DatabaseError`면 `4401`을 보내지 않고 연결을 유지해 다음 확인에서 다시 봅니다. 연결 수립 중이면 재시도용 코드로 닫습니다. 먼저 지금 DB 오류가 어떤 종료 코드로 끝나는지 시험으로 고정합니다.
- **6c 브라우저 [완료]:** `4401`을 받으면 바로 로그인 화면으로 가지 않고 세션 상태(`/accounts/session/`)를 한 번 확인합니다. 유효하면 다시 연결하고, 만료면 로그인 화면으로 갑니다.
- **6d 재시도 간격 [완료]:** 지금의 2배 증가(최대 10초)에 사용자마다 다른 흔들림(예: 0.5~1.5배)을 더해 동시 재접속이 한순간에 몰리지 않게 합니다.
- **시험으로 고정만:** 재연결 때 기존 캐릭터 교체와 위치 이어받기, 끊길 때 키 초기화. 이미 되어 있습니다.

확인:
- 세션 행이 있는 상태에서 `4401`을 받으면 재연결함.
- 세션이 만료됐으면 로그인 화면으로 감.
- DB 오류 주입 때 `4401`이 나가지 않음.
- 재시도 간격이 범위 안에서 흩어짐.

### 7단계. 운영 설정 (서버·인프라, 코드 밖)

배포 담당과 인프라에 요청할 항목입니다. 우리 쪽에서 운영 서버를 직접 바꾸지 않습니다.

- **7a [완료, 저장소 파일]** `deploy/ad71`: 타이머를 끄고 `dispatch_ad_reactions`를 `--once` 없이 상주 서비스(`--poll-interval 5`, `Restart=on-failure`)로 돌립니다. 하루 종일 한 코어의 약 17%가 사라집니다. 저장소의 `deploy/ad71` 파일은 이 계획에서 고칩니다.
- **7b** Kafka: 새 주소(10.10.10.166)에서 브로커 9092로 가는 길을 엽니다. 열린 뒤 쌓인 outbox가 한 건씩 빠지는 속도를 확인합니다.
- **7c** ~~MySQL Router 연결 풀~~: 운영 라우터에 이미 있다(`max_idle_server_connections=64`). 앱 쪽 연결 수는 4f·4g 로 줄였다.
- **7d** ~~`CAMPUS_RAFFLE_POLL_SECONDS=5`~~: 필요 없다(4d).

- **여러 프로세스로 늘리기:** 실사용 측정(사람당 운영 코어 약 3.1%)으로 필요해졌다. 별도 계획: [metaverse-multiprocess-plan.md](metaverse-multiprocess-plan.md).
- **동작을 그대로 두고 코드 줄이기(Ponytail 점검 목록):**
  - 항상 503인 `ad_bridge` `decision/` 뷰
  - 쓰이지 않는 카탈로그 상수·함수
  - 시험 전용 옛 좌표 이동 경로
  - 학습 모델 `save()`의 반복 제약 검사
  - 복붙된 검증기·JSON 파서
  - `ad-bridge/scripts`와 `backend/ad_bridge`의 중복(시험이 `backend/ad_bridge`를 보게 바꾼 뒤)

  부하 작업이 끝난 뒤 별도 단계로 합니다.

## 5. 완료 기준

- 정지한 사용자는 메시지를 만들지 않습니다(방송·본인 상태·빈 입력 0건).
- DB를 쓰지 않는 메시지는 DB 스레드를 거치지 않습니다.
- DB 저장이 느려도 이동 틱이 밀리지 않습니다.
- 같은 0b 조건(예: 20명 중 5명 이동)에서 초당 메시지 수와 CPU 시간이 기준선보다 줄어든 것을 숫자로 남깁니다. 목표치는 0단계 뒤 정합니다. 계산상 메시지 수는 약 4분의 1입니다.
- 기존 백엔드·프론트 시험이 모두 통과하고, 단계마다 추가한 시험이 그 단계의 동작을 고정합니다.
- 재로그인 원인이 로그로 구분되고, 일시적 장애로는 로그인 화면으로 가지 않습니다.

## 6. 배포할 때 (팀 절차)

순서가 중요하다. **추첨 테이블은 새 코드를 올리기 전에, 지금 운영 코드로 지운다** — 새 코드에는 추첨 마이그레이션이 없어서 올린 뒤에는 `migrate raffle zero` 를 쓸 수 없다.

### 6.1 추첨 데이터 지우기 (지금 운영 코드로, 새 코드를 올리기 전)

추첨 기능은 쓰지 않기로 했다(2026-10-16). 운영 DB 의 `raffle_*` 테이블 6개(event·entry·control·surveyattempt·surveyconnection·winnercontact)에는
Google 설문 연결 주소·접근 키, 참가자 닉네임, 당첨자 QR 이미지가 있다. 쓰지 않는 개인 정보·비밀 값이므로 백업한 뒤 지운다.

```bash
cd ~/backend
# 1) 백엔드를 멈춘다. 지금 코드는 추첨 테이블을 1초마다·접속할 때마다 읽으므로, 켜 둔 채 지우면 오류가 난다
sudo systemctl stop playdata-backend
# 2) 백업(서버에 mysqldump 가 없어도 되도록 Django 로). 비밀 값·개인 정보가 들어 있으니 본인만 읽게 만든다
umask 077 && .venv/bin/python manage.py dumpdata raffle --indent 1 -o ~/raffle-backup-$(date +%Y%m%d).json
# 3) 지운다(테이블 6개와 마이그레이션 기록). 계정·다른 앱의 데이터는 그대로다
.venv/bin/python manage.py migrate raffle zero --noinput
# 4) 확인: 모두 [ ] 여야 한다
.venv/bin/python manage.py showmigrations raffle
```

- 로컬 리허설(MySQL 8.4, 서로 참조하는 추첨 행을 넣은 상태): 테이블 6개·마이그레이션 기록이 지워지고 계정은 남았다. 새 코드는 `No migrations to apply`.
- **되돌려야 할 때**(새 코드 배포를 되돌리는 경우): 옛 코드로 `manage.py migrate raffle` 로 빈 테이블을 만들고 `manage.py loaddata ~/raffle-backup-YYYYMMDD.json`.
  리허설에서 6행과 QR 이미지(바이트)까지 그대로 돌아왔다.
- 백업 파일은 보관 기간을 정해 지운다(접근 키·개인 정보). `.env` 의 `CAMPUS_RAFFLE_*` 줄도 지운다(새 코드는 읽지 않는다).

### 6.2 새 코드 올리기

1. **백엔드와 프론트를 함께** 올린다. 이동 묶음(`moves`, 1d)은 새 JS 만 읽는다. 스크립트 주소의 내용 버전(`?v=`)이 바뀌므로 새로고침하면 새 JS 를 받지만,
   배포 중 열려 있던 탭은 재연결해도 옛 JS 라 다른 사람이 멈춰 보인다 — **열린 탭 새로고침 안내**가 필요하다.
2. `migrate --noinput` 은 할 일이 없다(새 마이그레이션 없음). 서비스를 켠다(`sudo systemctl start playdata-backend`).
3. 광고 반응 재전송: `deploy/ad71/README.md` 대로 예전 타이머를 끄고 서비스를 켠다(7a).

### 6.3 배포 뒤

1. `journalctl -u playdata-backend` 에서 `closed by server code=` 줄을 모아 재로그인 원인을 본다(0c → 6a). `waited ...s for the database` 는 DB 가 느렸던 순간이다(0d).
2. Kafka(7b)는 인프라가 새 주소의 방화벽을 연 뒤 outbox 가 빠지는지 본다.
