## 1. 제품 정의

교육생이 계정과 아바타로 가상 캠퍼스에 접속해 학습·질문·정보 공유·휴식 콘텐츠를 이용하고 학습 결과와 포인트 내역을 확인할 수 있는 서비스를 제공한다. 교육생은 광고주 역할도 맡아 캠페인·광고·소재·예산과 광고 반응·포인트 사용 결과를 관리할 수 있다. 관리자는 게시판의 수정·삭제와 광고주·광고 운영에 대한 관리 권한을 가진다.

플랫폼 활동과 광고 기록은 서비스별 계약에 따라 보존한다. 플랫폼 이벤트는 업무 기록과 연결해 수집·검증·표준화하고, 운영자는 실패 원천과 재처리 대상을 추적할 수 있어야 한다. 제품 범위는 사용자 화면, 업무 처리, 데이터 파이프라인, 운영 절차와 검증 증적을 포함한다.

### 1.1 이번 버전의 범위

팀원 5명이 캠퍼스·커뮤니티, 학습, 광고, 파이프라인, 인프라를 각각 담당한다. 이 문서의 기능 범위와 인수 기준도 같은 5개 영역으로 정리한다. 학습 보상·캠퍼스 포인트는 학습 영역에 포함하고, 서비스 운영·배포·백업·복구는 인프라 영역에 포함한다. 영역 간 연동과 공통 품질 검토는 관련 담당자가 함께 수행한다.

### 1.2 주요 사용자 시나리오

주요 사용자는 교육생과 관리자이며, 교육생은 광고주 역할을 함께 맡을 수 있다. 커뮤니티 이용도 교육생의 활동에 포함한다. 광고주 역할을 맡는다는 것이 캠퍼스·광고 계정의 자동 통합이나 포인트 전환을 뜻하지는 않는다.

| 사용자 | 기본 흐름 | 함께 확인할 예외 |
|---|---|---|
| 교육생 — 캠퍼스·학습 | 로그인 → 캐릭터·캠퍼스 진입 → 이동 → 학습 분류 선택 → 문제 풀이 → 결과·보상 확인 → 캠퍼스 복귀 | 세션 만료, 시도 제한, 동일 답안 재전송, 중단 후 재개 |
| 교육생 — 커뮤니티 | 게시글 조회·작성 → 댓글 조회·작성 → 동료와 정보·의견 교류 | 작성 권한 제한, 삭제된 대상 접근, 게시글·댓글 입력 오류 |
| 교육생 — 광고주 역할 | 광고 서비스 이용 → 캠페인·광고·소재 설정 → 기간·예산 설정 → 운영 상태 확인 → 반응·과금·잔액 조회 | 광고주 이용 권한, 관리자 통제 적용, 유효 광고 없음, 예산 부족, 중복 반응 |
| 관리자 — 게시판 관리 | 관리자 계정 접속 → 게시글·댓글 확인 → 관리 권한으로 수정·삭제 → 처리 결과 확인 | 일반 계정의 관리자 기능 접근, 삭제된 대상·동시 변경 충돌 |
| 관리자 — 광고 관리 | 관리자 계정 접속 → 광고주·광고 운영 상태 확인 → 정해진 관리 권한으로 통제 → 반영 결과 확인 | 관리 권한 부족, 통제 대상·적용 범위 불일치; 구체 조치와 기준은 확인 필요 |

이 역할 구분은 2026-10-18 사용자 설명을 반영한 제품 시나리오다. 파이프라인·인프라 담당자는 내부 구축·운영 역할로서 3.4~3.5절의 요구사항과 5.1.4~5.1.5절의 인수 기준에서 다룬다. 서비스 관리자 계정과 개발·인프라 담당자의 역할을 동일하게 취급하지 않는다.

권한 확인 사항: 기준 커밋의 [게시판 권한 코드][community-permissions]는 관리자뿐 아니라 작성자 본인에게도 수정·삭제를 허용한다. 위 교육생 시나리오는 조회·작성·댓글 이용을 중심으로 정리한 것이며, 작성자 본인의 수정·삭제를 제품 정책에서 유지할지 제한할지는 별도로 확인한다. 현재 코드가 관리자 전용 수정·삭제로 구현됐다고 단정하지 않는다.

### 1.3 제외·보류 범위

현금 결제·출금·환전은 범위 밖이다. 캠퍼스/광고 포인트 전환, 자동 학습 추천·개인별 능력 평가·AI 모델 학습, 자동 입찰·개인 맞춤 광고는 현재 완료 범위에 포함하지 않는다. 외부 게임·영상 내부의 이용 완료를 자동 수집한다고 가정하지 않는다. 다중 AZ 가용성·무중단 운영·목표 동시 접속 성능은 검증 없이 보장하지 않는다. 후속 결정은 8절에서 관리한다.

## 3. 기능 요구사항

실제 분담에 따라 5개 영역으로 나눈다. 각 영역의 담당자가 요구사항과 증적을 관리하며, 서비스 간 연동은 관련 담당자가 함께 검증한다. 기존 ID의 `POINT`는 학습 안의 포인트 기능, `DATA`는 파이프라인, `OPS`는 인프라의 운영 기능을 식별한다.

각 영역은 관련 동작을 묶은 핵심 기능 요구사항 6개로 구성한다. 통합한 항목의 세부 동작과 예외 조건은 유지하며, 하나의 요구사항에 여러 인수 기준을 연결해 검증한다. 기존 ID는 추적을 위해 유지하므로 번호가 연속하지 않을 수 있다.

| `FR-DATA-002` | `UN-DATA-001` | Must | **원천 보존·오류 격리:** 정상 Raw를 MongoDB에 원천 이벤트 ID와 함께 보존하고 같은 ID의 다른 내용으로 최초 원천을 덮어쓰지 않아야 한다. 해석 불가·내용 충돌·계약 검증 실패는 사유와 원천 참조를 구분 보존해 조사·재처리 대상을 찾을 수 있어야 한다. | active |

플랫폼의 발행 정의는 7개 토픽·15개 이벤트다. 브로커 설정이 없으면 Outbox에 대기하며 정의 개수가 실제 전송 성공을 뜻하지 않는다. 수신 실행 예시의 구독 목록은 `raw.points`를 포함하지 않으므로 실제 구독 설정을 별도로 확인해야 한다. 이동 체크포인트의 약 5초 간격을 Kafka 전달 시간 보장으로 해석하지 않는다. [플랫폼 이벤트 계약][platform-contract], [수신 파이프라인][sinker]

Spark 문서는 성공 Std의 9개 사실 테이블 적재를 설명한다. 이 PRD에서는 후속 적재 요구사항을 남기되 실제 운영 연결과 최종 인수 범위는 확인 대상으로 둔다. [Spark 처리][spark]

## 5. Acceptance Criteria

### 5.1 기능·통합 인수 기준

모든 행의 현재 검증 상태는 **미확인**이다. Evidence는 앞으로 확보할 증적의 종류이며, 문서 링크나 테스트 코드의 존재 자체를 실행 통과 증적으로 간주하지 않는다. 3절과 같은 5개 영역으로 묶고, 학습에는 포인트 검증을 포함한다. 영역을 가로지르는 품질 기준은 공통 검증으로 함께 확인한다.

### 5.2 증적과 완료 판정

각 실행 결과에는 `AC ID`, 검증 일시, 실행자, 환경, 커밋·계약·문제은행 버전, 입력 조건, 실제 결과, 증적 위치를 남긴다. 판정은 `미확인 / 통과 / 실패 / 보류`로 구분한다. 보류는 사유와 결정자를 기록하며 통과 건수에 포함하지 않는다. 코드 시험·브라우저 확인·실제 서비스 통합·운영 점검의 확인 수준을 함께 적는다.

이번 버전의 완료 판정은 포함된 Must 요구사항의 관련 AC 통과와 증적 검토를 전제로 한다. Should 제외, draft 범위, 미정 기준은 팀이 인수 포함 여부와 사유를 결정한다. 실패·미확인 항목이 남아 있으면 해당 범위의 완료를 선언하지 않는다. 최종 인수 승인자는 팀 확인이 필요하다.

### 6.2 서비스 연결과 식별자

|---|---|---|
| 학습 제출 → 답안·보상 | 사용자와 `submission_request_uuid`로 재전송 식별, `attempt_uuid`로 답안·지급 연결 | 요청 UUID와 답안 시도 UUID는 역할이 다르다. |

플랫폼 퀴즈 발행 문서는 `quiz_answered 1.1`을 사용하며 수신 문서는 1.0/1.1을 구분한다. 계약 지원 여부와 실제 서버의 구독·배포 버전은 각각 확인한다. 원천·표준 지문 알고리즘은 현재 문서의 `xxh3_64`와 canonical JSON 규칙을 따른다. [플랫폼 계약][platform-contract], [수신 파이프라인][sinker]

수신 파이프라인은 높은 파서 버전에서 기존 실패 결과를 성공으로 복구할 때만 결과를 교체하며 기존 성공 결과는 보존한다. Std 재발행이 가능하므로 후속 소비자의 중복 처리도 함께 검증한다. 원천 보존 기간이 지났거나 외부 서비스가 계속 중단된 경우까지 처리 완료를 보장하지 않는다. [수신 파이프라인][sinker]
