## 3. 요청 제한 수치 (조정 여부)

| 경로군 | 현재 값 | 측정에서 본 것 | 결정 |
|---|---|---|---|
| 결정 `POST` | 150/초, 버스트 300 | 이 하네스의 처리량(MySQL 약 100~110/초, SQLite 약 90~140/초)이 한도보다 낮아, 400개를 한꺼번에 보내도 429는 MySQL 0건·SQLite 23건뿐이다(서버가 느린 동안 토큰이 다시 찬다) | **유지** |
| 반응 `PUT` | 450/초, 버스트 600 | 수신 처리량 MySQL 약 160/초·SQLite 약 350/초(처리 분리 시), 수신 직후 처리를 켜면 약 100~110/초 | **유지** |
| 조회 `GET` | 150/초, 버스트 300 | MySQL 약 195/초·SQLite 약 450/초 | **유지** |

이유: ① 동시 사용자 150명이 실제로 만드는 요청률(사용자당 몇 초에 한 번 수준, 대략 수십 건/초)보다 한도가 여유 있고, ② 하네스는 서버와 클라이언트가 한 프로세스라 **처리량을 낮게 잡는 쪽으로 치우친 측정**이라 이 값을 근거로 한도를 내릴 수 없다. 한도는 한 매체의 폭주를 막는 장치이지 용량 보호 장치가 아니다 — 용량을 넘으면 잠금 대기 초과·연결 한도(503 + `Retry-After`)가 보호한다(SQLite 측정에서는 발생하지 않았고, MySQL 150 동시에서는 연결 한도로 503이 4건 나 재시도로 모두 수신 확인됐다). 측정 전에 정한 초기값을 **그대로 확정**하고, 다중 워커로 배포할 때(프로세스별 버킷 → 한도가 최대 N배로 느슨해진다)나 실제 서버로 다시 재면 이 표를 고친다.

## 4. 이 시험이 보여 주지 않는 것

- **다중 워커·다른 WSGI/ASGI 서버**: 서버는 단일 프로세스다. 프로세스별 요청 제한 버킷의 N배 문제는 확인하지 못했다(처리 프로세스는 별도로 2개를 띄워 DB 수준 동시성은 확인했다).
- **실제 네트워크·프록시**: 같은 장비의 루프백이다.
- **ReplicaSet·Router·인프라 서버**: 개발 PC의 **MySQL 단일 노드** 결과다. Router 경유 접속, 계획된 전환(switchover) 중 503과 복구, 원본 노드 장애 뒤 강제 failover의 유실 범위는 인프라 서버에서 확인할 일이다(계획 DB-1d 남은 항목, §7.3.4-6). **MongoDB**는 아직 연결 전이다(DB-2).
- **연결 풀·영속 연결**: `CONN_MAX_AGE=0`이라 150 동시에서 연결 한도에 닿는다(§2). 배포 구성이 정해지면 다시 잰다.
- **장시간 운용·용량**: 수 초~수십 초의 부하다. 로그·WAL 크기, 장기 지연은 보지 않았다.
- **150명이 실제 사용하는 패턴**: 동시 접속을 한 시각에 몰아 보낸 최악의 형태이며, 현실의 분산 도착보다 가혹하다.

## 7. 장애 시험 (DB-1d 로컬, 2026-10-09)

`scripts/failure_test.py`가 **임시 MySQL 8.4 컨테이너**에서 지속 유입(결정을 받고 노출을 보고하는 클라이언트 여러 개, 계약의 재시도 규칙대로) 중에 장애를 일으키고 약속이 지켜지는지 본다. **복구 판정**: 시험 서버는 접수 직후 처리를 끈다(`REACTION_PROCESS_ON_RECEIPT=False`). 그래서 반응을 처리할 수 있는 것은 **상시 처리 프로세스(`process_reactions`) 2개뿐**이다. 복구 뒤 별도 처리 명령(`process_reactions --once`) 없이 이 프로세스들만으로 대기열이 비워지는지(최대 90초)와, 복구 시각 이후 실제로 처리한 반응이 있는지를 최종 불변식 전에 판정한다(구현 `a9c0573`, 외부 검토 `f095d64`). 이전 판정은 프로세스가 살아 있는지만 보고 마지막에 별도 처리 명령으로 대기열을 비웠다. 그래서 살아 있지만 일하지 않는 프로세스도 통과했다. 같은 조건의 대조 실험에서는 대기열 759건이 남고 처리 0건으로 실패하는 것을 구현 세션이 확인했다. 측정: 문서 세션이 `--json`으로 실행(2026-10-09, 코드 `a9c0573`), 종료 코드 0.

| 시나리오 | 장애 | 요청 / 시도 | 끊김을 겪은 시도 | 500 | 끝내 수신 확인 | 처리 프로세스 | 복구 뒤 상시 프로세스 처리 / 남은 대기열 | 불변식(유실 0·이중 과금 0·잔액=원장·소진액=원장·대기열 없음) |
|---|---|---:|---:|---:|---|---|---:|---|
| restart | `docker restart`(정상 종료 → 기동, 계획된 재시작·전환에 가까움) | 1446 / 1473 | 27 | 0 | 전부(실패 0) | 2개 모두 생존 | 568건 / 0 | ✔ (결정 723·반응 723) |
| crash | `docker kill`(SIGKILL) → 기동, InnoDB 충돌 복구 | 1426 / 1442 | 16 | 0 | 전부(실패 0) | 2개 모두 생존 | 532건 / 0 | ✔ (수신 확인한 결정 713·반응 713 모두 존재) |
| processor-kill | 처리 프로세스 하나를 SIGKILL하고 새로 띄움(DB는 그대로) | 1270 / 1270 | 0 | 0 | 전부(실패 0) | 2개 모두 생존(하나는 새로 띄운 것) | 503건 / 0 | ✔ (결정 635·반응 635) |

이전 판정 방식으로 낸 첫 측정(코드 `f095d64`)은 요청 1130·1180·942건이었고 결과는 같았다(500 0, 실패 0, 불변식 통과).

- 끊김 동안 API는 **503 또는 연결 실패만** 냈고 500은 없었다. 클라이언트는 같은 ID로 재시도해 모두 수신 확인됐다.
- **강제 종료(crash)에서도 수신 확인(2xx)한 것은 전부 살아 있었다** — 커밋마다 로그를 디스크에 내리는 설정(`innodb_flush_log_at_trx_commit=1`)에서의 단일 노드 결과다.
- **복구는 상시 처리 프로세스만으로 끝났다.** 세 시나리오 모두 별도 처리 명령 없이 대기열이 0건이 됐고, 복구 뒤 상시 프로세스가 직접 처리한 반응은 568·532·503건이다. DB가 끊겼다 돌아와도 프로세스는 죽지 않았다(DB-1d 수정 — 이전에는 대기열 조회 예외로 죽었다). 새로 띄운 프로세스도 남은 일을 이어받았다.
- **이 시험이 보여 주지 않는 것**: ReplicaSet의 **강제 failover**(비동기 복제 지연분 유실)와 Router 경유 전환. 단일 노드의 커밋 내구성까지만 보장되며, 허용 유실 범위는 사람이 정한다(계획 §7.3.4-6).
