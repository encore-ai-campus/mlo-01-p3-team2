## 3. 요청 제한 수치 (조정 여부)

| 경로군 | 현재 값 | 측정에서 본 것 | 결정 |
|---|---|---|---|
| 결정 `POST` | 150/초, 버스트 300 | 이 하네스의 처리량(MySQL 약 100~110/초, SQLite 약 90~140/초)이 한도보다 낮아, 400개를 한꺼번에 보내도 429는 MySQL 0건·SQLite 23건뿐이다(서버가 느린 동안 토큰이 다시 찬다) | **유지** |
| 반응 `PUT` | 450/초, 버스트 600 | 수신 처리량 MySQL 약 140~160/초·SQLite 약 350/초(처리 분리 시), 수신 직후 처리를 켜면 약 90~110/초 | **유지** |
| 조회 `GET` | 150/초, 버스트 300 | MySQL 약 195~205/초·SQLite 약 450/초 | **유지** |

이유: ① 동시 사용자 150명이 실제로 만드는 요청률(사용자당 몇 초에 한 번 수준, 대략 수십 건/초)보다 한도가 여유 있고, ② 하네스는 서버와 클라이언트가 한 프로세스라 **처리량을 낮게 잡는 쪽으로 치우친 측정**이라 이 값을 근거로 한도를 내릴 수 없다. 한도는 한 매체의 폭주를 막는 장치이지 용량 보호 장치가 아니다 — 용량을 넘으면 잠금 대기 초과·연결 한도(503 + `Retry-After`)가 보호한다(SQLite 측정에서는 발생하지 않았고, MySQL 150 동시에서는 연결 한도로 503이 4건 나 재시도로 모두 수신 확인됐다). 측정 전에 정한 초기값을 **그대로 확정**하고, 다중 워커로 배포할 때(프로세스별 버킷 → 한도가 최대 N배로 느슨해진다)나 실제 서버로 다시 재면 이 표를 고친다.

## 4. 이 시험이 보여 주지 않는 것

- **다중 워커·다른 WSGI/ASGI 서버**: 서버는 단일 프로세스다. 프로세스별 요청 제한 버킷의 N배 문제는 확인하지 못했다(처리 프로세스는 별도로 2개를 띄워 DB 수준 동시성은 확인했다).
- **실제 네트워크·프록시**: 같은 장비의 루프백이다.
- **ReplicaSet·Router·인프라 서버**: 개발 PC의 **MySQL 단일 노드** 결과다. Router 경유 접속, 계획된 전환(switchover) 중 503과 복구, 원본 노드 장애 뒤 강제 failover의 유실 범위는 인프라 서버에서 확인할 일이다(계획 DB-1d 남은 항목, §7.3.4-6). **MongoDB**는 공유 시험 컨테이너의 단일 서버(부하 시험)와 임시 단일 노드 레플리카셋(장애 시험)에서만 봤다. 3대 레플리카셋의 과반 확인 지연과 failover 때의 이벤트는 인프라 서버에서 확인할 일이다.
- **연결 풀·영속 연결**: `CONN_MAX_AGE=0`이라 150 동시에서 연결 한도에 닿는다(§2). 배포 구성이 정해지면 다시 잰다.
- **장시간 운용·용량**: 수 초~수십 초의 부하다. 로그·WAL 크기, 장기 지연은 보지 않았다.
- **150명이 실제 사용하는 패턴**: 동시 접속을 한 시각에 몰아 보낸 최악의 형태이며, 현실의 분산 도착보다 가혹하다.

## 7. 장애 시험 (DB-1d 로컬 · Step 4, 2026-10-10)

`scripts/failure_test.py`가 **임시 MySQL 8.4 컨테이너와 임시 MongoDB 8.0 단일 노드 레플리카셋(인증 켜짐)**에서 지속 유입(결정을 받고 노출을 보고하는 클라이언트 여러 개, 계약의 재시도 규칙대로) 중에 장애를 일으키고 약속이 지켜지는지 본다.

- **복구 판정**: 시험 서버는 접수 직후 처리를 끈다(`REACTION_PROCESS_ON_RECEIPT=False`). 그래서 반응을 처리할 수 있는 것은 **상시 처리 프로세스(`process_reactions`) 2개뿐**이고, 이벤트를 MongoDB로 옮길 수 있는 것은 **상시 중계 프로세스(`relay_events`) 2개뿐**이다. 복구 뒤 별도 명령 없이 이 프로세스들만으로 대기열과 미전송이 비워지는지(각각 최대 90초), 복구 시각 이후 실제로 처리·전송한 것이 있는지를 최종 불변식 전에 판정한다(처리는 구현 `92f95ea`, 외부 검토 `f2e930b` / 중계는 Step 4-1f).
- **최종 불변식**: 유실 0·이중 과금 0·잔액 = 원장·소진액 = 원장·남은 대기열 없음, 그리고 이벤트 검증(§1 ⑤): 원본 행 ↔ outbox는 하나씩·내용 전체(JSON 타입 포함), outbox ↔ MongoDB는 ID 집합과 문서 전체.
- **대조 실험**(구현 세션): 처리 프로세스를 일하지 않는 프로세스로 바꾸면 대기열 759건이 남고 처리 0건으로, 중계를 일하지 않는 프로세스로 바꾸면 미전송 3052건이 남고 MongoDB와 불일치로 실패한다. 판정이 공회전을 통과시키지 않는다는 확인이다.

- 끊김 동안 API는 **503 또는 연결 실패만** 냈고 500은 없었다. 클라이언트는 같은 ID로 재시도해 모두 수신 확인됐다.
- **강제 종료(crash)에서도 수신 확인(2xx)한 것은 전부 살아 있었다** — 커밋마다 로그를 디스크에 내리는 설정(`innodb_flush_log_at_trx_commit=1`)에서의 단일 노드 결과다. 이벤트도 원본 행과 같은 트랜잭션이라 함께 살아 있었다(이벤트 일대일).
- **이번 `mongo-restart` 실행에서는 요청에 503·연결 실패가 0이었다**(관찰). 요청 경로는 MongoDB를 호출하지 않고 MySQL의 outbox에만 쓴다(보장). 끊긴 동안 미전송이 최대 191건 쌓였고, 복구 뒤 상시 중계만으로 0이 됐다. 짧은 재시작이었고 장기 장애는 재현하지 않았다 — 장애가 길면 outbox가 같은 MySQL에 쌓이고, 중계는 MySQL 연결과 잡은 행의 잠금을 쥔 채 MongoDB를 기다린다(설계 §10 "MongoDB 장애와 요청").
- **유입 도중 중계를 죽여도 이벤트는 늘거나 줄지 않았다**(`relay-kill`): 이벤트 ID가 원천 행에서 결정적이라, 보낸 뒤 표시하기 전에 죽었더라도 다시 보낼 때 같은 내용의 중복으로 통과한다. 새로 띄운 중계가 남은 일을 이어받았다.
- **복구는 상시 프로세스만으로 끝났다.** 다섯 시나리오 모두 별도 명령 없이 대기열과 미전송이 0건이 됐다. DB가 끊겼다 돌아와도 처리·중계 프로세스는 죽지 않았다.
- **이 시험이 보여 주지 않는 것**: MySQL ReplicaSet의 **강제 failover**(비동기 복제 지연분 유실)와 Router 경유 전환, MongoDB 3대 레플리카셋의 failover. 단일 노드의 커밋 내구성까지만 보장되며, 허용 유실 범위는 사람이 정한다(계획 §7.3.4-6).

## 9. InnoDB Cluster (3노드 그룹 복제 + Router, 2026-10-10)

- **이 시험이 보여 주지 않는 것**: 한 호스트의 Docker 클러스터라 네트워크 분리(과반을 잃는 경우)·지연은 넣지 않았다. 인프라 서버의 실제 failover 시간과 유실 범위는 따로 확인한다.
