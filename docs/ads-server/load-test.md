## 2. 측정값 (이 장비, 이 구성)

환경: 파일 SQLite(WAL, `synchronous=FULL`, `IMMEDIATE`), 파이썬 `wsgiref` 스레드형 서버(운영용이 아님) + 클라이언트가 **같은 프로세스**, 단일 서버 프로세스. 클라이언트는 계약의 재시도 규칙을 지킨다(이번에는 재시도가 필요 없었다).

| 단계 | 요청 | 최종 상태 | 처리량(건/초) | 마지막 시도 지연 p50 / p95 / p99 / max (ms) |
|---|---:|---|---:|---|
| A 동시 결정 | 150 | 201×150 | 94 | 605 / 1228 / 1542 / 1583 |
| B 동시 반응 | 150 | 201×150 | 107 | 510 / 1111 / 1367 / 1389 |
| B′ 동시 조회 | 150 | 200×150 | 456 | 176 / 311 / 316 / 319 |
| C 같은 유형 동시 | 150 | 201×150 | 109 | 429 / 934 / 1236 / 1337 |
| C′ 세 유형 동시 | 150 | 201×150 | 156 | 411 / 806 / 951 / 954 |
| D 재전송 폭주 | 150 | 201×1, 200×149 | 245 | 271 / 489 / 593 / 601 |
| E 지속 유입 | 2644 | 201×2644 | 351 | 5 / 120 / 877 / 3791 |
| F 버스트 초과 | 400 | 201×377, 429×23 | 137 | 1288 / 2454 / 2686 / 2888 |

- 150개가 **같은 순간**에 도착해도 전부 첫 시도에 성공했다(503·연결 거절 0 — 독립 검토의 두 번 실행도 같았다). 지연·처리량은 실행마다 달라(결정 p99 1.2~2.2초, 429 건수 9~23건) 고정 성능이 아니라 **이 하네스의 관찰값**으로 읽는다. 지연이 1~2초대인 것은 요청이 쓰기 잠금과 이 서버의 단일 프로세스(GIL)에서 줄을 서기 때문이다.
- **결정 요청 1건 = 질의 11개**(SELECT 6, BEGIN/SAVEPOINT/INSERT/RELEASE/COMMIT 각 1). 서버 안쪽 중앙값 3.4 ms. **`slot_name` 조회가 더하는 시간은 실행마다 0.1~0.8 ms**(독립 검토에서 0.10·0.78 ms)로 한 요청의 3.4 ms 안에서 작아 별도 최적화가 필요 없다(설계 §10 결정 API 세부 ⑤).
- 반응 처리는 수신 직후 처리를 켠 상태(B)에서 약 107건/초, 처리를 별도 프로세스에 맡긴 상태(E)에서 수신 약 350건/초였다. 수신(짧은 INSERT 하나)과 처리(과금까지)를 나눈 설계(§6.5-2)의 효과다.

## 3. 요청 제한 수치 (조정 여부)

| 경로군 | 현재 값 | 측정에서 본 것 | 결정 |
|---|---|---|---|
| 결정 `POST` | 150/초, 버스트 300 | 이 하네스의 처리량(약 90~140/초)이 한도보다 낮아, 400개를 한꺼번에 보내도 429는 23건뿐이다(서버가 느린 동안 토큰이 다시 찬다) | **유지** |
| 반응 `PUT` | 450/초, 버스트 600 | 수신 처리량 약 350/초(처리 분리 시), 수신 직후 처리를 켜면 약 110/초 | **유지** |
| 조회 `GET` | 150/초, 버스트 300 | 약 450/초까지 처리 | **유지** |

이유: ① 동시 사용자 150명이 실제로 만드는 요청률(사용자당 몇 초에 한 번 수준, 대략 수십 건/초)보다 한도가 여유 있고, ② 하네스는 서버와 클라이언트가 한 프로세스라 **처리량을 낮게 잡는 쪽으로 치우친 측정**이라 이 값을 근거로 한도를 내릴 수 없다. 한도는 한 매체의 폭주를 막는 장치이지 용량 보호 장치가 아니다 — 용량을 넘으면 잠금 대기 초과(503 + `Retry-After`)가 보호한다(이번 측정에서는 발생하지 않았다). 측정 전에 정한 초기값을 **그대로 확정**하고, 다중 워커로 배포할 때(프로세스별 버킷 → 한도가 최대 N배로 느슨해진다)나 실제 서버로 다시 재면 이 표를 고친다.

## 4. 이 시험이 보여 주지 않는 것

- **다중 워커·다른 WSGI/ASGI 서버**: 서버는 단일 프로세스다. 프로세스별 요청 제한 버킷의 N배 문제는 확인하지 못했다(처리 프로세스는 별도로 2개를 띄워 DB 수준 동시성은 확인했다).
- **실제 네트워크·프록시**: 같은 장비의 루프백이다.
- **MySQL·MongoDB**: SQLite 결과다. 같은 결정·유형의 `ACCEPTED`를 하나로 제한하는 안전망은 조건부 유일 제약이라 MySQL·MariaDB에서는 쓸 수 없다(설계 §10, 전환 때 다시 검증).
- **장시간 운용·용량**: 수 초~수십 초의 부하다. 로그·WAL 크기, 장기 지연은 보지 않았다.
- **150명이 실제 사용하는 패턴**: 동시 접속을 한 시각에 몰아 보낸 최악의 형태이며, 현실의 분산 도착보다 가혹하다.
