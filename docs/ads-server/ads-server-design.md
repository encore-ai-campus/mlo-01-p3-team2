# 1. 왜 다시 설계하나

이전 설계는 교안(22일차 게임 서버 연동)의 동작을 재현하는 데 맞춰져 **소비하는 쪽(매체 서버)의 개념에 광고 서버가 끌려갔다.** 요청·응답 필드, 인증, 슬롯, 대상 식별이 매체 쪽 사정에 맞춰져 있었다.

**이번 원칙 [확정]**

1. 광고 서버는 **독립적으로 동작하고 자체 구조적 무결성을 갖춘다.** 매체 서버가 없어도 캠페인·입찰·소재·예산을 운영할 수 있고, 매체 서버를 가짜(stub)로 바꿔도 테스트가 돈다.
2. 소비하는 쪽·공급하는 쪽 모두 **인터페이스 계약으로만** 만난다. 계약이 먼저고, 코드는 계약을 구현한다.
3. 광고 서버는 매체의 개념(사용자 테이블, 강의실, 게임 등)을 모른다. 필요한 값은 계약에 **불투명 값**으로 받는다.

## C4 Insight 입력의 원칙 [제안]

광고 분석·입찰 제안·개인 맞춤 같은 확장은 **데이터 파이프라인이 만든 결과가 광고 서버로 들어오는 길**이 필요하다. 그 길이 광고 서버의 무결성을 깨지 않게 아래를 지킨다.

1. **자문(advisory)이지 명령이 아니다.** 들어온 값은 별도 저장소에 출처·버전·유효기간과 함께 저장된다. 입찰 정책(§4)을 자동으로 바꾸지 않는다. 관리자가 확인해 적용한다. (자동화는 범위 밖)
2. **광고 서빙 경로는 실시간으로 파이프라인에 의존하지 않는다.** 파이프라인이 죽어도 광고는 나간다. 서빙은 이미 저장된 값만 읽는다.
3. 입력 종류(후보): ① 슬롯·캠페인별 성과 집계(노출·클릭·전환) ② 입찰 추천 ③ 대상(`subject_id`)별 신호 (개인 맞춤용, 이후).
4. 전달 방식(HTTP push / Kafka 소비 / 파일 투입)은 **[열림]**. Step 4~5 이후 정한다. 계약은 방식과 무관하게 메시지 스키마로 정의한다.

## C5 포인트 충전 입력의 원칙 [제안, 예약]

메타버스에서 얻은 포인트를 광고 포인트로 쓰게 하는 연계다. 지금은 구현하지 않고 **들어올 자리**만 확보한다.

1. 충전은 **원장에 `TOPUP` 항목을 추가하는 것으로만** 반영한다(잔액을 직접 고치지 않는다, §4.7).
2. **외부 거래 ID로 멱등**이다. 같은 거래가 두 번 와도 한 번만 반영된다.
3. 외부 사용자와 광고주 계정을 어떻게 연결할지(불투명 `external_ref`를 계정에 저장?)는 **[열림 §7-7]**. 독립성 원칙상 광고 서버는 매체의 사용자 모델을 모른다.

## C1 엔드포인트 [제안: RESTful, 초안 작성됨]

원본은 [contracts/serving.openapi.yaml](contracts/serving.openapi.yaml)(OpenAPI 3.1)이고, 아래는 요약이다. 둘이 다르면 계약 파일이 맞다.

| 메서드·경로 (`/api/media/v1` 아래) | 의미 | 성공 | 주요 오류 |
|---|---|---|---|
| `POST /decisions` | 광고 요청 → **Decision 생성** | **201** + `Location`. 광고가 없어도, **활성 매체가 소유한 비활성 슬롯**이어도 201(`ad: null`) | 400, 401(키 없음·무효), 403(**매체 비활성**), **404(없는 슬롯·다른 매체의 슬롯)**, 413, 415, 429, 503 |
| `GET /decisions/{decision_id}` | 내 결정 조회(정합 확인용) | 200 | 401, **404**(없거나 다른 매체 것) |
| `PUT /decisions/{decision_id}/reactions/{reaction_id}` | **반응 보고(멱등)** | **201** 처음 접수 / **200** 같은 내용 재전송 | 400, 401, **409**(같은 ID, 다른 내용), 429, 503 |
| `GET /decisions/{decision_id}/reactions/{reaction_id}` | 반응의 **처리 결과** 조회(`RECEIVED`/`ACCEPTED`/`REJECTED`) | 200 | 401, 404 |
| `GET /health` | 상태 확인(인증 없음) | 200 | |
| `GET /assets/{sha256}.{jpg\|png}` (루트 경로) | 소재 이미지(C3) | 200 / 304 | 404 |

**설계 선택**

- **자원 중심**: 광고 요청이 `Decision` 자원을 만들고, 반응은 `Decision` 아래의 하위 자원이다. 동사가 아니라 자원과 HTTP 메서드로 표현한다.
- **반응은 `PUT` + 매체가 정한 `reaction_id`**: 클라이언트가 ID를 정해 같은 주소로 보내면 몇 번을 보내도 결과가 같다(멱등). 설계의 "2xx 받을 때까지 같은 `reaction_id`로 재시도" 규칙이 HTTP 의미 그대로 성립한다. 유일성 범위는 **매체 안**이라, 다른 매체가 같은 ID를 먼저 써도 충돌하지 않는다.
- **접수와 처리의 분리**: `PUT`의 2xx는 "저장했다"는 확인이고, 과금 판정은 이후에 일어난다. 결과는 `GET`으로 본다. 존재하지 않는 결정·다른 매체의 결정에 대한 보고도 일단 접수되고 `REJECTED`로 판정된다(접수한 반응은 지우지 않는다, §4.4-13).
- **결정 요청(`POST`)은 멱등하지 않다.** 재시도하면 새 결정이 생길 수 있지만 과금은 반응에서만 일어나므로 무해하다.
- **매체는 본문이 아니라 키로 식별**한다(`X-Media-Key`). 요청에 `media_id`를 싣지 않는다. 응답에는 **입찰·금액·정책 정보가 없다**(매체가 알 필요 없는 내부 정보).
- **상태 코드**: 키 없음·오류는 **401**, 키는 유효하지만 불가(매체 비활성 등)는 **403**, 남의 자원은 **404**(존재를 알리지 않음), 검증 오류는 **400**, 한도 초과·잠금은 **429/503 + `Retry-After`**.
- **오류 형식**: `application/problem+json`(RFC 9457) — `type`·`title`·`status`·`code`·`detail`·`request_id`(+ 검증 오류는 `errors[]`). 프로그램은 `code`로 분기한다.
- **공통 규약**: JSON(UTF-8), `snake_case`, ID는 UUID, 시각은 RFC 3339 UTC(`Z`), 요청 본문 최대 16 KiB, 모든 응답에 `X-Request-ID`.

**슬롯 지정 [확정]**: UUID(`slot_id`)로 지정한다. 사람이 읽는 이름(`slot_name`)은 응답에 함께 실어 주되 식별에는 쓰지 않는다(DRD도 UUID 중심). **열린 항목 [열림]**: 매체별 요청 제한 수치, 소재 `title` 최대 길이(현재 200).

## C1 반응 전달 규칙 [확정 방향]

반응(노출·클릭·전환)은 곧 과금이고 **유실되면 안 되므로**, 전달 방식을 계약에 못 박는다.

1. **즉시 보고한다.** 매체는 노출·클릭·전환을 감지하는 즉시 보고한다. 모아서 보내는 배치는 없다. [확정]
2. **2xx 응답 = 광고 서버가 영속 저장했다는 확인**이다. 광고 서버는 디스크에 쓴 뒤에만 2xx를 보낸다(§6.5).
3. **2xx를 받기 전까지 매체는 같은 `reaction_id`로 재시도한다**(타임아웃·5xx·연결 실패 모두, 지수 백오프). 같은 `reaction_id`는 몇 번을 보내도 한 번만 처리된다. 광고 서버는 최소 한 번(at-least-once) 전달을 받고 중복은 `reaction_id`로 제거한다.
4. `reaction_id`는 **매체가 만든다**(UUID). 감지 시점에 만들고 재시도 때 바꾸지 않는다. 유일성의 범위는 **매체 안**이다.
5. 광고 서버가 일시적으로 받지 못하면 **503**(또는 제한 초과 **429**)을 `Retry-After`와 함께 준다(수신 확인을 하지 않음). 이때 매체는 같은 요청을 다시 보낸다. 형식 오류 같은 그 밖의 4xx는 재시도해도 소용없으므로 재시도하지 않는다.
6. `PUT`의 응답은 반응 자원(`status: RECEIVED`)이다. **처리 결과(인정/거부)를 응답으로 기다리지 않고** `GET`으로 확인한다. 수신 확인과 처리는 분리된다(§6.5).

원본은 [contracts/console.openapi.yaml](contracts/console.openapi.yaml)이다. V1에서는 JSON API로 구현하지 않지만, **서비스 계층(`campaigns`·`billing`의 `api`)이 지켜야 할 규칙의 명세**로 지금부터 쓴다. 템플릿 화면과 이후의 JSON API가 같은 규칙을 따르게 하기 위함이다(§6.6).

| 성과·알림(읽기) | `/reports/daily`, `/alerts` | `GET` |

**설계 선택**

- **입찰 수정 = 새 버전 추가.** `PUT`·`PATCH`로 입찰을 고치지 않고 `POST .../bids`가 새 `bid_version`을 만든다(§4.2). **`expected_version`**(화면에서 본 버전)이 현재와 다르면 **409 `stale_version`**이다.
- **입력은 거절하지 않고 알려준다.** 하한 미만·상한 초과 입찰도 저장되며, 응답의 **`effects`**(슬롯별 `eligible`·`applied_amount`·`reason`)가 노출 여부와 적용 금액을 알려준다. 저장 전에는 **`bid-preview`** 로 같은 결과를 미리 본다.
- **삭제가 없다.** 캠페인·광고그룹·소재는 이력(결정·원장)이 참조하므로 `DELETE` 대신 끄기(`status`·`enabled`)로 처리한다.
- **과금 단위는 바꿀 수 없다**(409 `unit_immutable`). 고른 슬롯은 모두 그 단위여야 한다(400 `unit_mismatch`).
- **`SUSPENDED`(관리자 중단) 중에는 광고주가 `status`를 바꿀 수 없다**(409 `suspended`). 사유는 캠페인 응답에 담겨 읽을 수 있다. **그 밖의 수정은 허용한다 [확정]**. 고친 뒤에는 **재검토 요청**(`POST /campaigns/{id}/review-requests`)으로 관리자에게 알린다 [제안, §4.5].
- **소유권**: 남의 자원·없는 자원은 모두 404다.
- **금액은 정수 포인트**(`30`), 시각은 UTC, 일별 성과의 날짜 경계는 **예산의 일 경계와 같다**(§4.7).
- **알림(`/alerts`)은 저장하지 않고 현재 상태에서 계산**한다(관리자 중단, 예산 소진, 잔액 부족, 입찰 하한 미만·상한 적용 등).

**범위 밖**: **관리자 기능**(입찰 정책 새 버전 입력, 캠페인 중단/해제, 포인트 조정, 매체·슬롯 관리, 광고주 계정 관리)은 Django admin(서버 렌더)이라 C6에 없다. 이 기능들도 서비스 `api` 함수로만 존재하며, 관리자 화면을 분리하게 되면 **그때** 별도 계약(C7)으로 추가한다 [확정].

## 독립성 규칙 (코드 리뷰 체크리스트)

- 광고 서버 코드·문서에 매체 서버의 모듈, 테이블, 교안 용어가 나오지 않는다.
- **노출 대상 UUID(`subject_id`)는 받는다 [확정].** C1의 필수 필드이고 Decision·이벤트에 저장한다. 이후 개인 맞춤 확장에 쓰기 위함이다.
  - **V1에서 수집만 한다. 조회·해석·분석은 구현하지 않는다.** 선택 로직도 `subject_id`를 읽지 않는다. [확정]
  - 가명 UUID여야 한다. 로그인 ID·닉네임 등 직접 식별자는 받지 않는다(계약에 명시, 입력 검증).
  - 광고주 화면·관리자 화면·API 응답으로 되돌려주지 않는다. [제안]
- 매체 부가정보 `context`는 **크기 제한이 있는 불투명 JSON**. 저장만 하고 V1에서 해석하지 않는다.
- **C1 응답의 문자열(제목·이동 주소)은 광고주가 입력한 신뢰할 수 없는 값이다.** 계약에 명시하고, 매체는 화면에 쓸 때 이스케이프하며 이동 주소는 새 창(`noopener`)으로 연다.
- **시각은 저장·계산·계약 모두 UTC**(ISO 8601, `Z`)다. KST는 **화면 표시 변환에서만** 쓴다. [확정] 일 단위 경계(일예산 등)도 기본은 UTC 기준이므로 화면에 리셋 시각(KST 09:00)을 표시한다. 경계는 바꿀 수 있게 열어 둔다 [열림 §7-1].
- 외부 데이터 표준(DRD)과의 이름 대응은 **나가는 경계(C2)에서만** 한다. 내부 모델은 DRD가 바뀌어도 흔들리지 않는다. [제안]

# 4. 도메인 (광고 서버 자체의 어휘)

소유 주체별로 세 부류로 나눈다. 이 경계가 곧 모듈 경계다(§6).

**식별자와 이름 [확정]**: 모든 자원은 **UUID로 식별**한다. 자원 모델(매체·슬롯·캠페인·광고그룹·소재 등)은 UUID가 PK이고, **추가 전용 기록**(입찰·입찰 정책 버전, 원장, 결정, 감사 로그)은 **정수 PK + UUID UNIQUE 식별자**(`bid_id`·`bid_policy_id`·`entry_id`·`decision_id`)다. 계약·이벤트·다른 모듈은 UUID로만 가리킨다. 이름(`name`, 슬롯명 등)은 사람이 읽기 위한 **편의 정보**이며 바뀔 수 있다. 계약·로직·이벤트는 이름이 아니라 ID로 식별하고, 응답에는 읽기 쉽도록 이름을 **함께 실어 주되 식별에는 쓰지 않는다**. 이름의 유일성(예: 슬롯명)은 사람의 혼동을 막으려는 제약이다 [제안: 매체 안에서 유일. DRD의 `slot_name`은 전역 유니크라 DRD 쪽과 정합 확인 필요].

```
[관리자 소유 · Master]        Media ──< Slot(게재 위치, 과금 단위) ──< BidPolicy (하한·기준가·상한, 버전)

[광고주 소유 · Operational]   Advertiser ──  Wallet ──< LedgerEntry (추가만)
                              Advertiser ──< Campaign (기간·일예산·상태)
                                               └──< AdGroup (게재 위치들·과금 단위·입찰·ON/OFF)
                                                      ├──< Creative (이미지·제목·이동 주소)
                                                      └──< Bid (광고그룹별 버전)

[추가만 · Append-only]        Decision (불변 스냅샷) ──< Reaction ──> LedgerEntry(CHARGE)
```

## 4.1 입찰 정책 마스터 `BidPolicy` [제안: 보완 요청 반영]

`bid_version`만 있고 이를 규정하는 마스터가 없던 것을 보완한다. **입찰 기준값(하한·기준가·상한)은 관리자가 마스터에서 관리한다.** 정책이 정한 **노출 범위 `[하한, 상한]`** 안에 드는 입찰만 노출된다(§4.2). **게재 위치(슬롯)마다 금액과 방식(과금 단위)을 다르게 둔다. [확정]**

| 필드 | 설명 |
|---|---|
| `slot` + `pricing_unit` | 키. 과금 단위는 `IMPRESSION`(노출) / `CLICK`(클릭) / `CONVERSION`(전환) [확정]. **슬롯은 과금 단위를 하나 가진다.** 한 슬롯에 여러 단위를 두는 것은 V2 이후 [확정 보류] |
| `floor_amount` | **하한.** 노출 범위의 아래 경계 |
| `base_amount` | **기준가.** 입찰 화면의 기본 입력값. 선택 알고리즘이 이 값을 어떻게 쓸지는 알고리즘 몫이다(V1 알고리즘은 쓰지 않는다) |
| `cap_amount` | **상한.** 노출 범위의 위 경계. 이 금액을 넘는 입찰은 모두 상한으로 취급 [확정] |
| `policy_version` | 슬롯별 1부터 증가. **수정이 아니라 새 버전 행 추가.** 현재 값 = 최대 버전 |
| `changed_by`, `changed_at`, `reason` | 누가·언제·왜 바꿨는지(감사) |

- 제약: `floor ≤ base ≤ cap`, 모두 0 초과 정수. DB 제약 + 서비스 검증 양쪽.
- 정책은 관리자 화면에서 **수동 수정**한다(V1). 이후 알고리즘 자동화는 범위 밖이며, 그때는 C4 입력을 관리자가 검토해 새 버전으로 넣는 경로를 쓴다.

## 4.2 입찰 `Bid` [확정: 하한 미만도 입력 가능]

- 입찰은 **광고그룹**(§4.6)에 붙는다. 광고그룹의 `pricing_unit`은 **생성 시 고정**되고 바꿀 수 없다(입찰 이력의 의미가 섞이지 않게).
- 입찰 변경 = **새 `bid_version` 행 추가.** 광고주가 입력한 금액을 그대로 저장한다.
- **입력은 거절하지 않는다.** 하한 미만도, 상한 초과도 저장된다. 검증은 0 초과 정수·표현 가능한 최대값뿐이다. 화면은 **게재 위치별 현재 정책 기준으로 안내**한다: 하한 미만이면 "현재 하한 미만이라 노출되지 않습니다", 상한 초과면 "상한 금액으로 적용됩니다".
- **노출 자격과 적용 금액은 선택 시점에, 요청된 슬롯의 현재 정책으로 계산**한다(저장하지 않는다). 같은 입찰이라도 슬롯마다 결과가 다를 수 있다.
- **이 계산(아래 표)은 `engine`의 순수 함수 한 곳에만 둔다 [확정].** 선택 로직과 광고주 화면의 안내값(`effects`·`bid-preview`)이 같은 함수(`engine.api`)를 부른다. `campaigns`·`masters`는 입찰과 정책의 **값만 공급**하고 금액을 계산하지 않는다.

| 입찰 금액 | 결과 (해당 슬롯 정책 기준) |
|---|---|
| `입찰 < 하한` | **후보에서 제외** (노출되지 않음) |
| `하한 ≤ 입찰 ≤ 상한` | 입찰 금액 그대로 적용 |
| `입찰 > 상한` | **상한 금액**으로 적용 |

- 관리자가 정책을 바꾸면 같은 입찰의 자격이 바뀔 수 있다(하한을 낮추면 노출되기 시작, 올리면 노출이 멈춤). 입찰 행은 그대로이고 선택 시점에 계산하므로 별도 갱신 작업이 없다. **어느 정책 버전으로 판정했는지는 Decision에 남는다.**

| 버전 | 누가 | 무엇을 | 의미 |
|---|---|---|---|
| `policy_version` | 관리자 | 슬롯의 하한·기준가·상한 | 노출 범위 규칙의 이력 |
| `bid_version` | 광고주 | 광고그룹의 입찰 금액 | 광고주 의사의 이력 |
| Decision | 시스템 | 위 두 버전을 모두 기록 | 과거 선택이 어떤 규칙·입찰로 이뤄졌는지 재현 |

### 동시 수정은 낙관적 잠금(`expected_version`)으로 막는다 [확정: 1-1에서 구현]

입찰·입찰 정책의 변경은 새 버전 행 추가다. 이때 **두 사람이 같은 화면(같은 버전)을 보고 각자 저장하면** "최대 버전 + 1"만 쓰는 구현은 둘 다 성공(버전 n+1, n+2)해서 **나중 사람이 앞사람의 변경을 모른 채 덮어쓴다**(lost update). SQLite는 쓰기 트랜잭션을 직렬로 처리하지만 그것은 *순서*를 만들 뿐, 두 변경이 같은 기준에서 나왔다는 *의도의 충돌*을 알지 못한다. 그래서 호출자가 화면에서 본 버전을 함께 보내게 하고(`expected_version`), **현재 버전과 다르면 409 `stale_version`** 으로 거절한다. 거절된 쪽은 새로 불러와 다시 판단한다.

**낙관적 잠금을 고른 이유**

| 대안 | 결과 | 판단 |
|---|---|---|
| 마지막 저장이 이김 | 앞 변경이 알림 없이 사라진다. 정책은 노출 경쟁의 규칙이고 입찰은 광고주의 의사라, 조용한 덮어쓰기는 이력(Decision이 기록하는 두 버전)의 의미를 흐린다 | 불채택 |
| 비관적 잠금(편집 시작 시 잠금) | 편집 화면에 머무는 시간(분 단위) 동안 잠금을 쥐어야 한다. 사용자가 창을 닫으면 풀리지 않아 만료·강제 해제 규칙이 따로 필요하다. 또 SQLite는 쓰기가 직렬이라 DB 잠금을 오래 쥐면 **반응 수신(150명 동시, §6.5)까지 막는다**. `select_for_update`는 SQLite에서 의미도 없다 | 불채택 |
| **낙관적 잠금(채택)** | 잠금 없이 저장 시점에 "내가 본 버전이 아직 현재인가"만 비교한다. 충돌은 드물다(관리자 소수, 캠페인 소유자 한 사람). 서버가 무상태라 화면이 JSON API로 분리돼도(§6.6) 그대로 쓴다(HTTP의 `If-Match`와 같은 방식) | **채택** |
| 서버가 자동 병합 | 정책 값(하한·기준가·상한)은 서로 의존해서(`하한 ≤ 기준가 ≤ 상한`) 필드 단위 병합이 규칙을 깨뜨릴 수 있다 | 불채택 |

- 이 모델에서는 **버전 번호 자체가 잠금 토큰**이다. 이미 "행 추가 + 버전" 구조라 컬럼을 더하지 않는다.
- `(부모, 버전)` 유니크 제약은 **안전망**이다(다른 DB로 옮겨 쓰기가 병행될 때 검사와 저장 사이의 틈을 막는다). 주된 방어는 `expected_version` 비교다.
- **적용 범위**: 입찰(`POST .../bids`)과 입찰 정책(단건·일괄). 캠페인·광고그룹·소재의 `PATCH`에는 적용하지 않는다 — 이들은 이력 행이 아니고 필드 단위로 보내서 충돌 범위가 좁으며, 값이 바뀌어도 과거 결정(Decision 스냅샷)이 보존되기 때문이다. 이 영역에서 덮어쓰기 문제가 실제로 생기면 `updated_at` 기반 `If-Match`를 추가한다.
- 근거 테스트: `test_policy_stale_expected_version_rejected`(순차), `test_concurrent_policy_saves_only_one_wins`(동시), `test_bulk_policy_is_all_or_nothing`. 검사를 일부러 끄면 동시 저장이 둘 다 성공(`['ok','ok']`)하는 것을 확인했다.

## 4.3 광고 선택: 교체 가능한 전략 [확정]

선택 알고리즘은 **이름·버전이 붙은 전략**이고 설정(`ADS_SELECTION_POLICY`)으로 고른다. **알고리즘을 바꿔도 Decision의 구조는 바뀌지 않는다.**

```python
# engine/policies/base.py (스케치)
class SelectionPolicy(Protocol):
    name: str                                   # "highest-bid/v1" → Decision에 기록
    def select(self, candidates: Sequence[Candidate],
               request: AdRequest, rng: Random) -> Selection: ...
# Selection = (chosen: Candidate | None, trace: dict)
#   trace = 알고리즘별 판단 근거. Decision에 그대로 저장
```

- 입력은 두 타입이다 **[확정]**. 둘 다 불변 값 객체이고, 금액은 **정수 포인트**, 시각은 UTC다.
  - **`Candidate`** = 판정 전 사실. `records`가 `masters`·`campaigns`·`billing`의 `api`에서 값을 모아 (광고그룹 × 소재 × 요청 슬롯)마다 하나씩 만든다.
  - **`Eligible`** = `Candidate` + `applied_amount`. `engine`이 ① 적용 금액을 계산하고 ② 자격 필터를 통과시킨 것만 `SelectionPolicy`에 넘긴다.

| 그룹 | `Candidate` 필드 | 쓰임 |
|---|---|---|
| 식별 | `campaign_id`, `ad_group_id`, `creative_id`, `slot_id` | 선택 결과 식별, Decision 기록, 응답 조립 |
| 과금 | `pricing_unit` | Decision 기록, 이후 단위 혼합 비교(V2) |
| 입찰 | `bid_amount`, `bid_version`, `bid_created_at` | 적용 금액 계산, Decision 재현, trace |
| 정책 스냅샷 | `floor`, `base`, `cap`, `policy_version` | 적용 금액 계산, 하한 필터, 이후 확률 노출 공식, Decision 재현 |
| 자격 판정용 사실 | `campaign_status`, `ad_group_enabled`, `period_start`, `period_end`, `wallet_balance`, `remaining_daily_budget` | 필터가 판정 |

- 요청 쪽 `AdRequest`는 `subject_id`, 슬롯, **`now`**(UTC)를 가진다. `engine`은 시계를 읽지 않고 `now`를 주입받는다(테스트에서 시각 고정).
- 후보에 넣지 않는 것: 이미지 URL·소재 본문(응답 조립 단계가 `creative_id`로 조회), 타겟팅 속성(V1 범위 밖, 필요할 때 필드와 필터 파일을 추가), `subject_id`(요청에 속함).
- **필터 체인(상태·기간·하한·예산·잔액)과 적용 금액 계산이 모두 `engine`** 이고, 정책 이름에 따라 달라지는 것은 `select()`뿐이다.
- `request`(`subject_id` 포함)와 `rng`는 **시그니처에 항상 있다.** V1 알고리즘은 `request`를 읽지 않고, `rng`는 동점 처리에만 쓴다. 이후 알고리즘이 시그니처를 바꾸지 않고 들어오게 하기 위함이다.

**V1~V2: `highest-bid/v1` [확정]**

1. 자격을 통과한 후보 중 **적용 금액이 가장 큰 것**을 고른다.
2. **동점이면 동점 후보 중 무작위로 하나를 고른다 [확정].** 상한을 넘는 입찰은 모두 상한이라 동점이 흔하고, 이때 상한에 닿은 광고들이 고르게 노출된다.
3. `trace`에 동점 후보 목록과 뽑은 값을 남긴다(사후 검증용). 후보가 없으면 `chosen = None`(광고 없음).

**이후 방향 [확정 방향, 공식은 미정]**: 입찰액에 따른 **확률 노출**(`weighted-by-bid/v1`). 적용 금액에 비례해 뽑고, 후보별 확률과 난수를 `trace`에 남긴다. 기준가를 어떻게 쓸지(예: 과금 단위 정규화)는 그때 정한다. **이 전환은 `engine/policies/` 새 파일 + 설정값 한 줄로 끝나야 한다.** 이것이 이번 구조의 합격선이다.

테스트: ① 판정표(최고가·동점·후보 없음·자격 제외) ② 시드 고정 시 동점 선택이 재현되고, 많이 반복하면 동점 후보가 고르게 뽑힘 ③ `subject_id`만 바꿔도 같은 입력에서 같은 결과 ④ 정책 이름만 바꿔 다른 알고리즘으로 교체되고 Decision 구조가 같음.

## 4.4 구조적 무결성 (이게 설계의 합격선)

1. Decision은 한 번 쓰면 바뀌지 않는다.
2. `Bid`·`BidPolicy`는 행을 고치지 않는다. 같은 (대상, 버전)은 유니크 제약으로 중복 저장을 막는다.
3. 모든 Reaction은 존재하는 Decision을 가리킨다. 같은 `reaction_id` 재전송은 멱등.
4. 광고주는 자기 캠페인·지갑만 본다·고친다. 소유권 검사는 한 곳에서 한다.
5. 캠페인 상태 전이 표는 한 파일에 있고, 그 밖에서 상태를 직접 쓰지 않는다.
6. 업로드 파일은 신뢰하지 않는다(§8 Step 0-5).
7. 정책의 `floor ≤ base ≤ cap`은 어떤 경로로 저장해도 깨지지 않는다.
8. **원장(`LedgerEntry`)은 추가만 한다.** 수정·삭제 없음. 정정은 반대 부호의 새 항목(`ADMIN_ADJUST`)으로 한다.
9. **지갑 잔액은 항상 원장 합계와 같다.** 어긋나면 테스트가 실패한다(정합성 점검 함수).
10. **과금은 `reaction_id`당 최대 1번**이다(유니크 제약). 과금액은 Decision에 기록된 적용 금액이며 다시 계산하지 않는다.
11. 잔액은 0 밑으로 내려가지 않는다(§4.7).
12. **수신 확인(2xx)은 영속 저장 뒤에만 보낸다.** 결정(Decision)도 저장이 끝난 뒤에 `decision_id`를 응답한다.
13. **수신한 반응은 어떤 경우에도 지워지지 않는다.** 거부된 반응도 사유와 함께 상태(`REJECTED`)로 남는다.
14. **`ENDED` 캠페인과 그 하위(광고그룹·소재·입찰)는 바뀌지 않는다.** 종료 판정은 저장된 상태가 아니라 기간(`ends_at ≤ now`)으로 한다(§4.5).

## 4.5 캠페인 상태 [확정: 승인 단계 없음]

관리자 승인 없이 생성 즉시 집행한다. 문제가 있는 광고는 관리자가 사후에 **중단**한다.

| 상태 | 설명 | 누가 바꾸나 |
|---|---|---|
| `ACTIVE` | 기간 내면 노출 후보 | 생성 시 자동, 광고주(재개) |
| `PAUSED` | 광고주가 끔 | 광고주 |
| `SUSPENDED` | **관리자 중단.** 사유 기록. 광고주는 해제 불가·사유는 열람 | 관리자(중단·해제) |
| `ENDED` | **종료. 확정된 사실이라 어떤 값도 바뀌지 않는다.** 기간이 끝났거나 광고주가 직접 종료 | 시스템(기간 종료), 광고주(조기 종료) |

- 광고그룹은 별도로 ON/OFF만 가진다(광고주가 켜고 끈다). 관리자 중단은 캠페인 단위다.
- **예산 소진·잔액 부족은 상태가 아니라 선택 시점에 계산되는 조건**이다(§4.7). 예산을 늘리거나 충전하면 별도 조작 없이 다시 노출된다.
- **정지 중에도 광고주는 소재·입찰·기간 등을 수정할 수 있다 [확정].** 그래야 문제를 고쳐서 다시 집행할 수 있다. 단 `status`는 바꿀 수 없다.
- **`ENDED`는 끝이다 [확정].** 어떤 필드도 수정할 수 없고(409 `ended`), 소속 광고그룹·소재·입찰의 쓰기도 막힌다(읽기만). 소재 이미지는 C3 URL에서 내려간다(404). 종료 시점이 변하지 않아야 집계·정산이 정확하기 때문이다. 이어서 집행하려면 새 캠페인을 만든다(복제 기능은 이후 확장, §7-11). 쓰기 가드는 `campaigns` 서비스 한 곳에 둔다.
- **종료일(`ends_at`)은 종료 전 캠페인(`ACTIVE`·`PAUSED`·`SUSPENDED`)에서 늘리거나 줄일 수 있다 [확정].** 새 값은 현재 시각보다 뒤여야 한다(`null`은 기간 제한 없음).
- **종료 판정은 저장된 상태가 아니라 기간이다 [확정].** `ends_at ≤ now`이면 상태가 아직 갱신되기 전이라도 종료된 것으로 보고 수정을 거절한다(되살리기 방지). 판정은 `engine.api`의 순수 함수 `is_expired(ends_at, now)` 한 곳이고, 선택 필터·전환 작업·수정 가드가 같이 쓴다.
- **전환 [확정]**: 시스템 작업 `end_expired_campaigns(now)`가 `ends_at ≤ now`이고 아직 `ENDED`가 아닌 캠페인(**`ACTIVE`·`PAUSED`·`SUSPENDED` 모두**)을 `ENDED`로 바꾼다. 멱등·조건부 갱신이며 관리 명령으로 주기 실행한다(실행 방식은 §7-9와 함께). 갱신이 늦어도 `engine`의 기간 필터가 노출을 막으므로 안전하다(후보 조회는 구조적 소속만 쓰고 기간 판정은 `engine` 한 곳). 종료 직전 상태는 `ended_from`에 남기고 중단 사유는 그대로 둔다.
- **조기 종료 [확정]**: 광고주가 `POST /campaigns/{id}/end`를 호출하면 `ends_at`을 현재로 확정하고 `ENDED`로 바꾼다. **되돌릴 수 없고** 화면은 확인을 한 번 받는다. `ACTIVE`·`PAUSED`에서만 가능하다(`SUSPENDED` 중에는 광고주가 `status`를 바꿀 수 없다는 규칙을 따라 409 `suspended`).
- **재검토 요청 [제안]**: 이메일이 없어 관리자가 광고주의 수정을 알 방법이 없으므로, 광고주가 고친 뒤 **버튼으로 요청**을 만든다(메모 선택). 요청은 추가만 되는 기록(`ReviewRequest`: `OPEN` → `RELEASED` / `REJECTED` / `CLOSED_ENDED`, 관리자 답변 메모)이다. **정지 중인 캠페인에만, 동시에 하나만** 만들 수 있다. 관리자는 관리자 화면의 **재검토 대기 목록**에서 **해제**(캠페인이 `ACTIVE`로 돌아감) 또는 **반려**(정지 유지, 사유 필수)한다. 결과는 광고주 화면의 요청 내역과 알림(`/alerts`)으로 알린다. 요청 없이도 관리자는 직접 해제할 수 있다. 캠페인이 `ENDED`가 되면 `OPEN` 요청은 자동으로 `CLOSED_ENDED`로 닫히고, 종료된 캠페인의 해제는 409 `ended`다.
- 중단된 캠페인의 소재 이미지는 **C3 URL에서도 내려간다**(404).
- 승인 없이 곧바로 공개되므로 §5의 남용 방지(가입 제한·소재 수/용량 상한)와 §8 Step 0-5(업로드 보안)가 더 중요하다.

## 4.6 광고그룹과 게재 위치 [확정 방향: 위치별 금액·방식이 다르므로 그룹화 필요]

네이버처럼 **캠페인 → 광고그룹 → 소재** 구조로 한다. 게재 위치(슬롯)가 여러 곳이고 위치마다 금액·방식이 다르므로, 위치 선택과 입찰을 묶는 단위가 필요하다.

| 단위 | 담는 것 |
|---|---|
| **Campaign** | 이름, 기간, **일예산**, 상태와 종료 직전 상태 `ended_from`(§4.5). 광고주가 성과를 묶어 보는 단위 |
| **AdGroup** | 이름, **게재 위치(슬롯) 1개 이상**, 과금 단위(생성 시 고정), 입찰(버전), ON/OFF |
| **Creative** | 이미지, 제목, 이동 주소. 광고그룹 소속. V1은 광고그룹당 1개 [확정: V1 한정, 이후 늘릴 수 있음] |

- 광고그룹이 고른 **모든 슬롯은 광고그룹의 과금 단위와 같은 단위**여야 한다(하나의 입찰 금액이 같은 의미여야 하므로). 화면은 광고그룹의 과금 단위를 고르면 해당 단위의 슬롯만 보여준다.
- 슬롯마다 정책이 다르므로 같은 광고그룹도 **슬롯별로 적용 금액과 노출 자격이 다르다.** 예: 입찰 30 → 슬롯 A(범위 10~50)는 30, 슬롯 B(범위 10~20)는 20(상한), 슬롯 C(범위 40~100)는 제외.
- 슬롯 S에 대한 광고 요청의 후보 = **S를 게재 위치로 가진 광고그룹들**(+ 소재, 캠페인 조건 통과).
- **그룹화 [제안: 권장안, 이견 시 변경]**: 게재 위치는 매체(플랫폼)에 속하므로 **이미 매체 단위로 묶여 있다.** 광고그룹은 여러 슬롯(다른 매체의 슬롯 포함)을 고를 수 있어서, **플랫폼이 늘어나면 매체와 슬롯만 등록하면 된다.** 광고주 화면의 위치 선택은 매체별로 묶어 보여준다. 슬롯이 많아져 정책을 하나씩 넣기 번거로워지면 관리자 화면에 **"선택한 슬롯들에 같은 값으로 새 버전 입력" 일괄 동작**을 둔다(정책 버전은 그대로 슬롯마다 따로 쌓인다). 별도 `SlotGroup` 모델은 두지 않고, 필요해지면 `masters`에 추가한다(영향 범위: `masters`와 관리자 화면).

## 4.7 예산·포인트·과금 [확정: 구현한다. 세부는 제안]

의미가 없더라도 **예산과 포인트는 구현한다 [확정].** 실제 돈은 오가지 않고, **포인트는 광고 서버 안에서만 쓰는 단위**다.

**지갑과 원장**

- 광고주마다 지갑이 하나 있다. **잔액은 원장(`LedgerEntry`)의 합계**다. 항목 종류는 `SIGNUP_GRANT`(가입 지급) / `CHARGE`(반응 과금) / `ADMIN_ADJUST`(관리자 조정·환불) / `TOPUP`(예약, C5).
- **가입하면 설정값(`SIGNUP_GRANT_POINTS`)만큼 지급한다 [확정].** 가입과 지급은 같은 트랜잭션이다. 가입 흐름은 `console`이 `foundation`(계정 생성)과 `billing`(지급)을 차례로 호출한다.
- 이후 메타버스에서 얻은 포인트를 충전하는 연계(C5)를 고려한다 [확정 방향]. 원장에 `TOPUP` 항목을 추가하는 것으로만 반영한다.

**예산**

- 캠페인에 **일예산**을 둔다. 그날 과금 합계가 일예산에 도달하면 후보에서 제외된다. 일예산은 필수인지, 총예산도 둘지는 **[열림 §7-1]**. 지갑 잔액이 사실상 총량 한도 역할을 한다.
- **"그날"의 경계는 열어 둔다 [열림 §7-1].** 기본은 UTC 자정이다(KST 09:00 리셋). 안전하게 열어 두려고 ① 경계 계산을 **함수 하나·설정값 하나**(`BUDGET_DAY_OFFSET_HOURS`, 기본 0)에 모으고 ② 일 소진액을 **원장에서 다시 계산할 수 있는 파생값**으로 두며(재계산 명령 제공) ③ 화면의 리셋 시각 표시도 같은 함수에서 만든다. 나중에 KST 자정(+9)으로 바꾸려면 설정값을 바꾸고 재계산하면 된다.

**과금**

- 과금은 **반응 유형이 광고그룹의 과금 단위와 같을 때만** 발생한다(노출 단위면 `IMPRESSION` 반응마다, 클릭 단위면 `CLICK` 반응마다). 다른 유형의 반응은 기록만 하고 과금하지 않는다.
- 과금액 = **그 반응의 Decision에 기록된 적용 금액.** 결정 이후 입찰·정책이 바뀌어도 그 반응의 과금액은 변하지 않는다.
- 과금 여부와 금액을 정하는 규칙은 **교체 가능한 `ChargePolicy`** 로 둔다(기본 `by-unit/v1`: 위 규칙). 어떤 정책으로 과금했는지 원장 항목에 이름을 남긴다(R8).
- 같은 트랜잭션에서 ① 원장 `CHARGE` 항목 추가 ② 지갑 잔액 갱신 ③ 캠페인의 그날 소진액 갱신을 함께 한다.

**후보 자격에 추가되는 조건 (선택 시점)**

- 지갑 잔액 ≥ 적용 금액, 캠페인의 오늘 남은 예산 ≥ 적용 금액. 이 값들은 `Candidate`의 `wallet_balance`·`remaining_daily_budget`으로 **숫자로 전달**되고 `engine`의 필터가 `applied_amount`와 비교해 판정한다(`engine`은 DB를 모른다).
- 결정과 과금 사이에 **시차**가 있으므로(특히 클릭·전환 단위는 결정 한참 뒤에 과금) 잔액·예산을 **약간 넘는 과금이 생길 수 있다.** 과금은 **남은 잔액만큼만 차감**하고 잔액을 0 밑으로 내리지 않는다. 부족분은 원장에 표시한다 **[확정]**. 일예산은 소프트 한도(약간 넘을 수 있음)다.

**반응 처리와 유효성 규칙 [확정: 수용, 세부는 바뀔 수 있음]** — 반응이 곧 과금이므로 수신한 반응은 **규칙 체인**을 거친다. 규칙은 하나씩 독립된 파일이고, 어떤 규칙을 어떤 순서로 쓸지는 설정으로 정한다(R8). 처리 결과(`ACCEPTED`/`REJECTED`+사유)와 적용한 규칙 이름은 반응에 기록된다.

| 규칙 | 내용 | 기본 |
|---|---|---|
| `known-decision` | 존재하는 Decision을 가리켜야 한다 | 적용 |
| `same-media` | 보고한 매체(인증된 키)가 **그 Decision을 만든 매체**와 같아야 한다 | 적용 |
| `once-per-type` | **Decision당 반응 유형별 1번**만 인정한다 | 적용 |
| `report-window` | Decision 이후 일정 시간 안에 보고해야 한다 | **미적용.** 매체가 감지 즉시 보고하므로 의미가 없다 [확정]. 필요해지면 파일 하나와 설정 한 줄로 켠다 |

`reaction_id` 멱등(같은 ID 재전송은 처음 결과를 그대로 돌려주고 중복 처리하지 않음)은 규칙이 아니라 **수신 단계의 기본 동작**이다(§6.5).

# 5. 계정과 화면

## 5.1 계정 [확정: 이대로 진행]

- 사용자 모델 하나에 역할 두 개(`admin`, `advertiser`). URL을 `/admin-console/`, `/advertiser/`로 나누고 서로의 화면에 못 들어간다.
- 관리자 계정은 **가입 화면이 없다.** 서버 명령으로만 만든다. 가입 폼은 역할 필드를 받지 않는다.
- **광고주는 회원가입한다 [확정].** 받는 항목은 **아이디, 비밀번호, 닉네임, 반** 뿐이다. 실제 돈이 오가는 광고가 아니므로 이메일·전화·실명은 받지 않는다. 가입하면 **포인트가 지급된다**(§4.7).
  - 아이디 `[a-z0-9_]{4,20}`, 닉네임 길이 제한, 반은 자유 입력 짧은 문자열(표시용, 로직에 쓰지 않음, 매체의 강의실 개념과 연결하지 않음) **[제안, 열림 §7-4]**
  - **이메일이 없으므로 비밀번호 찾기는 관리자 초기화**로 한다 [제안].
  - 공개 가입 + 무승인 집행 + 가입 지급이라 **남용 방지**를 둔다 [제안]: 가입 시도 IP 제한, 광고주당 캠페인·광고그룹·소재 수와 업로드 총량 상한(설정값), 관리자의 계정 비활성화. **여러 계정으로 지급 포인트를 모으는 행위**는 이후 메타버스 포인트가 연계되면 문제가 되므로 그때 재검토 **[열림 §7-2]**.
  - **소재 이동 주소(`redirect_url`)는 피싱에 쓰일 수 있다.** **`https`만 허용**, 길이 제한, 관리자 모니터링 화면에 도메인을 눈에 띄게 표시한다 **[확정: 추천안 진행]**.
- **로그인 시도 제한 [확정]: 5회 실패 시 5분 잠금.** 잠금 기준은 (아이디+IP) 조합 [제안: 아이디만 기준이면 남이 계정을 잠가버릴 수 있다].
- 관리자 2단계 인증은 제외, 이후 필요 시 [확정].

## 6.1 모듈

`foundation`은 저장소 루트의 `platform/`(인프라 Ansible)과 이름이 겹치지 않게 지은 이름이다.

apps/ads_server/                     (승격 후 위치. 문서는 docs/ads-server/)

  serving_api/     C1 구현. 요청 검증·인증·응답 변환만

```

## 6.2 변경 내성 규칙 (구조가 흔들려도 범위가 커지지 않게)

| # | 규칙 | 막는 것 |
|---|---|---|
| R1 | **계층 + 아래 방향 import만.** 같은 층끼리는 서로 모른다 | 순환 의존, 연쇄 수정 |
| R2 | **모듈 밖에서는 `<모듈>.api`만 import한다.** 내부 파일 이름은 자유롭게 바꾼다 | 내부 리팩터링이 사방으로 번지는 것 |
| R3 | **Django 앱 `label`과 DB 테이블명(`db_table`)을 고정**한다. 앱 사이 FK는 `"campaigns.Campaign"` 같은 라벨 문자열로 쓴다 | 폴더·패키지를 옮길 때 마이그레이션과 테이블이 깨지는 것 |
| R4 | **구현 선택은 `config/` 한 곳**에서 한다(저장소 구현·EventSink·선택 전략·URL 마운트) | 설정이 코드에 흩어지는 것 |
| R5 | **외부 URL은 모듈 이름과 무관**하다. 경로는 `config/urls.py`에서만 정한다 | 폴더 이동이 계약을 깨는 것 |
| R6 | R1·R2·`engine` 순수성은 **테스트로 강제**한다(`tests/boundaries/`). 층 정의는 그 파일의 딕셔너리 하나 | 규칙이 문서로만 존재하다 무너지는 것 |

**계층 (위 → 아래로만 의존)**

```
L4  serving_api   console            (바깥과의 접점. 서로 모른다)
L3  records                          (결정·반응 유스케이스. campaigns·billing·masters·engine·events를 api로 조합)
L2  campaigns   billing              (서로 모른다. billing은 캠페인을 ID로만 안다)
L1  masters   engine   assets   events     (서로 모른다)
L0  foundation

- `engine`은 어떤 프로젝트 모듈도 import하지 않는다(순수 데이터만 받는다).
- `billing`은 `campaigns`를 import하지 않고 캠페인을 ID 값으로만 다룬다. 예산 한도는 `records`가 두 모듈에서 읽어 `Candidate`에 숫자로 담는다.
- `masters`·`campaigns`·`billing`·`records`가 분리된 앱인 이유는 R7이다. **모델을 다른 앱으로 옮기는 것이 Django에서 가장 비싼 이동**이라, 처음부터 소유 주체 선으로 나눠 두면 이후에 쪼갤 일이 줄어든다.
- 인터페이스(추상 클래스)는 **구현이 실제로 갈아끼워지는 곳**에만 둔다: `SelectionPolicy`(최고가 → 확률 노출), `AssetStorage`(로컬 → 객체 저장소), `EventSink`(JSONL → Kafka). DB 교체는 Django 설정이 맡는다.

## 6.3 이벤트와 outbox [제안]

결정·반응·과금이 저장되는 **같은 트랜잭션**에서 outbox 행을 함께 쓴다(저장과 발행이 어긋나지 않게). 중계(relay)가 outbox를 읽어 `EventSink`로 보낸다. Step 4는 JSONL sink, Step 5는 Kafka sink와 relay 실행 방식만 추가한다.

## 6.4 타겟팅 확장 지점 [확정 방향: V1은 구현하지 않고, 이후 추가가 쉬워야 한다]

이후 맞춤 광고로 확장될 때 **기존 코드를 고치지 않고 얹을 수 있게** 아래 자리만 확보한다. 지금은 모델 필드도 만들지 않는다.

| 필요한 것 | 들어갈 자리 | 지금 확보해 둔 것 |
|---|---|---|
| 타겟 조건을 담는 곳 | `campaigns`의 광고그룹 하위 모델(예: `AdGroupTarget`). 네이버도 광고그룹에 둔다 | 광고그룹이라는 단위 자체 |
| 후보를 걸러내는 로직 | `engine/filters/targeting.py` 새 파일. 필터 목록은 설정으로 구성 | 필터 체인 구조, `Candidate`가 광고그룹 ID를 가짐 |
| 대상 정보 | `request.subject_id` + C4로 들어온 대상 신호 저장소. `records`가 조회해 `request`에 실어 `engine`에 전달 | `subject_id` 수집, `request`가 선택 시그니처에 있음, C4 계약 자리 |
| 결과 기록 | `Decision.trace`에 필터 근거 추가 | `trace`가 알고리즘 중립 구조 |

## 6.5 동시성과 유실 방지 [확정 요구: 동시 사용자 최대 150명, 수신한 반응은 유실 0]

동시에 노출되면 반응 보고 최대 150건이 한꺼번에 들어온다(광고 요청도 마찬가지). **한 건도 유실되면 안 되고, 두 번 과금되어도 안 된다.** V1 저장소인 SQLite는 쓰기가 한 번에 하나씩이므로 아래 원칙으로 설계한다.

1. **저장 후 확인.** 반응도 결정도 디스크에 커밋한 뒤에만 2xx(또는 `decision_id`)를 보낸다(§4.4-12).
2. **수신과 처리를 분리한다(inbox).** 수신은 **짧은 INSERT 하나**다. 원문(JSON 그대로)·(`매체`, `reaction_id`) 유니크·상태 `RECEIVED`·수신 시각(+ 이벤트 outbox 행)을 한 트랜잭션에 쓴다. 과금·잔액·소진액 같은 무거운 갱신은 **별도 트랜잭션의 처리 단계**가 한다. 처리가 실패해도 수신된 반응은 `RECEIVED`로 남는다.
3. **처리는 재시도 가능하고 멱등하다.** 처리 단계는 `RECEIVED`인 반응을 집어 규칙 체인과 과금 정책을 적용하고 `ACCEPTED`/`REJECTED`로 바꾼다. 수신 직후 한 번 시도하고, 못 끝낸 것은 주기적 재처리 명령(`process_reactions`)이 이어서 처리한다. 같은 반응을 몇 번 처리해도 과금은 한 번이다(`reaction_id` 유니크). **최소 한 번 전달 + 멱등 처리 = 유실도 이중 과금도 없다.**
4. **원문을 보존한다.** 수신한 JSON 그대로를 저장하므로 규칙·정책이 바뀌어도 다시 처리할 수 있고, Step 4의 Raw 수집이 곧 이 원문이다.
5. **받지 못할 땐 503.** DB가 바빠 수신하지 못하면 확인을 보내지 않고 503을 준다. 매체가 같은 `reaction_id`로 재시도한다(C1 규칙 3·5).
6. **SQLite 설정**: WAL 모드, **`synchronous=FULL`**(커밋이 디스크에 내려간 뒤에 확인해야 "저장 후 확인"이 성립한다. `NORMAL`이면 정전·OS 장애 때 마지막 커밋을 잃을 수 있다), `busy_timeout`(수 초), 쓰기 트랜잭션은 즉시 시작(`IMMEDIATE`), 짧은 트랜잭션, 워커 수는 적게(Step 0-1).
7. **한계를 명시한다.** SQLite는 쓰기가 직렬이라 초당 수백 건 수준이 한계다. 150명 규모에는 충분하지만, 넘으면 MySQL 전환(S단계)이나 큐 도입이 필요하다. 전환은 `records`·`billing`의 저장 구현과 설정에 한정된다(R3·R4).
8. **증거는 부하 테스트다.** 150개 동시 반응·150개 동시 결정을 보내 ① 수신 확인한 건이 전부 저장됐고 ② 유실이 0이며 ③ 이중 과금이 0이고 ④ 잔액이 원장 합계와 같음을 확인한다(Step 2-6).

## 6.6 콘솔 분리 대비 [확정: V1은 Django 하나(템플릿)로, 이후 분리할 수 있게]

V1의 관리자·광고주 콘솔은 **Django 하나에서 템플릿으로** 만든다 [확정]. 이후 프론트를 별도 앱으로 분리할 수 있도록 지금부터 아래 규칙을 지킨다. 분리는 "뷰·템플릿을 JSON 직렬화로 바꾸는 일"이 되어야 한다.

**지금 지키는 규칙**

1. **콘솔 뷰에는 비즈니스 규칙이 없다.** 입력 검증·소유권 검사·상태 전이·금액 계산은 아래 모듈의 `api`(서비스)에 둔다. 뷰는 "서비스 호출 → 결과 렌더"만 한다(R2의 연장).
2. **오류는 도메인 예외로 던지고**, 화면(또는 이후 JSON)으로의 변환은 콘솔 가장자리 **한 곳**에서만 한다.
3. **폼은 입력 변환만 한다.** 규칙 판단은 서비스가 하고, 같은 규칙을 폼과 서비스에 두 번 쓰지 않는다.
4. 서비스가 돌려주는 값은 **화면 전용 가공 없이 직렬화할 수 있는 데이터 구조**로 한다. ORM 객체를 템플릿에 그대로 흘리지 않는다. [제안]
5. 관리자 화면은 Django admin이라 분리 대상이 아니다(서버 렌더 유지).

**분리하게 되면 (이후)**

- 이미 초안이 있는 **C6 콘솔 API**([contracts/console.openapi.yaml](contracts/console.openapi.yaml))를 구현하고, `console/`을 템플릿 렌더에서 JSON 응답으로 바꾼다. C6의 규칙(입찰 추가만, `expected_version`, 정지 중 제한, 쿼터 등)은 V1부터 서비스가 지키므로 화면만 바뀐다.
- 배포는 리버스 프록시로 **같은 출처**를 유지한다(`/`=프론트, `/api/`=Django). 그러면 세션 쿠키와 CSRF를 거의 그대로 쓰고 CORS가 필요 없다. 토큰 방식은 다른 도메인으로 갈 때만 검토한다.

| 다시 점검할 것 | 내용 |
|---|---|
| 인증 방식 | 세션 쿠키 유지 여부(같은 출처면 유지) |
| CSRF | 프론트가 토큰을 받아 요청에 싣는 방식 |
| CORS | 같은 출처면 불필요, 다른 도메인이면 허용 목록 |
| CSP | 프론트가 쓰는 스크립트·이미지 출처 |
| 오류 응답 | 화면 대신 JSON 오류 형식(변환은 규칙 2의 한 곳) |
| 업로드 | 이미지 업로드를 API로 받는 경로의 크기·형식 검증(서버 규칙은 그대로) |

**안 바뀌는 것**: Step 0의 서버 쪽 규칙(설정·비밀값, 로그인 잠금, 역할·소유권 검사, 업로드 검증, 보안 헤더, 감사 로그)과 도메인 전부.

| 데이터 문서 우선순위 | 광고 도메인 데이터는 **광고 서버 DRD(`intake/ads-server-drd.md`)가 팀 DRD보다 우선**. 팀 DRD의 광고 영역은 가정 기반 Draft라 광고 서버 DRD에 맞춰 고친다 [확정, 2026-10-07] |
| 매체 키 | 형식 `<key_id 32자 16진>.<token_urlsafe(32)>`. `key_id`로 행을 찾고 비밀의 **SHA-256**을 상수시간 비교(비밀이 256비트 무작위라 느린 해시가 필요 없다). 평문은 저장·로그·감사에 남기지 않고 발급·교체 때 **한 번만** 보인다. 매체마다 여러 키가 동시에 유효할 수 있고, **교체는 새 키 발급 + 기존 키를 유예 뒤 만료**(0~30일, 기본 24시간), 유출은 즉시 폐기. 비활성 매체의 유효한 키는 403, 그 밖의 모든 실패(없음·형식 오류·모르는 키·틀린 비밀·폐기·만료)는 구분 없이 401 [확정, 2-2] |
| 요청 제한 구현 | (매체 UUID, 경로군) 토큰 버킷, **프로세스 메모리**. 워커 N개면 한도가 최대 N배 느슨해진다는 한계를 코드와 위협 모델에 명시하고, 2-6 부하 측정 뒤 공유 저장소(DB·캐시) 전환 여부를 정한다 [확정: 초기 구현, 2-2] |
| 응답 규칙(C1) | 키 없음·무효 401 → **유효한 키지만 매체 비활성 403** → 활성 매체의 **비활성 슬롯 201 + `ad: null`**(결정 기록) → **없는·다른 매체의 슬롯 404**(구분해 알리지 않음, 결정 없음). 계획 2-2의 403과 2-3의 201이 충돌하던 것을 이렇게 통일. **인증이 필요한 모든 엔드포인트(조회 포함)가 401·403·429·503을 같은 방식으로 선언**하고, 401은 `WWW-Authenticate: MediaKey realm="ads-media-api"`를 항상 보낸다(`X-Media-Key` 방식의 challenge 스킴). Problem 본문의 `status`는 HTTP 상태와 같아야 한다(RFC 9457 §3.1.2) [확정, 2-1] |
| 요청 제한 | 매체(UUID)별·경로군별 토큰 버킷. **결정 150/초·버스트 300, 반응 450/초·버스트 600, 조회 150/초·버스트 300**, 초과 시 429 + `Retry-After`, 키 교체 후에도 같은 버킷. **150명 가정의 개발용 초기값이며 측정 결과가 아니다**(2-6에서 조정) [확정: 초기값, 2-1] |
| 소재 `title` | 1~200자 [확정, 2-1] |
| 전환(`CONVERSION`) | 매체가 **사전에 정의한 목표 완료**를 보고. 광고 서버는 의미를 해석하지 않고 결정 존재·매체 일치·결정당 유형별 1회·결정의 과금 단위로만 판정 [확정, 2-1] |
| 반응 처리 실행 | 접수(2xx) = inbox 저장 완료이며 뒤의 처리 실패가 접수를 뒤집지 않는다. 처리는 inbox 커밋 뒤 별도 트랜잭션으로 한 번 시도, 남은 `RECEIVED`는 **단일 관리 프로세스가 1초 주기·배치 100**으로 재처리. 재시작·중복·자정 이후 재처리에서도 원래 `received_at`과 과금 멱등 키를 유지 [확정: 초기값, 2-1] |
| C3 이미지 공유 | 같은 내용의 파일은 같은 주소다. 중단·종료된 캠페인의 이미지는 **같은 파일을 보유한 다른 활성 캠페인이 없으면** 404 [확정, 2-1] |
| 이미지 보유 관계 | 소재의 이미지를 교체해도 이전 파일은 지우지 않으므로(과거 결정이 URL을 참조), **`CreativeImage`(소재가 지금까지 보유한 파일)** 를 저장하고 이 관계로 ① 광고주별 **보유 총량 쿼터**(같은 파일은 한 번만 셈) ② **서빙 가능 여부**(교체 후에도 캠페인이 `ACTIVE`·`PAUSED`인 동안 과거 이미지도 열림, 중단·종료되면 전부 404)를 판단한다. 보유량은 파일을 삭제하는 정책(보존 기간, §7-8)이 생기기 전까지 줄지 않는다 [확정, Step 1 보완 2026-10-07] |
| 잔액·금액 범위 | 개별 금액 검사와 별개로 **합산 결과(잔액)도 0 이상 `MAX_AMOUNT`(2^53−1) 이하**여야 한다(서비스 검사 + DB `CHECK`). 과금 입력과 과금 정책의 반환값은 `bool`을 제외한 정수·허용 범위여야 하고, 아니면 원장·잔액·소진액 모두 무변경 [확정, Step 1 보완 2026-10-07] |
| 동시 수정 보호 | **낙관적 잠금**: 입찰·입찰 정책은 `expected_version`이 현재와 다르면 409 `stale_version`. 비관적 잠금·마지막 저장 승리·자동 병합은 채택하지 않음(근거 §4.2). 캠페인·광고그룹·소재 `PATCH`는 V1에서 적용하지 않음 [확정] |
| 광고주 한도 기본값 | 캠페인 20·광고그룹 100·소재 100·이미지 총량 100MB·광고그룹당 소재 1(V1). **모두 설정값의 기본**(`MAX_*`)이며 시연 규모에 맞게 바꿀 수 있다. CAPTCHA 도입 여부는 §7-5에서 계속 열려 있음 [구현: Step 1-2] |
| 예산 일 경계 구현 | `BUDGET_DAY_OFFSET_HOURS`(기본 0 = UTC 자정) 한 곳, 소진액은 원장에서 `recompute_spend`로 다시 계산 가능, 정합성은 `check_ledger` [구현: Step 1-3, §7-1은 경계 값 결정까지 열림] |
| 종료 판정의 DB 조건식 | 종료 판정의 원본은 `engine.is_expired` 한 곳이다. 쿼리로 다시 써야 하는 곳(`expire_due`·`is_asset_servable`)은 경계에서 일치함을 테스트로 대조한다 [구현: Step 1-2] |
| 후보 타입 | **`Candidate`(판정 전 사실) → `Eligible`(+적용 금액)** 두 타입. 필드 목록은 §4.3 [확정] |
| 적용 금액·하한 판정의 책임 | **`engine` 순수 함수 한 곳.** `campaigns`·`masters`는 값만 공급하고, 콘솔의 `effects`·`bid-preview`도 `engine.api`를 호출 [확정] |
| 금액 타입 | **정수 포인트**(하한·기준가·상한·입찰·적용 금액·잔액·예산). 나눗셈은 이후 알고리즘 안에서만 [확정] |
| 시각 주입 | `engine`은 시계를 읽지 않고 `AdRequest.now`(UTC)를 받는다 [확정] |

# 11. 이전 설계에서 가져오는 것 / 버리는 것

| 가져온다 | 버린다 |
|---|---|
| 입찰 버전 행 추가 방식, 결정 스냅샷 불변 | 교안 호환용 경로·필드·별명 |
| 후보 조회를 한 번의 질의로(N+1 제거) | 선택 로직이 서비스 안에 박힌 구조(교체 불가) |
| 최고가 선택(`highest-bid/v1`)을 V1로, 단 **교체 가능한 전략**으로 | 한 앱에 다섯 계층을 모두 넣는 구조 |
| 인증을 입력 검증보다 먼저 | 매체 슬롯·게임 ID를 코드 상수로 두기 |
| 의존 규칙을 테스트로 강제 | DRD 필드명을 내부 모델에 그대로 쓰기 |
| 후보·입찰 버전을 결정에 남기는 방식 | 과금·정산을 범위 밖으로 두기(이번엔 포인트 과금까지 포함) |
