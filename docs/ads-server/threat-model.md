# 3. 신뢰 경계

```
[학습자 브라우저] ──(이미지 URL C3, 클릭 /c/)──▶ ┐
[광고주 브라우저] ──(콘솔, 세션)──────────────▶ │  nginx      ──HTTP──▶  광고 서버(Django, 127.0.0.1) ──▶ MySQL 8.4(업무 데이터 + outbox) / 로컬 파일
[관리자 브라우저] ──(Django admin)───────────▶ │  (TLS·HSTS·                 └ 중계 ──▶ MongoDB ad_events ◀──(읽기) 데이터 파이프라인
[매체 서버]      ──(C1, X-Media-Key)──────────▶ ┘   허용 목록)
                       (모두 HTTPS)
```

- 광고주가 입력한 값은 **광고 서버를 거쳐 학습자의 화면**(매체가 렌더)에 도달한다. 이 경로가 §5의 핵심이다.
- 매체 서버는 신뢰하되 **검증한다**(키 인증, 소유 확인, 멱등, 규칙 체인).
- **앞단 nginx**(6-5d, 설계 §10 "배포 구성"): TLS·80→443·HSTS와 접속 허용 목록(강의실 라우터·메타버스 서버)을 맡고 요청을 같은 호스트의 Django로 HTTP로 넘긴다. Django는 nginx가 붙인 `X-Forwarded-For`의 오른쪽 1번째 값을 클라이언트 IP로 쓰고(T6), 포트는 nginx 밖에 열지 않는다. HTTPS·접속 통제가 nginx 설정에 달렸다는 점은 §6 잔여 위험이다.
- 데이터 파이프라인과의 경계는 MongoDB `ad_events` 컬렉션과 이벤트 스키마다(Step 4). 파이프라인은 MySQL을 읽지 않고, 요청 경로는 MongoDB에 연결하지 않는다(중계만 쓴다).

# 5. 두 개의 핵심 경로

## 5.1 광고주가 입력한 값이 학습자에게 닿는 경로 (무승인 공개 집행)

관리자 승인이 없으므로, 광고주가 만든 소재가 **즉시** 학습자 화면에 나간다. 막을 것과 막지 못하는 것을 구분한다.

| 입력 | 위험 | 대응 | 남는 위험 |
|---|---|---|---|
| 이미지 | 부적절한 이미지, 위장 파일, 개인 정보 | 형식·재인코딩(T15~T18), **사후 중단**과 이미지 404(T19) | **내용의 부적절함은 사후에만 잡는다.** 관리자가 보기 전까지 노출될 수 있다 |
| 제목 | XSS, 사칭·욕설 | 길이 제한, 이스케이프 계약, CSP | 내용 검열은 하지 않는다 |
| 이동 주소 | **피싱·악성 사이트** | `https`만(`javascript:`·`http:`·사용자 정보가 든 주소·공백·2048자 초과 거부, 테스트 `test_creative_image_validated_and_urls_https_only`), 관리자 모니터링에 **도메인 표시**, 중단 | **도메인 평판은 확인하지 않는다.** 정상 `https` 사이트로 위장한 피싱은 사후 신고·모니터링으로만 잡는다 |
| 업로드 총량·개수 | 저장소 소진 | 광고주당 캠페인·광고그룹·소재 개수와 이미지 총량 상한(`test_quota_limits`). 소재 개수는 보관하지 않은 것만 세고, 이미지 총량은 보관한 소재까지 센다 — 보관과 올리기를 반복해도 저장은 상한에서 멈춘다(6-9c, `test_archiving_frees_the_count_but_not_the_image_quota`). 광고그룹당 소재 수 상한은 6-9c에서 없앴다(광고주당 상한이 묶는다) | |

**운영 대응**: 관리자 모니터링 화면에서 최근 등록·변경된 소재의 **썸네일과 이동 주소 도메인**을 한눈에 보고, 문제 시 **즉시 중단**(이미지는 404). 광고주는 고친 뒤 **재검토 요청**을 낸다. 가입 지급 포인트가 있어 공개 가입 계정이 쉽게 늘 수 있으므로 계정 비활성화 수단을 둔다.

## 5.2 반응 위조·중복으로 포인트가 오가는 경로

반응(노출·클릭·전환)이 **곧 포인트 차감**이다. 틀린 반응이 광고주의 잔액을 깎거나 통계를 부풀린다.

| 위협 | 대응 | 단계 |
|---|---|---|
| 매체 키 유출 후 위조 요청 | 키는 평문을 저장하지 않고(`<key_id>.<256비트 비밀>` 중 비밀의 SHA-256만) 발급 때 한 번만 보임, 상수시간 비교(없는 키도 같은 비교), 즉시 폐기·유예 교체(두 키 동시 유효), 매체별 요청 제한, 거절 로그에는 공개 식별자만. 테스트: `test_issued_key_is_shown_once_and_only_its_hash_is_stored`, `test_comparison_is_constant_time_even_for_unknown_keys`, `test_rotation_keeps_both_keys_valid_during_the_grace_period`, `test_revoked_and_expired_keys_are_rejected`, `test_missing_or_invalid_key_is_401_with_challenge_and_identical_bodies`, `test_rejected_key_log_has_the_public_id_but_never_the_secret`, `test_burst_then_429_with_retry_after_and_refill`, `test_rotating_the_key_keeps_the_same_bucket` | 2-2 |
| 다른 매체의 `decision_id`로 보고 | 규칙 `same-media` | 2 |
| 멈췄던 매체가 다시 켜진 뒤 그 전 결정으로 보고 | 규칙 `media-period`(필수 조건, 비활성화 기록 `masters_media_deactivation`, T45), 비활성화 커밋 전의 판정·결정은 매체 생명주기 잠금(T45 ⑥) | 6-1, 6-2 |
| 같은 반응 재전송(네트워크 재시도) | 멱등: (매체, `reaction_id`) 유니크 → 한 번만 처리·과금 | 2 |
| 같은 결정에 노출을 여러 번 보고 | 규칙 `once-per-type` | 2 |
| 존재하지 않는 결정에 보고 | 규칙 `known-decision`, 접수는 하되 `REJECTED`로 보존 | 2 |
| 접수 후 유실 | 커밋한 뒤에 수신 확인(2xx), 커밋마다 디스크에 내리는 MySQL 설정(`innodb_flush_log_at_trx_commit=1`·`sync_binlog=1`, `test_commit_is_durable_on_this_server`), inbox 분리, 재처리. 장애 시험의 강제 종료(SIGKILL)에서 수신 확인한 결정·반응 전부 생존([load-test.md](load-test.md) §7, 단일 노드 — 강제 failover의 유실 범위는 잔여 위험). Step 2까지는 SQLite `synchronous=FULL` | 0-1, 2, DB-1 |
| 처리 중 장애로 이중 과금 | 과금은 `reaction_id`당 최대 1번(유니크), 별도 트랜잭션. 테스트: `test_charge_idempotent_by_reaction_ref`, `test_charge_concurrent_same_ref_once`, 제약 `test_ledger_db_constraints` | 1-3, 2 |
| 원장 변조 | 추가 전용(수정·삭제·같은 PK 덮어쓰기·upsert 불가), 잔액=원장 합계 점검. 테스트: `test_ledger_is_append_only_and_cannot_be_overwritten`, `test_check_ledger_detects_tampering`, `test_balance_equals_ledger_sum_after_any_sequence` | 1-3 |
| 결정 이후 입찰·정책(비율 포함)이 바뀌어 과금액이 달라짐 | 과금액은 Decision에 기록된 적용 금액 × Decision에 남긴 그 유형의 비율(6-10c)(`test_decision_snapshot_survives_edits`, `test_decision_records_both_versions_and_policy_name`, `test_the_amount_is_the_decisions_not_a_recomputation`) | 1-5, 2, 6-10c |

**남는 위험**: 매체 서버가 **정상 키로 거짓 반응을 보내는 경우**(예: 실제로 보여주지 않은 노출 보고)는 광고 서버가 알 수 없다. 매체와 신뢰 관계로 다룬다.

# 7. 이 표를 갱신하는 규칙

1. 새 URL·모델·파일 경로·외부 계약이 생기면 **해당 위협 행을 먼저 추가**하고 검증 테스트를 정한다.
2. 위협 행의 **검증 테스트가 통과**해야 해당 단계를 완료로 본다.
3. 사고·결함이 발견되면 이 표에 위협으로 추가하고 재발 방지 테스트를 붙인다.
