# AWS 인프라 프로젝트 요구사항과 결정 상태

- 작성일: 2026-10-07 / 갱신일: 2026-10-08 (한국 시간)
- 상태: 요구사항 정리 · 설계 확정 전
- 근거: 사용자가 제공한 기존 대화와 해당 대화에서 직접 답한 내용

이 문서는 사용자가 확인한 조건과 아직 결정하지 않은 내용을 관리한다. 노드 수와 선택한 초기 사양은 아래 결정 기록과 README를 따르며, 전체 네트워크·설정·비용을 검증한 배포 완료 문서는 아니다. 잠정안은 비교를 위한 가정으로 사용할 수 있지만, 확정 조건으로 바꾸려면 사용자 또는 팀의 확인이 필요하다.

## 1. 프로젝트 목적과 범위

직접 만든 메타버스 게임의 이벤트를 수집하고, Kafka·Spark·MongoDB 클러스터를 활용해 처리하고 원본을 보관한다. AWS 인프라 설계, 예상 비용 계산, 구성 스크립트 작성을 함께 진행한다.

- AWS 리전은 서울 리전을 사용한다.
- 서버는 EC2에 배치한다. MySQL은 EC2 3대에 직접 설치하는 클러스터로 구성한다(2026-10-08 사용자 정정).
- 최대 동시 접속 **150명**을 예상 기준으로 고려한다(2026-10-07 사용자 갱신). 기존 100명 기준을 대체하며, 실제 평균 접속자와 부하는 아직 확인되지 않았다.
- 게임은 이미 만들어졌지만 이벤트 로그는 아직 구현하지 않았다.
- 광고 서비스를 위한 별도 EC2 1대를 구성에 추가한다(2026-10-08 사용자 요청).
- 원본 데이터는 계속 유지하려는 의도가 있다. 저장 위치와 이관·삭제 정책은 추가 결정이 필요하다.

## 2. 확정된 조건과 제약

| 항목 | 사용자 답변에 따른 조건 | 적용 시 유의 사항 |
|---|---|---|
| 리전 | 서울 리전 | 비용 계산과 구성에 동일하게 적용 |
| 가용 영역 | 서로 다른 물리 AZ 2개 사용 확정 | 5개 계정의 실제 AZ ID 매핑과 노드 배치는 별도 검증 |
| 광고 서버 | 별도 EC2 1대 추가 확정 | 사양·디스크·공인 IP·광고 트래픽은 견적용 가정과 실제 요구량을 구분 |
| MySQL | EC2 3대로 클러스터 직접 구성 | 관리형 DB가 아님. InnoDB Cluster·단일 Primary·통신 스택은 설계 제안과 구분 |
| 쓰기 경로 | 로그인·계정 변경·게임 상태 변경을 포함한 모든 애플리케이션 쓰기는 Kafka 우선 경유 | DB 조회·인증 검증과 구분. Consumer 배치·상태 반영 완료 응답은 보안 그룹 설계의 제안 |
| 초기 사양 선택 | Frontend·Bastion small, MongoDB·MySQL medium, Kafka 3대·Spark Worker 2대 large | 나머지 Master·Backend·광고 3대는 기존 medium 유지 가정. 성능 측정 후 조정 |
| 계정 | AWS 계정 5개를 사용해 계정별 비용을 최대한 비슷하게 배분 | 초기 설계는 account1 4대, 나머지 계정 3대씩. 실제 잔액·계정 설정·배포 상태는 미확인 |
| 예산 성격 | 계정당 $60의 AWS 크레딧 | 현금 지출 예산과 구분 |
| 계정별 한도 | 계정별 $60을 넘으면 안 됨 | 총액만 맞추는 방식으로 계산하지 않음 |
| 최초 총 크레딧 | 5개 계정 × $60 = $300 | 현재 가용 잔액을 의미하지 않음 |
| 크레딧 만료 | 사용자 답변상 19일 이후 소멸 | 대화 맥락상 2026년 10월 19일을 가리키며, 정확한 만료 시각·조건은 미확인 |
| 정규 운영일 수 | 총 평일 5일 | 2026-10-07 사용자 갱신, 서버당 총 45시간 |
| 운영일 | 2026-10-13~19 중 13·14·15·16·19일 | 사용자가 10월 13일 시작을 확정 |
| 정규 운영 시간 | 운영일마다 09:00~18:00 | 한국 시간(Asia/Seoul), 하루 9시간 |
| 운영 시간 외 | 서버를 꺼도 됨 | 야간·주말 테스트 일정과 자동 종료 적용 여부는 별도 확인 |
| 테스트 | 지금부터 테스트하며 비용이 발생할 수 있음 | 테스트 비용도 계정별 잔액에 반영 |
| 원본 보관 의도 | 모든 원본 데이터를 넣고 계속 유지하려고 함 | MongoDB에서의 보관 기간과 장기 보관 정책은 미정 |
| 실제 AWS 적용 | 리소스 생성·변경·삭제는 사용자 승인 후 진행 | 설계·견적·스크립트 준비와 실제 적용을 구분 |

2026-10-07 추가 답변으로 기존 ‘13일’ 기간 가정을 **평일 5일·매일 09:00~18:00·총 45시간**으로 대체했다. 시작일은 추가 확인을 통해 **10월 13일로 확정**했고, 운영일은 13·14·15·16·19일이다. 가용 영역은 **2개 사용으로 확정**했다. 야간과 17·18일 주말은 EC2 정규 실행 시간에 포함하지 않는다. EBS·NAT·고정 IP를 첫날 09시부터 마지막 날 18시까지 유지하면 **153시간**이므로 EC2 실행 시간과 구분한다. 이 생성·정리 시각은 견적용 가정이며, 원본 보관과 실제 자원 삭제 방침을 확정한 것은 아니다.

## 3. 잠정안과 미정 사항

| 항목 | 현재 답변 또는 방향 | 확정이 필요한 내용 |
|---|---|---|
| 서버 실행 환경 | EC2 기반, 선택한 초기 사양은 README 참조 | 운영체제·프로그램 버전, 부하 검증, Driver·Consumer 자원 배분 |
| 광고 서버 사양·접속 | 견적은 t3.medium·OS gp3 20GB·공인 IPv4 1개를 임시 적용 | 광고 서비스 구현, 데이터·미디어 저장량, 외부 직접 접속 여부와 필요한 사양 |
| MySQL 복제 방식 | EC2 3대 클러스터는 확정. InnoDB Cluster 단일 Primary 방식을 제안 | 서버 버전, 통신 스택, Router 배치, 복구 절차와 실제 복제 트래픽 |
| Spark 장애 대응 | ZooKeeper를 사용해 장애 시 마스터를 자동으로 다시 선정하려는 방향 | 마스터 전환과 실행 중인 작업 복구 목표, 실제 구성 방식 |
| MongoDB 장애 대응 | 클러스터에서 한 대가 장애 나도 원본을 유지하려는 방향 | 복제 구성, 장애 시 쓰기·조회 요구, 데이터 유실 허용 여부 |
| Kafka 장애 대응 | 역할을 함께 실행하면 자체 복구가 가능할 것으로 생각하며, 정확히는 모른다고 답함 | Broker·Controller 구성, 데이터 복제, 장애 시 요구 동작 |
| 이벤트 수집 | 방향키를 누르고 있는 동안 계속 발생시키는 방향 | 기록 간격, 수집할 행동, 이벤트 필드·크기 |
| Kafka 보관 | 최소 하루 정도 보관할 것으로 예상 | 보관 기간과 재처리 요구 |
| Spark 집계 | ‘반마다’ 사용시간을 집계할 것으로 유추하며, 5분 단위일 수도 있음 | ‘반’의 의미, 사용시간 정의, 집계 주기, 결과 저장·표시 위치 |
| MongoDB 장기 보관 | 모든 원본을 계속 보관하려는 의도 | 장기 보관소 이관 후 MongoDB 원본 삭제 허용 여부 |
| Parquet·S3·Glacier | 저장 공간이 부족하면 활용할 생각 | 파일 변환·내보내기 절차, 보관 위치, 조회 시간 요구, 비용 부담 |

위 장애 대응 설명은 사용자의 의도와 현재 이해를 기록한 것이다. 기술적으로 검증된 설계나 장애 복구 보장으로 취급하지 않는다. Kafka 하루 보관과 Spark 5분 집계는 사용자가 ‘아마도’, ‘확정은 아님’, ‘오로지 내 유추’라고 표현한 잠정안이다.

## 4. 현재 상태와 미확인 정보

- 이벤트 로그가 아직 구현되지 않아 실제 초당 이벤트 수와 이벤트 크기는 측정되지 않았다.
- 한 계정에서 약 $3를 사용한 것으로 알고 있다는 답변이 있다. 실제 청구액·잔액은 미확인이다.
- Kafka·Spark 클러스터를 이미 구성했다는 말을 들었다는 답변이 있다. 계정, 담당자, 버전, 노드 수, 실행 상태와 설정 파일은 미확인이다.
- `C:\aws-infra`가 작업 폴더로 지정되어 있다. 기존 코드와 구성은 요구사항과 대조해 확인해야 한다.
- 이 문서를 작성하기 위해 AWS 계정이나 실제 리소스를 조회하지 않았다.

## 6. 설계·비용·스크립트 작성 기준

1. 기존 자료와 코드를 읽고 현재 구성과 부족한 정보를 정리한다.
2. 최소 비용 구성과 확장 가능한 구성을 비교하고 성능·가용성 제약을 설명한다.
3. AWS 공식 가격을 확인해 리전, 확인 날짜, 사용량 가정과 계산식을 기록한다. 스토리지·네트워크·로그 등 부대 비용을 포함한다.
4. 평일 5일·총 45시간의 운영 기간 비용을 우선 계산한다. 확정된 10월 13일 시작·19일 종료 기준의 자원 유지 시간(견적용 153시간)을 별도로 표시하고, 월 환산은 참고로 구분한다. 계정별 현재 잔액과 준비·테스트 비용도 반영한다.
5. 기존 프로젝트의 도구와 방식을 따라 구성 코드를 작성한다. 도구가 미정이면 선택 이유를 설명한다.
6. 실행 전 검증, 적용 방법과 리소스 정리 방법을 문서화한다.
7. 요구사항이 바뀌면 비용표와 코드도 갱신한다. 예산 초과 예상이나 사용자 결정이 필요한 사항을 알린다.
8. 정보가 없으면 임의로 확정하지 않고 계산용 가정과 확인할 질문을 구분한다.
9. 실제 AWS 리소스 생성·변경·삭제는 사용자 승인 후 진행한다.
