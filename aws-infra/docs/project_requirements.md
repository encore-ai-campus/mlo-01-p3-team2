# AWS 인프라 요구사항과 현재 구현의 경계

문서 갱신: 2026-10-10. 아래 현재 구현은 로컬 코드·설정과 라우팅 문서에 근거한다. 과거 대화의 요구사항과 실제 배포 성공 여부를 동일하게 취급하지 않는다.

## 1. 프로젝트 목적

게임 이벤트를 Kafka로 수집하고 Spark로 처리하며 MongoDB에 원본을 보관하는 EC2 기반 플랫폼이다. 게임·광고 애플리케이션의 모든 쓰기를 Kafka로 보내려는 요구는 애플리케이션 구현 사항이다. 보안그룹과 설치 플레이북만으로 그 경로를 보장하지 않는다.

## 2. 운영·예산 요구

서울 리전의 AWS 계정 5개와 물리 AZ 2개를 사용한다. 과거 운영 일정은 2026-10-13·14·15·16·19, 매일 09:00~18:00의 총 45시간이다. 계정당 최초 크레딧 $60, 총 $300과 19일 이후 만료 조건은 사용자 답변 기록이며 현재 잔액·정확한 만료 시각은 미확인이다. 준비·테스트 비용과 운영 후 자원 보관료도 계정별 예산에 포함해야 한다.

50·100·150명, 1인당 초당 30개 이벤트는 견적 시나리오다. 서버가 이 부하를 처리한다는 성능 검증 결과가 아니다. 원본을 계속 보관하려는 의도는 유지하지만 백업·장기 보관·삭제 시점은 별도 결정 사항이다.

## 3. 현재 기본 서버 구성

[현재 계정별 배치](costs/account-allocation.md)는 서비스 15대와 선택적 배스천 1대다. Account 1은 Front 2대·game·ad와 별도 배스천을, Account 2는 Mongo-1·Spark-2를 가진다. MySQL 2대·MongoDB 3대·Kafka 3대·Spark 3대이며 크기·대수는 배포 프로필에서 변경할 수 있다. 계정별 자원·통신 비용이 균등하다는 보장은 없다.

MySQL은 2노드 InnoDB ReplicaSet이며 수동 failover를 사용한다. 과거 기록의 MySQL 3노드 InnoDB Cluster와 다르다. Spark는 Master 2개·Worker 3개, ZooKeeper ensemble 3개다. Kafka는 Broker/Controller 3개, MongoDB는 Replica Set 3개다. AZ A에 다수 노드가 있는 배치는 A 전체 장애에서도 클러스터 가용성을 보장하지 않는다.

기본 t3a.small / t3a.large, OS 20GiB/대, 전체 EBS 4,120GiB는 현재 설정 값이다. 데이터 EBS 포맷·마운트가 자동화되지 않았으므로 별도 볼륨을 만들었다는 사실만으로 서비스 데이터가 그 볼륨에 저장된다고 판단하지 않는다.

## 4. 네트워크와 다운로드

VPC CIDR은 10.10·20·30·40·50.0.0/16이다. Account 1의 Public A·C ALB는 HTTP 80, /static/*는 Front, /ads/*는 ad, 기본 경로는 game으로 전달한다. HTTPS 리스너와 인증서를 자동 구성하는 단계가 아니다.

기본 NAT는 0개다. 배스천의 Squid TCP 3128을 통해 사설 서버가 HTTPS 저장소·파일을 다운로드한다. Account 1의 Front 2대에는 EIP를 할당하고 배스천은 자동 공인 IP를 사용한다. 계정 간 서비스 연결은 Peering과 역할별 보안그룹을 사용한다. 포트 범위는 [보안그룹 안내](security-groups.md)를 따른다.

## 5. 자동화가 하는 일

Terraform은 foundation·connectivity·workload·bastion 상태를 분리해 서버와 네트워크를 생성한다. deploy.ps1의 Inventory는 실제 서버 주소와 계정별 키를 Ansible 인벤토리로 연결한다. Proxy는 Squid·APT·다운로드 환경을 준비한다. Deploy나 Proxy를 마쳤다고 MySQL·Kafka·Spark 설치가 끝난 것은 아니다.

플랫폼의 site.yml 역할별 실행에서 서비스를 설치한다. zookeeper 태그만 실행하면 Spark 설치는 진행되지 않으므로 zookeeper,spark를 함께 선택한다. game·ad 애플리케이션은 현재 설치 역할이 없고, backend·monitoring은 해당 인벤토리 그룹이 있어야 실행된다. Ubuntu 프록시 준비 단계의 지원 조건은 Ubuntu 24.04 amd64다.

## 6. 삭제와 데이터 보관

현재 compute 데이터 EBS의 prevent_destroy는 false다. 전체 삭제 실행기는 저장 계획과 명시적 데이터 삭제 동의를 요구하고 소스의 보호 설정을 자동 변경하지 않는다. EBS·서비스 상태·키를 삭제하는 작업과 문서 정리는 별개다. 실제 삭제 범위와 순서는 [실행 안내](deployment-runbook.md)를 따른다.

## 7. 확인이 필요한 범위와 관련 문서

실제 계정 잔액·AMI 제공·AZ 배치·서비스 복제·장애 복구·부하·데이터 보관 정책은 별도 확인한다. 문서의 과거 로컬 테스트 기록은 새로 생성한 EC2의 검증 결과가 아니다.

- [프로젝트 개요](../README.md), [배포·설치 실행 안내](deployment-runbook.md)
- [현재 자원과 과거 비용 견적](costs/README.md), [상세 과거 견적](costs/dual-az.md)
- [코드 탐색용 라우팅 문서](infra-routing/ROUTING-README.md), [플랫폼 설치 안내](../../aws-platform/platform/README.md)

아래 기록은 당시 사용자 답변과 설계 논의의 이력이다. 초기 MySQL 3대·medium 사양·NAT 등 과거 결정 항목이 현재 코드와 다를 수 있으며, 현재 구현을 설명하는 명령이나 배치로 재사용하지 않는다. 이번 문서 정리를 새 설계 승인으로 기록하지 않는다.
